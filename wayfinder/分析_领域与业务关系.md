# 娃娃学习 App · 领域与业务关系分析

> 用途：作为「娃娃兴趣画像 + 个性化出题」扩展的基线。先看清现有 domain / 业务关系 / 接缝，再据此展开产品。
> 依据：`backend/app/models.py`、`backend/app/domain/*`、`backend/app/api/routes/*`、`frontend/lib/features/children/**`、PRD 全三期、产品方案、术语表、项目分析文档。

---

## 1. 现有领域模型（实体与关系）

```
User(家长 1—* 娃娃 自关联)
  │  parent_id
  ├─ Task(parent_id, child_id?, status: draft→ready→assigned→done, specs:JSON)
  │     └─ TaskQuestion(派发快照：深拷贝 Question 全字段，ready/assigned 后冻结)
  ├─ Question(题库层：subject/grade/knowledge_point/qtype/stem/options/answer/explanation/difficulty，可跨 Task 复用)
  ├─ AnswerRecord(child_id, question_id, correct, score, source)
  ├─ WrongQuestion(child_id+question_id 唯一；review_stage/due_at 遗忘曲线)
  ├─ TutorLog(child_id, grade, subject, knowledge_point, question, answer, blocked)
  ├─ TutorQuota(child_id 唯一：daily_ask_limit / daily_minutes_limit / allowed_subjects)
  └─ TutorUsage(child_id + usage_date 唯一：used_seconds)
```

**关键事实：娃娃（child）实体当前只有** `display_name / username / password / grade / is_active / parent_id`。**没有任何兴趣 / 偏好 / 画像字段。** 这是本次扩展的核心落点。

---

## 2. 业务关系与数据流

- **角色**：家长（班主任，注册即管理员）↔ 娃娃（独立账号，按 `parent_id` 隔离，进度/题目/作答互不可见）。
- **出题闭环（F-103）**：
  家长选 `child / subject / grade / knowledge_point / qtype / difficulty / count`
  → `QuestionGenerator.generate(...)`（薄封装）
  → `provider.generate_question(subject, grade, knowledge_point, qtype, difficulty)`
  → 写 `Question` + `Task` → 派发快照 `TaskQuestion` → 娃娃 `/tasks/today` 作答 → `Grader` 批改 → 错题/掌握度/打卡。
- **AI 生成的关键接缝（唯一注入点）**：
  - 抽象：`backend/app/domain/provider.py` 的 `LLMProvider.generate_question(...)` 签名。
  - 实现：`backend/app/domain/langchain_provider.py` 的 `generate_question` —— prompt 模板目前**只含学科/年级/知识点/题型/难度**：
    ```
    请为{grade}年级《{subject}》的“{knowledge_point}”出一道{qtype}题，难度{difficulty}。
    ```
  - Mock：`backend/app/domain/mock_provider.py`（零 key 跑通闭环，测试依赖它）。
- **前端采集接缝**：`features/children/presentation/screens/add_child_screen.dart`
  → `children_remote_data_source.createChild(username, password, displayName, grade?)`
  → `POST /children`（`UserCreate`）。

## 3. 兴趣画像如何接入现有架构（接缝分析）

兴趣**不是 curriculum 锚点**（锚点是 `knowledge_point`），而是出题意境/口味的「调味剂」：
> 例：知识点=「两位数加减法」+ 兴趣=「恐龙」→ 出一道「霸王龙有 23 颗牙，又长出 15 颗，共有几颗？」的应用题。

| 层 | 需要扩展的接缝 | 说明 |
|---|---|---|
| 采集 | `AddChildScreen` + `UserCreate` | 新增兴趣字段（多选/自由文本） |
| 存储 | `User` 表（加 `interests: JSON`）或独立 `ChildProfile` 表 | 见下方决策 |
| 生成抽象 | `LLMProvider.generate_question` 加 `interests` 形参 | 业务层不绑定具体厂商 |
| 生成实现 | `langchain_provider.generate_question` prompt 增加兴趣语境 | 约束：紧扣 `knowledge_point`，不偏离教材 |
| Mock 一致性 | `mock_provider` 同步接收 `interests` | 保证零 key 闭环测试不破 |
| 安全/管控 | `_SYSTEM` 年龄锁 + `TutorQuota` 学科白名单 | 兴趣仅作口味，**绝不绕过**内容安全与 curriculum |
| 迁移 | 当前无 Alembic，`init_db` 用 `create_all` | 加列需数据回填（旧 child → 空数组/默认） |

## 4. 业务关系扩展点（产品展开方向）

1. **参与度驱动**：产品方案已识别「低龄娃娃学习动力难维持」是核心痛点；兴趣题是直接的激励杠杆。
2. **交叉洞察**：兴趣 × 薄弱点（如「喜欢恐龙但恐龙应用题正确率低」）可成为家长看板的新维度。
3. **答疑个性化**：`TutorService.explain` 举例时也可结合兴趣（正交于现有安全/管控，不冲突）。
4. **与现有约束正交**：账号隔离、答案隔离、内容安全双层、学科白名单、Alembic 缺失等技术债均不被破坏，只需在既有接缝上增量扩展。
