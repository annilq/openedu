# Spec：AI 意图路由归一（所有服务走同一个裁决点）

> 决策依据：[ADR-0081 §2.3](../adr/0081-tasks-ai-converge-to-chat.md)（本节已由本 spec 反转）。
> 设计底稿：[`docs/refactor/2026-10-10-ai-intent-routing-unification.md`](../refactor/2026-10-10-ai-intent-routing-unification.md)。
> 术语以 `CONTEXT.md` 为准（题目 / 题库 / 任务 / 任务题 / 错题 / 错题本 / 复习项 / 结构化动作 / SubAgent / 会话）。
> 本文件是 GitHub issue 的正文源；落库后以 issue 为准。
> 范围：P0（动作通道）+ P1（两处改判迁进信号）+ P2（`req.quiz` 走运行时），**一次写全**。

## Problem Statement

AI 学习助手名义上有一个意图路由：所有请求先由 `AgentRuntime.decide` 判定交给哪个 SubAgent（任务引导 / 学情查询 / 出题助手 / 伴学答疑），再流式运行。但实际上**每加一个新特性，都不是在路由器里加规则，而是在对话编排函数里加一个 `if`**。

今天只有一处真正调用路由，旁边却有四处在覆盖或绕过它：

1. 课件练习的上下文定向——路由**算完之后**再改判（「提示」改去伴学答疑、出题改去任务引导）。
2. 判断题闭环——`quiz` 标记的请求**完全不走运行时**，直连出题管线，连 `run` 都不经过。
3. 待判定态——消费待判定态后**强制**改判到伴学答疑。
4. 结构化出题——**根本不调路由**，`business` 写死为出题助手，传给路由的用户消息是**空串**。

这造成四类具体问题：

**一、跨切面能力在不同链路上时有时无。** 学生输入安全闸门只在对话链路上挂了；结构化出题那条路自己构造依赖且把闸门设为无，所以学生出题时输入不设防。出题助手该有的资料库检索、学科提示、溯源引用，在「换一题」上**一项都没有**——因为换一题走的是直连出题管线那条路，不是运行时。教师会感觉「换一题换出来的题比第一次出的差」，这是真的差，不是错觉。

**二、越权和错配被静默吞掉。** 路由结尾有一条兜底：算出来的业务若对当前角色不可见，就悄悄换成第一个可见业务。对自然语言是无害兜底，对结构化动作就是把「你不能用这个功能」变成「答非所问」——不报错、不拦截，最难排查的那种。

**三、触发词在互相抢。** 为了压住对方，各 SubAgent 的优先级被一路抬上去（任务引导 20 压学情查询 12，学情查询 12 又是为接住另一个被撤掉的业务）。每新增一个业务就要重新调一遍这张表。而学情查询的触发词里有一个单字「查」，优先级又高于伴学答疑，于是「查一下这道题为什么选 B」被只读检索接走——用户要的是讲解。

**四、文档里承诺的能力并不存在。** 路由模块收下一个「可选的 LLM 意图分类器」参数，函数体里**从来没有调用过它**；两个依赖构造点也都没注入。文档写的「规则 → 启发式 → LLM 兜底」三级路由，第三级是空的。留着它会让人以为「接上 LLM 分类就好了」。

实测确认了「让路由去猜结构化请求」行不通：把结构化规格合成一句自然语言再交给现有路由，`出 3 道四年级下学期数学题，知识点：轴对称` 落到**伴学答疑**，`换一题` 落到**伴学答疑**，空串也落到**伴学答疑**。

## Solution

**把路由的输入从「一段文本」升级为「结构化意图信号」，路由仍是唯一裁决点。**

信号有三部分：用户原始输入（结构化请求时可为空）、结构化动作键、结构化上下文。路由变成三级：

1. **动作直配**：动作键与各 SubAgent 清单里声明的 `actions` **等值**匹配，命中即路由。它**排在触发词匹配之前**，且**不参与优先级排序**——所以不存在「谁的词更长、谁的优先级更高」，也就没有竞争。
2. **触发词规则匹配**：现有逻辑完全不变。
3. **启发式兜底词 + 最低优先级兜底**：现有逻辑完全不变。

「哪个业务拥有哪个动作」从此是**一张声明在 SubAgent 清单里的表**，不是散在对话编排里的 `if`。新增一个动作 = 清单加一行，不动任何业务代码。

配套三条硬约束：

- **动作命中但业务对当前角色不可见** → 返回显式的「动作不可见」（端点转 403），**不许**再用那条「换成第一个可见业务」的静默兜底。
- **未知动作** → 落回自然语言路由，不报错（保持容错）。代价是动作名与清单不同步时会静默失效，所以必须有契约测试兜住。
- **删掉那个从未生效的 LLM 分类器参数**，连同它的声明与透传。

真正的收益不是「路由更准」，而是**裁决点归一**：输入安全闸门、角色可见性、助手名解析、将来的配额与观测，都只在一个地方生效一次。

## User Stories

1. 作为教师，我希望按规格出题时请求仍经过与对话同一个路由，这样我出的题和助手里出的题走同一套能力。
2. 作为教师，我希望「换一题」也经过同一个路由，这样换出来的题同样能用上我上传的资料、学科提示和溯源，而不是比第一次的差。
3. 作为教师，我希望「换一题」时资料库检索真的生效，这样我上传的讲义能影响重新生成的题。
4. 作为学生，我希望能让助手出题给自己练，这样我不用等教师布置。
5. 作为学生，我希望我出的题同样经过输入安全闸门，这样不适内容在我这条路上也被拦下。
6. 作为学生，我希望我用自己的角色打教师专属动作时，收到的是明确的「不能用」而不是一段答非所问的回答，这样我不会以为助手坏了。
7. 作为教师，我希望我打一个不存在的动作时，请求退化成按我说的话正常路由，这样一次拼错不会整条失败。
8. 作为学生，我希望「查一下这道题为什么选 B」得到讲解而不是只读检索结果，这样我不用换个说法再问一遍。
9. 作为学生，我希望说「为什么」「讲解」这类词时一定落到伴学答疑，不被单字触发词抢走。
10. 作为教师，我希望在课件练习里说「提示」时得到提示、说「出题」时被引导到对应页面，这两种不同的语义不要被拍平成同一件事。
11. 作为教师，我希望在课件练习里出题时拿到的是「去哪儿出题」的出口，而在助手里出题时拿到的是题卡，这两个场景保持各自的行为。
12. 作为学生，我希望在判断题闭环里作答后，判定与讲解由模型结合题目给出，而不是固定的几句模板话。
13. 作为教师，我希望判断题闭环也经过运行时，这样它能拿到资料库检索、学科提示和溯源。
14. 作为教师，我希望所有 AI 请求无论走哪条路，产出的事件帧序列是同一套，这样前端不用为每条路写一种渲染。
15. 作为维护者，我希望新增一个结构化动作只需要在 SubAgent 清单里加一行，不用改对话编排函数。
16. 作为维护者，我希望「哪个业务拥有哪个动作」是一张可被测试断言的表，而不是散落在各处的条件分支。
17. 作为维护者，我希望新增业务时不需要再去调整优先级表，这样不会再出现「为了压住别人把优先级一路抬上去」。
18. 作为维护者，我希望动作命中不受清单遍历顺序影响，这样重构不会悄悄改变路由结果。
19. 作为维护者，我希望动作不可见时拿到显式的不可见结果，这样我能把它翻译成 403 而不是静默换一个业务。
20. 作为维护者，我希望那个从未被调用的 LLM 分类器参数被删掉，这样没人再误以为路由已有第三级兜底。
21. 作为维护者，我希望每个已声明的动作恰好有一个归属业务、没有孤儿也没有悬空，这样动作名改错时会被测试拦下而不是静默失效。
22. 作为维护者，我希望学生走结构化出题时安全闸门确实被调用，这样这条链路的防护是可断言的。
23. 作为维护者，我希望这次改动不重排任何触发词优先级，这样已实测过的路由结论（如「帮我创建一个任务」落到任务引导）不会被推翻。
24. 作为前端开发者，我希望判断题闭环改走运行时后新增的帧是已知的几类（用户消息帧、两条路由思考帧），这样我只需在现有折叠逻辑里多忽略几类，不用新写渲染器。

## Implementation Decisions

**路由输入升级为结构化意图信号。** 新增一个不可变信号对象，承载三样东西：用户原始输入（结构化请求允许为空）、结构化动作键（可为无）、结构化上下文（可为无）。运行时的 `decide` 改为接受它；为迁移期保留「只传文本」的旧调用形式，避免一次性改动所有调用点。

> 信号类型形状（来自设计底稿，非可运行原型；只列承载决策的部分）：
>
> ```
> IntentSignal:
>   text:    str              # 用户原始输入，结构化请求可为空
>   action:  str | None       # 结构化动作键
>   context: dict | None      # 结构化上下文（课件 / 待判定态）
> ```

**三级路由，动作直配排在最前且不参与优先级。** 路由模块新增动作匹配：动作键与清单 `actions` 等值比较，命中即返回。它在触发词匹配之前执行，且不参与任何优先级排序——唯一性由契约测试保证（见下），因此不需要排序规则。未命中动作则完全沿用现有触发词与启发式逻辑。

**动作归属声明在 SubAgent 清单里。** 清单数据结构新增 `actions` 字段（默认空）。出题助手声明拥有「按规格出题」与「换一题」两个动作。对话编排函数里不再出现「有动作则写死某个业务」的条件分支。

**动作不可见必须显式，不许静默回落。** 现在路由结尾有一条「若算出的业务对当前角色不可见，就换成第一个可见业务」的兜底。这条兜底对自然语言保留；对**动作路由**必须换成分支：返回业务为空且带上「动作不可见」的原因，由端点翻译成 403。理由：静默回落会把越权变成答非所问，不报错、不拦截。

**未知动作回落自然语言路由，不报错。** 保持对未知动作的容错。这是有意的取舍：代价是动作名与清单不同步时会静默失效，因此**必须**由契约测试兜住（每个已声明动作恰好一个归属业务、无孤儿、无悬空）。

**删除从未生效的 LLM 分类器参数。** 路由模块收下该参数但从不调用，依赖端口声明了它但两个构造点都没注入。连同端口声明与运行时透传一并删除。理由：留着一个不生效的扩展点会让人误判现状；真需要弱意图兜底时重写一个真被调用的扩展点，并把「是否启用」做成显式配置——那是独立议题。

**修掉单字触发词「查」。** 学情查询的触发词里有一个单字「查」，其优先级高于伴学答疑，导致「查一下这道题为什么选 B」被只读检索接走。移除单字，保留已有的双字以上触发词，并把这条实测结果钉进回归。

**P1：两处「路由后改判」迁进信号。** 课件上下文定向与待判定态定向，改为在信号归一化阶段产出动作键，由清单声明归属，不再在路由算完之后改判。⚠️ 一处必须保留的语义差别：课件练习里「出题」的归属是**任务引导**（把用户引导到页面），助手里「出题」的归属是**出题助手**（真的出卡）。迁移时不得把两者拍平成同一个动作键，否则会丢失这个区别。

**P2：判断题闭环改走运行时。** `quiz` 标记的请求不再直连出题管线路，改由运行时以出题助手运行，从而拿到资料库检索、学科提示、溯源引用与工具信封。⚠️ 帧序列会变化：运行时会多产出用户消息帧与两条路由思考帧，前端折叠逻辑需同步多忽略这几类。

**不重排任何触发词优先级。** 现有优先级是实测调出来的（任务引导 20 压学情查询 12 就是为了让「帮我创建一个任务」不被只读查询接走）。本次改动让动作通道完全绕开优先级比较，因此无需也不应重排；重排会推翻既有实测结论。

**依赖顺序。** P0 是 ADR-0081 中「给对话接口增加结构化动作字段」的前置——先有动作通道，动作字段才有落点。P2 的帧序列变化需与前端折叠逻辑同批。

## Testing Decisions

**接缝：只有一个——`AgentRuntime.decide`。** 所有断言都打在它的返回值（路由决策）上：动作直配结果、动作不可见时返回显式不可见而非回落、未知动作回落自然语言路由、安全闸门是否被调用。既有先例就是这么测的（SubAgent 运行时测试里那组路由用例：教师出题 / 教师查询 / 教师伴学 / 学生越权改判 / 学生查询可见 / 学生不安全输入被拦），本次沿用同一形状，不新增接缝。

**好测试的判据：只断言外部行为，不断言实现细节。** 具体说——断言「给定这个信号和这个角色，路由决策是什么」，不断言「路由内部先走了哪一级、匹配了第几个词」；断言「安全闸门被调用」，不断言「依赖对象里挂了哪个具体实现」。这样三级路由后续怎么重排，测试都不会碎。

**被测模块：** 路由模块（动作直配、回落、不可见分支）、运行时（决策组装与可见性过滤）、SubAgent 清单（动作声明）、对话编排（信号归一化）。端点层与数据库不在本接缝内，不测。

**新增契约测试（防静默失效）：**
- 每个已声明的动作**恰好一个**归属业务；无孤儿（声明了但没有请求方）、无悬空（有请求方但没声明）。
- 动作命中**不受清单遍历顺序影响**（打乱顺序结果不变）。
- 动作命中但角色不可见 → 显式不可见，**不是**第一个可见业务。
- 未知动作 → 落回自然语言路由。
- 学生走结构化出题时输入安全闸门**被调用**（现在这条链路没调用）。

**回归测试（钉实测）：** 把实跑出来的路由结果钉住——空串、合成的出题句、「换一题」均落到出题助手；「查一下这道题为什么选 B」落到伴学答疑；既有路由用例全绿；后端全量保持无失败。

## Out of Scope

- **归属模型**：ADR-0082 的题目归属（`owner_id`）与学生题库，不在本 spec 内。本 spec 只解决「请求交给谁处理」，不解决「题目归谁所有」。
- **答案可见性**：ADR-0081 §2.8 已决定服务端一律全量下发、由客户端按角色控显，本 spec 不涉及。
- **端点删除与 URL 收敛**：ADR-0081 中删除结构化出题端点、两个同步重生成端点的处置，属于那一份 ADR 的落地，不在本 spec 内。
- **前端渲染**：除 P2 引起的折叠逻辑需多忽略几类帧外，前端其余改动不在本 spec 内。
- **重排触发词优先级**：明确不做，理由见上。
- **接上真正的 LLM 意图分类**：本 spec 只删除那个从未生效的参数；真要做弱意图兜底是独立议题。
- **导出、统计、迁移脚本**：不受本次改动影响，不涉及。

## Further Notes

**为什么「都走意图路由」不能按字面实现。** 实测：把结构化规格合成一句自然语言再交给现有路由，`出 3 道四年级下学期数学题，知识点：轴对称` 落到伴学答疑——因为出题助手的触发词是「出题 / 出几道 / 题目 / 来几道」，一个都匹配不上「出 3 道…题」，启发式也落空，最后掉到兜底的最低优先级业务。这不是词表不够全，是**文本匹配这个机制不适合结构化请求**。而结构化出题现在传给路由的用户消息本来就是空串，直接改成走路由只会更糟。

**取舍：为什么动作不可见要报错而不是静默回落。** 静默回落的好处是「用户总能得到一个回答」，坏处是这个回答是错的且无法归因。对结构化动作（通常是按钮触发、语义明确）而言，答非所问比报错更糟。

**取舍：为什么未知动作不报错。** 与上面相反——未知动作通常来自版本错配或拼错，回落自然语言能让请求「尽量还是能用」。它带来的静默失效风险由契约测试承担，而不是让所有用户承担一次硬失败。

**已知技术债（本 spec 不修，但记录）：** 结构化出题那条链路构造依赖时把安全闸门设为无，这个缺口在它并入统一路由后自动消失；在那之前，它就是学生出题不设防的实际原因。
