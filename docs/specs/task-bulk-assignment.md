# Spec：作业批量派发

> 决策依据：[ADR-0069 作业批量派发](../adr/0069-task-bulk-assignment.md)。

## Problem Statement

教师布置作业的方式是**一次只能给一个人**：

1. **给全班布置同一份作业要重复几十次。** 派发接口只接收单个学生，一个 40 人的班要点 40 次派发，产生 40 条几乎一模一样的任务记录。
2. **任务列表爆炸。** 一次作业在学生侧是一份，在教师侧变成 40 条，任务页滚不到底。
3. **没法知道谁没交。** 任务状态只有「已派发 / 已完成」，且是**整份任务**的状态，教师看不出 40 个人里谁做完了、谁还没动。
4. **改派、撤派无从下手。** 想从作业里去掉一个人、或者补派给一个新转来的学生，只能作废重来。

这些在「一个教师带一两个学生」的规模下只是低效，在引入班级之后就变成结构性阻塞——**班级如果不能批量派发，就只是一个显示用的标签**。

## Solution

把任务从「一个学生的派发容器」升格为**作业模板**：新增**作业派发对象**关系，一份任务可以一次派发给多个班级或指定的多个学生。派发对象展开去重后写入，每个被派发的学生一条关系，携带派发时间与完成时间——「谁交了 / 谁没交」由此回答。

任务列表回到「一份作业一条」，条数反而下降。

## User Stories

1. 作为教师，我想一次把一份作业派发给整个班级，以便不用重复点几十次。
2. 作为教师，我想一次派发给多个班级，以便跨班布置同一份作业。
3. 作为教师，我想在派发时额外勾选几个不在这些班里的学生，以便照顾特殊名单。
4. 作为教师，我希望同一个学生既被班级选中又被我单独勾选时**只派发一次**，以免出现重复记录。
5. 作为教师，我想看到这份作业派给了哪些人、谁已完成、谁还没交，以便催交。
6. 作为教师，我想从作业里取消某几个学生的派发，以便处理转班或误派。
7. 作为教师，我希望取消全部派发对象后作业回到「待派发」状态，以便我重新派给别的人。
8. 作为教师，我想在任务列表上看到这份作业派给了多少人，以便一眼分辨是个人作业还是全班作业。
9. 作为教师，我想按班级过滤任务列表，以便只看某个班的作业。
10. 作为学生，我只想看到派发给我的作业，以便不被别人的任务干扰。
11. 作为学生，如果某份作业没有派发给我，我希望答题时被明确拒绝，而不是产生一条不属于任何人的作答记录。
12. 作为学生，我做完一份作业的全部题目后，希望我的完成状态被单独记下来，以便教师看到我交了。
13. 作为教师，我希望作业在**所有**被派发学生都完成后才标记整体完成，而不是第一个人做完就算完成。
14. 作为学生，我希望即使别的同学已经做完，我仍然可以继续作答我自己的那一份。
15. 作为教师，我希望打卡也只认「这份作业派发给了我」，以便打卡数据不串。
16. 作为教师，我希望已有的历史作业在升级后仍然能被正确识别派给了谁，以便老数据不丢。
17. 作为教师，我希望一次派发是原子的——要么全部成功，要么一个都不写，以免出现派了一半的作业。

## Implementation Decisions

**数据模型**

- 新增**作业派发对象**关系表：任务 + 学生 + 派发时间 + 完成时间（可空），`(task, student)` 唯一。
- 唯一约束必须写在 `CREATE TABLE` 里。SQLite 的 `ALTER TABLE ADD COLUMN` 会静默忽略 `UNIQUE`，事后补不上（ADR-0061 §R）。
- 任务表现在那个单值学生列**保留但不作为事实源**：新代码一律读派发对象关系，**不做双写**。保留它是兼容旧客户端读路径的过渡态，后续单独立项移除。

**派发语义**

- 派发接口入参从「单个学生」改为「班级列表 + 学生列表」，服务端展开后**按学生去重**（同一学生可能既来自班级又来自显式列表），批量写入。
- 两个列表都为空 → 422。
- 任务状态从「一个学生的状态」变为**作业整体状态**：首次派发后置为已派发；**全部**派发对象都有完成时间时自动转为已完成。
- 学生答完该作业全部题目 → 写入该派发对象的完成时间。
- 新增「派发对象列表」端点，返回每个人的完成时间，即谁交了谁没交。
- 新增「取消派发」端点；全部取消后状态回退到待派发。

**必须改造的三处**

- 答题校验：从「按任务上的单值学生列定位」改为「查这条派发关系是否存在」，不存在即拒绝。这是**必修项**，否则批量派发后除第一个人之外的所有人都无法作答。
- 打卡校验：同样只认派发关系。
- 学生端「今日任务」：从「我名下已派发的任务」改为按派发关系过滤。

**不需要改的（本 spec 成本可控的关键）**

- 作答记录、打卡记录、错题**都已自带学生维度**，不依赖任务上的单值学生列。因此答题、错题归集、复习队列、进度、掌握度整条下游链路**不需要改动**。
- 教师端任务列表改为一份作业一条，带班级与派发人数，条数**下降**。
- 导出练习卷需复核：确认是导出整卷还是按学生分卷。

**迁移**

- 启动期幂等建表，并从历史任务上的单值学生列回填派发关系（派发时间取任务创建时间；已完成的补完成时间，无更精确的历史数据）。
- 回填后**不清除**单值学生列（过渡期保留）。

## Testing Decisions

**主测试缝：REST 端点。** 沿用仓库既有的端点测试缝——FastAPI TestClient 打真实临时 SQLite 库（夹具 `tests/conftest.py` 的 `client`，身份助手 `tests/utils/user.py`）。建任务的先例见 `tests/api/routes/test_wrong_questions.py`（用「已生成题卡」直接落库，是唯一业务写库点）。

测试只断言**外部行为**：发请求看响应，再看随后的 `GET` 与登录学生自己的视角。不直接调用内部函数、不断言私有实现细节。

必测场景：

- 整班派发：一个班 N 人 → 派发对象恰好 N 条，任务列表仍是 1 条
- 班级 + 显式学生**交集去重**：重叠的学生只出现一次
- 两个列表都空 → 422
- 未被派发的学生答题 → 403（这是本 spec 最容易回归的一处）
- 被派发的学生答题 → 成功并产生作答记录
- 全员完成后任务整体状态自动转为已完成；只完成一半时任务**仍是已派发**，且未完成的那个学生**仍能作答**
- 取消部分派发、取消全部派发后状态回退
- 学生端「今日任务」只见派给自己的
- 老库回填幂等：重复执行迁移不产生重复关系
- 越权：别的教师对我的任务派发 / 取消应 403

运行纪律：`pytest` 沙盒须 `--basetemp`；端点级验证必须**逐个派发对象账号真实调答题接口**，只改 service 不落端点等于没做。

## Out of Scope

- 跨班级共享作业模板（作业仍属单个教师）
- 同一作业对不同学生出**不同题**（本轮一份作业 = 一份题集）
- 按学生覆盖截止时间
- 批改结果回流到掌握度（ADR-0065 §7 维持关闭）
- 「谁没交」的提醒推送 / 催交通知

## Further Notes

- **任务状态语义是破坏性变更。** 前端任何按「已完成」判断「不能再作答」的逻辑都要复核：现在「已完成」意味着全班都做完，个别学生完成后必须仍能继续作答。这是本 spec 最可能的回归点。
- 过渡期存在单值学生列与派发关系两套数据，回填前建的任务与回填后建的任务行为必须一致，需要测试钉住。
- **自动判完成依赖完成时间的准确写入。** 答一半就走的学生会让作业永久停在「已派发」。本轮接受，教师可作废重建。
- 派发必须原子：一次请求内要么全部写入要么全部回滚，不允许出现派了一半的作业。
