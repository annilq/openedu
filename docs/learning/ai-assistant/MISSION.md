# Mission: 读懂并演进 openedu 的 AI 助手 Agent 架构

## Why
用户是这个仓库的主导开发者，需要**在不破坏既有边界的前提下持续给 AI 助手加能力**：新增 SubAgent、新增查询工具、新增卡片、换模型厂商、改路由。要做到这一点，光知道「代码在哪」不够——必须能回答「这条缝为什么画在这里」，否则新代码会照着错的先例长，把已经付过学费的缺陷重新做一遍。

## Success looks like
- 能对着一条用户问句，把从 SSE 请求到卡片渲染的完整链路口述出来，并指出每一步由哪一层负责。
- 新增一个 SubAgent / 工具 / 卡片时，能自己列出「必须同步改的几个点」和「会被哪条守卫测试拦下」。
- 面对「要不要上 LangGraph / 上 GenUI / 用 LLM 做意图分类」这类选型问题，能说清本仓的取舍依据与代价，而不是凭印象。
- 出错时（401、独白当答案、工具空转）能立刻定位到是归因、协议分流还是 schema 的问题。

## Constraints
- **重架构轻实现**：用户明确要求「不需要具体技术实现细节，重点在技术流程、架构」。每课只讲机制与取舍，不贴大段源码。
- 事实必须以本仓代码与 ADR 为准；推测要标注。
- 时间碎片化：每课应在一次坐下来的时间内读完，可打印。
- 用户偏好简洁的技术说明 + 可执行的 next steps。

## Out of scope
- Flutter 设计系统细节（另有 `.impeccable.md` 与 ADR-0044~0046）。
- 出题提示词工程与学科 Persona 的具体文案。
- 前后端其他 feature（任务、复习、导出）的业务规则，除非与 AI 链路共用领域规则。
