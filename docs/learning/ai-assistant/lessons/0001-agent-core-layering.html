分层与内核：为什么内核不认识「数学题」

openedu 的 AI 助手把一个「能出题、能答疑、能查学情」的助手拆成了业务无关的内核与业务集成层两半。这一课讲清这条缝画在哪、为什么画在这里。

事实源：backend/agent_core/ · backend/app/ai/subagents/ · ADR-0024 / 0031 / 0032 / 0021 / 0033 / 0026 · 建议先读 docs/agents/architecture.md §1

本课知识点

  1. 所有 AI 能力走一个端点
  2. 内核 / 集成层二分
  3. 端口与适配器：依赖指向抽象
  4. 发现即注册：文件夹化 SubAgent
  5. 意图路由：确定性优先
  6. 角色可见性是唯一真相源

一、入口与分层

1所有 AI 能力收敛到一个 SSE 端点

出题、伴学答疑、学情查询、写意图引导——四类能力对客户端只暴露 POST /api/v1/assistant/chat 一个地址，响应是一条 Server-Sent Events 流。旧的三条端点（/ai/tutor/ask、/ai/tasks/generate、/tutor/ask）已废弃收敛。

架构优点

新增一种 AI 能力 = 新增一个 SubAgent 文件夹，端点零改动、客户端零改动。鉴权、缓冲头（X-Accel-Buffering: no）、空消息校验这些 HTTP 关注点也只有一处可审计。

当时的设计决策

早期是每个能力一个端点，客户端要为「出题」「答疑」「批改」各写一套解析。ADR-0024 把它收成一条流，并强制 router 只做 HTTP 适配——编排不许留在 HTTP 层，否则 ORM 与领域类型会泄漏进路由文件（评审时那个文件已膨胀到 700+ 行）。

同类主流实现方式

① 每能力一端点（传统 REST：/generate、/explain）：简单直观，端点即文档，但客户端要为每种能力写一份解析与重试。
② 服务端托管会话的 run 模型：OpenAI Assistants / Responses 的 threads + runs，LangChain 的 Agent Protocol（/threads + /runs/stream）——把多轮状态放到服务端，本仓的会话表是同一思路的自建轻量版。
③ 通用 agent 交互协议：AG-UI 用「一条有序类型化事件流」把任意框架接到前端（注意：其规范目前仍是 draft）。openedu 的事件帧是 AG-UI 式，但不是它的完整实现。

代价 / 遗留

「一个端点」意味着协议要在帧里自解释：客户端必须靠 eventType 判别，任何新增语义都得走 extra 扩展而不是加新帧类型，否则协议会膨胀。

ADR 锚点：ADR-0024（统一 SSE 端点）· ADR-0025（事件帧契约）

2内核 / 集成层二分：内核不认识「数学题」

agent_core 是与业务、与 FastAPI、与具体 LLM SDK 解耦的纯 Python 内核；app 是 FastAPI 集成层。两者同发一个 wheel，但在 import 层面被硬切开。业务字段（学科、年级、孩子 id）一律走 SubAgentContext.extra 透传，内核只搬运不解读。

架构优点

内核可独立发包、可被另一套业务复用；业务语义变化（新增学科、新增题型）不触达内核；内核的 9 条不变量由 CI 用 AST 静态扫描守住，不是靠 review 纪律。

当时的设计决策

ADR-0031 把 LLMProvider 端口上移到内核时明确否掉了「在 app 层直接持有 provider 实现」——那样内核就不可移植。边界被写成可测的不变量：agent_core（除 adapters/）不得 import app.*、不得 import 任何三方库；service 不得反向依赖 router/FastAPI；归属判定只经 core.guard。

同类主流实现方式

① 单一全栈框架（LangGraph / AutoGen / OpenAI Agents SDK）：编排、状态、工具、持久化由框架一起提供，起步快，但框架概念会渗进业务代码，换框架＝重写。
② 纯库式内核 + 业务自写编排：Pydantic AI、Vercel AI SDK 这类，抽象薄、可控，但限流 / 轮次 / 回灌这些边界要自己补。
③ 本仓：自写极薄内核 + 显式不变量扫描。适合「能力种类少、但对确定性与儿童安全要求高」的场景。

代价 / 遗留

自写内核意味着框架生态（可视化调试、持久化 checkpointer、现成的 human-in-the-loop）都没有，context compaction、后台钩子等能力要自己补（ADR-0035 的钩子 seam 就是补的一条）。

ADR 锚点：ADR-0031（端口上移）· ADR-0032（wheel 打包）· 守卫 tests/ai/test_layering_invariants.py

3端口与适配器：依赖方向恒指向抽象

内核只定义四个抽象端口：LLMProvider（消息级大模型）、Retriever（检索）、Safety（安全闸门）、RuntimeDeps（一次请求的依赖包）。具体实现落在 agent_core/adapters/genkit.py——全工程唯一 import genkit 的地方，且是函数体内延迟导入。

架构优点

换模型厂商只改适配器一个模块；没装 genkit 也能 import 内核（测试可用替身 provider 跑通整条编排）；「引擎解析」与「引擎构造」分离——密钥解密、模型目录在 app 层，构造在适配器层。

当时的设计决策

ADR-0030 把引擎解析收成单一链 resolve_engine（家长 ModelConfig → 解密 → 中性参数 → 适配器构造），否掉了「各 service 各自解析引擎」——后者会让「批改忽略所选模型」这类分裂反复出现。ADR-0039 进一步取消内置模型目录，唯一配置源是家长在客户端录入的 ModelConfig。

同类主流实现方式

① 直接依赖 SDK（各处 import openai）：最常见也最省事，代价是换厂商要全仓改、单测必须打桩网络。
② 统一网关 / 代理：LiteLLM、OpenRouter 在做「一个接口对多家」，把差异吃掉；但多一层运行时依赖与故障面。
③ 多适配器并列：LangChain 的 provider 生态就是这条路，本仓只留一个适配器，是因为当前只有 ollama 与 openai_compat 两种形态。

代价 / 遗留

「唯一落点」是静态扫描守出来的，任何人手抖在别处 import 一下就红；同时适配器的延迟导入让类型检查变弱，需要契约测试补位。

ADR 锚点：ADR-0030（引擎单一解析链）· ADR-0034（build_ai_provider 归一封装）· ADR-0039（模型来源单点化）

二、能力怎么长出来

4发现即注册：新增能力 = 丢一个文件夹

每个 SubAgent 是一个文件夹：agent.py（执行体）+ manifest.py（声明）+ tools/（可选工具）+ skills/（SOP 提示词）。启动时扫描目录自动注册，没有任何手工登记表。

app/ai/subagents/
├── guide/      priority 20 · roles[parent]        「创建/派发任务」→ 引导卡
├── query/      priority 12 · roles[parent,child]  只读查询（8 个工具）
├── question/   priority  0 · roles[parent]        流式出题（schema 约束解码）
└── tutor/      priority -10· roles[parent,child]  伴学答疑（单调用）
架构优点

能力清单在文件系统里即可读全；新增能力不触碰任何注册代码；manifest 同时承载路由词表、可见角色、优先级与 SOP，**一个文件即是该能力的全部对外契约**。

当时的设计决策

「业务维度 = SubAgent，学科维度 = Persona，二者正交组合」——否掉了「每学科每业务各建一个 Agent」（组合爆炸），也否掉了「一个通用 Agent 靠 system prompt 切换」（seam 难维护）。同理 RAG 命中与学科人格由调用方注入，出题管线只消费不持有，保证流式与落库两路 prompt 口径一致。

同类主流实现方式

① 显式图构造：LangGraph 的 add_node/add_edge，节点与边一清二楚、可可视化，但每加一个能力要改构图代码。
② 装饰器注册：OpenAI Agents SDK、CrewAI 的 @agent/@tool，注册点分散在模块里。
③ 目录约定 + 自动发现：本仓与 Claude Skills、各类插件系统同路，约定优于配置。

代价 / 遗留

路由词表写在 manifest 里，改词表等于改路由行为，必须有守卫测试；文件夹命名与 business 字段不一致时会静默错位（靠发现时打印告警，不阻断）。

ADR 锚点：ADR-0021（业务 × 学科正交）· ADR-0033（文件夹化 SubAgent）

5意图路由：确定性优先的三段式

输入先按角色过滤出「可见业务集」，过安全闸门，然后按 priority 降序做子串规则匹配（triggers）；全不中才用更宽的 hints 启发式；再不中就落到 priority 最低者（tutor）。分类器接口预留了 LLM 兜底，但默认不启用。

架构优点

路由结果可预测、可单测、零延迟、零 token。对儿童产品这是硬要求：同一个问句每次必须落到同一个助手，不能因为模型心情不同而走不同分支。

当时的设计决策

真机教训（ADR-0054）：家长说「帮我创建一个任务」被只读的 query 接走，因为 query 的词表含泛词「任务」且优先级最高。修法是新开 guide（priority 20）专接写意图——优先级不是调参，是功能本身。同时 guide 的词表只收「动作+对象」完整短语、hints 故意留空：写意图要精度，宁可漏给 query 也不误抢查询。

同类主流实现方式

① LLM 意图分类：一次小模型调用打标签，覆盖面广、能处理改写与口语，但引入延迟、成本与非确定性。
② 语义路由：embedding 相似度匹配（semantic-router 一类），比子串更抗措辞变化，仍需阈值调参。
③ supervisor / handoff 模式：让主 agent 自己决定分发给哪个子 agent（LangGraph supervisor、OpenAI Agents SDK 的 handoffs），灵活但完全交给模型。
④ 混合（本仓）：规则打底 + 可选 LLM 插槽，是儿童产品里常见的稳妥解。

代价 / 遗留

词表要人工维护，泛词会互相抢；priority 成了隐式耦合——新增能力必须先想清楚它压过谁。所以 ADR-0054 要求「优先级结构」本身被测试钉死。

ADR 锚点：ADR-0030（规则 + 启发式）· ADR-0054（写意图 guide 与优先级即功能）

6角色可见性是唯一真相源

每个 manifest 声明 roles，runtime 用 visible_businesses(role) 过滤，分类器只在可见集内决策——不可见的能力在路由阶段就不可达，而不是「路由到了再靠提示词拒绝」。娃娃端说「帮我创建任务」会落到只读答复，这不是遗漏，是边界。

架构优点

安全边界落在结构上而非提示词上：娃娃端拿不到出题、拿不到答案，不是因为模型「听话」，而是因为那个 SubAgent 根本不在可见集里。这一条可以被单测断言。

当时的设计决策

ADR-0026 最初把娃娃端强制收敛到伴学；ADR-0033 放宽为「可见学情查询，但工具侧恒查自己、去答案」。放宽的前提是裁剪下沉到工具侧（project_for_role）——统一收口，新增工具忘了裁剪会被契约测试拦下，不靠 review。另一条：SOP 文本本身含「越狱/暴力」等安全词，所以 SOP 必须在输入闸门之后注入，否则每条娃娃提问都被自己的 SOP 判为不安全。

同类主流实现方式

① 提示词里写「不要告诉孩子答案」：最常见的软约束，模型一被诱导就破防。
② 工具层 RBAC / 租户隔离：在取数层做权限过滤，与业务强耦合但最硬；本仓的 core.guard + 工具侧裁剪是这条路。
③ 协议层能力协商：MCP 的 roots / sampling 让服务端声明可见范围，思路相近但面向跨进程。

代价 / 遗留

「可见性」分散在两处（manifest 的 roles、工具侧的裁剪），新增能力要同时想清楚两层；跨层越权只能靠测试发现。

ADR 锚点：ADR-0026（娃娃端收敛）· ADR-0033 决策 8/9（角色裁剪只在工具侧）

检索练习（先想再看）

1. 为什么「新增一种 AI 能力」在本仓不需要改端点和客户端？

因为能力差异被封装进 SubAgent 文件夹 + 统一事件帧：端点只认一条 SSE 流，客户端只认 eventType，种类信息走帧里的字段而不是新的 URL 或新协议。

2. 把安全规则写进提示词，和写进 manifest 的 roles，差别在哪？

提示词是软约束，模型可能被诱导绕过，且不可断言；roles 是路由前的集合过滤——不可见的能力在结构上不可达，可以写成单测断言。

3. 什么时候该放弃「规则路由」改用 LLM 分类？

当意图种类多、措辞变化大、且路由错了不会造成安全问题时；反过来，儿童产品、强合规场景、可预测的低成本路径，规则优先更合适。本仓把 LLM 分类器留成可选插槽，就是为这个判断留口子。
