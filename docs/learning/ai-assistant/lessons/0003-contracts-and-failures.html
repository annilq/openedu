契约与失败边界：出错时系统怎么说话

一个 AI 系统真正的成熟度，不看它顺利时多流畅，而看它出错时说什么、泄露什么、还能不能继续。本课讲 openedu 在卡片、思维链、失败归因、工具 schema、扩展点、历史回放这六条边界上定的规矩。

事实源：agent_core/{protocol,ports,subagent}.py · adapters/genkit.py · query/{render.py,tools/_shared.py} · ADR-0042 / 0043 / 0038 / 0040 / 0035 / 0048 / 0054

本课知识点

  1. 呈现双轨与类型化卡片（不做 GenUI）
  2. 推理与正文分流
  3. 失败归因：能力问题 ≠ 厂商问题
  4. strict schema 与缺席编码
  5. 扩展钩子：LLM 不可见的干预点
  6. 会话历史与只读回放

一、对客户端的契约

12呈现双轨：TOOL_RESULT 存原始，DATA 供渲染

同一份工具结果走两条轨：TOOL_RESULT 存原始载荷（喂给模型的上下文 + 落库回放），DATA 帧携带类型化卡片（data.type 是种类判别键，data.result 只放结构化字段）。前端按 kind 分派渲染器，未登记的 kind 走降级卡。

架构优点

模型上下文与人类展示解耦：为了好看而裁剪数据不会污染模型上下文，为了省 token 而压缩也不会让卡片缺字段。落库整帧存 data（含 kind），payload 自描述，将来做回放能分派回正确渲染器。

当时的设计决策

改动前 render_cards 把结果压成 {type: 标签, subject, stem} 一行展示串，于是「result.type 是标签、data.type 是种类」同名异义，前端只能二选一地误读；出题卡甚至没有 type 字段，题型/选项/解析全部不可见。ADR-0042 把判别键统一成一个，并明确不做通用 GenUI（服务端下发 UI schema）——消费者只有一个 Flutter 客户端 + 一套设计系统，让服务端描述布局等于把设计系统与可达性契约从客户端搬到服务端，而服务端不该知道现在是家长端还是娃娃端。

同类主流实现方式

① 服务端生成 UI（GenUI）：CopilotKit 的 generative UI、Vercel AI SDK 的 RSC streaming、以及 A2UI / MCP-UI 一类「用 JSON 描述组件树」的方案——跨端复用强，代价是服务端承担设计系统一致性。
② 纯文本 + Markdown：最省事，前端一个渲染器通吃；代价是没有结构化交互（点不了、跳不动）。
③ 类型化卡片 + 受控动作：本仓路线；ADR-0054 再加一条 actions: [{label, target}]，target 是枚举不是 URL——导航在客户端，服务端只说「去布置任务」，不说「跳哪个路由」。

代价 / 遗留

两端各持一份 kind / target 常量表，跨语言无法直接断言一致，只能两端各守一半；新增 target 必须同时改后端常量与前端映射，否则按钮变成「点了没反应」。学科颜色由前端从 subject 推，颜色不进线协议。

ADR 锚点：ADR-0042（类型化卡片）· ADR-0054（受控跳转动作 · target 是枚举）

13推理与正文分流：思维链永不当答案

适配器给每个文本增量打上语义通道（TextKind.TEXT / REASONING）。runtime 只把 TEXT 累进最终答案；REASONING 只作思考回显，不进答案、也不进回灌历史。外发前还会过滤掉命中调用协议的片段。

架构优点

把「流向」与「语义」对齐：语义在端口层标注，去向在 runtime 决策，适配器不替 runtime 决定。于是「模型没走原生 function calling、把调用写进思维链」这一整类事故在结构上被消灭。

当时的设计决策

真机：家长问「查一下 lsc 的错题本」，模型不发原生 ToolCall，1255 字符英文独白被当成答案下发到儿童端。根因是协议层不分通道。ADR-0043 的取舍有三条：协议层分离而非继续堆正则（启发式永远追不上措辞）；kind 放端口层而非留在适配器（流向决策在 runtime）；无调用且正文空 → 硬失败而非降级纯文本。判据还拆成强弱两档：强标记（<invoke name= 这类调用外壳）命中即判泄露、不要求点名已注册工具——因为模型最常见的形态恰恰是编造工具名。

同类主流实现方式

① 厂商原生分通道：OpenAI Responses API 的 reasoning summary、Anthropic 的 thinking block，由 API 直接给出独立字段，最干净，前提是用这几家。
② 框架层约定：Vercel AI SDK 的 reasoning part、LangGraph 的 custom stream 通道，思路相同、落点不同。
③ 后置正则过滤：不改协议，只在出口筛掉 <invoke> 一类标记；拦得住「有标记的」，拦不住「答案本身就是独白」。

代价 / 遗留

纯自然语言叙述（「我去查一下」，无协议标记、正文非空）仍会作为普通正文流出——危害已消除，根治要靠模型侧原生 FC。前端目前还没消费 THINKING 与正文的区别，思维链回显未落地。

ADR 锚点：ADR-0043（TextDelta.kind 语义通道分流）

二、出错时怎么说话

14失败归因：能力问题 ≠ 厂商问题

引擎失败被分成两类、各说各的话：模型缺 function calling 能力 → TOOL_UNSUPPORTED；厂商拒绝请求（认证 / 限流 / 网络 / 参数被拒）→ PROVIDER_ERROR。分类默认落在后者。用户看到的是策展文案（「API Key 无效，请在模型管理里重填」），原始厂商报文只进日志。

架构优点

用户拿到的是可执行的下一步，而不是一整段厂商 JSON；归因逻辑只有一个函数（classify_failure），三条分支（schema / tools / 纯文本）与旁路（批改）都复用它，同一个 401 不会在不同路径被说成两种话。

当时的设计决策

事故形态：密钥解不开 → 密文被当成 API Key 发给厂商（401），而旧实现把工具路径上任意异常包成「模型不支持工具调用」，于是用户去换模型，真问题却是密钥。ADR-0038 定了两条硬契约：decrypt() 解不开只返回 None（密文永不出门）；失败分类默认落 PROVIDER_ERROR。同时要求上层不得用 except Exception 把引擎失败抹成「请添加模型」。

同类主流实现方式

① 通用重试库：tenacity / OpenAI SDK 内置重试，解决抖动，但会把认证失败也一起重试、还会抹掉归因。
② 框架重试策略：LangGraph 的 retry policy 按节点配置，粒度好，但默认话术仍是框架给的。
③ 可观测性平台兜底：LangSmith / OpenTelemetry 记录原始错误，用户面仍要自己策展文案——本仓是「策展文案 + 日志原文」的组合。

代价 / 遗留

标记词表是启发式，新厂商可能要补词；未命中一律落 unknown 并带原始原因，绝不误报成能力问题。启动期密钥健康检查尚未做——家长要等提问失败才知道密钥失效。

ADR 锚点：ADR-0038（失败归因与密文契约）· ADR-0033（硬失败不降级）

15strict schema 与缺席编码：模型被迫填值时怎么办

工具参数在 OpenAI strict 模式下会被无条件改写成「所有 property 必填」——源码里写的 "required": [] 在 wire 上根本不存在。于是每个可省略参数都必须有一个类型合法的缺席编码：字符串 ""、整数 0、枚举必须含 NO_FILTER="all"，并在 handler 归一为「未提供」。

架构优点

把「模型被迫为每个参数编值」这个结构性前提显式化：模型有合法方式表达「不过滤」，就不必靠猜；归一收口在 resolve_children 一个函数，7 个工具一次性受益，新增工具忘了改会被行为级测试拦下（用缺席编码填满全部参数必须与「不传」出参一致）。

当时的设计决策

真机：strict 强迫填 status，枚举里却没有「不过滤」，模型填 "" → handler 报错 → 模型反复试探 → 撞上「不要重复调用同一工具」的 SOP → 空转并把调用写进正文，用户看到原始协议。第二例是文本化缺席：模型传字符串 "null" 表示「没有目标娃娃」。所以 UNSET_TOKENS 覆盖了 "" / all / none / null / nil / n/a… 多语言口径，且回灌给模型的错误消息要带可执行出路（「按昵称定位请改用 child_name」），光说「不是 uuid」模型只会换个猜法重试。

同类主流实现方式

① 关掉 strict：genkit 未暴露开关，走不通；OpenAI 原生 API 可以 strict: false，代价是参数结构不再保证。
② 砍掉过滤参数（工具恒定查全部）：彻底消除陷阱，但丢掉「只查数学错题」「最近 5 道」这类能力。
③ 让模型多问一轮（必填 + 缺失时反问）：交互更啰嗦，儿童产品不可接受。
④ 缺席编码 + 收口归一（本仓）：最小改动，代价是 0 的语义被占用（=不设限）、"all" 成为保留词。

代价 / 遗留

依赖外部私有行为（openai.lib._pydantic 的改写），升级 SDK 时要重新评估——所以留了一条证据锚点测试：断言「必填陷阱」依然存在，SDK 变了它会先失败，提醒你重新评估而不是删补丁。

ADR 锚点：ADR-0040（缺席编码与 NO_FILTER）

三、可扩展性与读路径

16扩展钩子：模型看不见的干预点

内核在 tool loop 上固定三个挂载点：before_turn（改写 system/prompt/history）、after_tool（改写工具结果）、rewrite_messages（发送前统一改写，不写回 canonical history）。默认零行为，钩子抛异常被吞掉，不影响主链路。

架构优点

审计、截断超大结果、注入租户级约束这类需求不必改内核或每个 SubAgent；与「SOP 注入 system prompt」这条 LLM 可见通道互补——一条改模型的想法，一条改送出去的数据。

当时的设计决策

架构评审指出「可扩展性全靠 SOP 注入」不够：SOP 是 LLM 可见的提示词，做不了不可见的裁剪与审计。ADR-0035 参照参考架构（pi-coding-agent 的 lifecycle hooks）在内核加 seam，并明确约束：钩子必须幂等、轻量，且改写消息必须保持 role/tool_calls/ref 成对不变量，否则会破坏厂商的 ToolRequest↔ToolResponse 配对。

同类主流实现方式

① 中间件：LangGraph 的 middleware / deepagents 的 SubAgentMiddleware（含上下文隔离、rubric 自评），能力最全。
② 生命周期 hooks：OpenAI Agents SDK 的 RunHooks（on_agent_start / on_tool_end 等），形态与本仓最接近。
③ 协议级中间件：AG-UI 的 middleware「在 enforcement 之前运行」，让兼容层先翻译再剥离。

代价 / 遗留

只有跑 tool loop 的 SubAgent 会触发三个固定点（tutor/question 是单调用，无挂载点）；钩子故障被静默吞掉，排查时要靠日志。

ADR 锚点：ADR-0035（扩展钩子 seam）

17会话历史：页内切模式，孩子的会话只读

读路径新开家长专属端点（列表 + 详情），与调试端点 /ai/debug/conversations 刻意不复用。列表分两段：家长的会话点开是恢复续接，孩子的会话点开是只读回放（带「只读」徽标）。页面内切 chat / history / reading 三态，不新增路由。

架构优点

两个消费者各自得到贴合的形状：用户面拿到可渲染的气泡，审计面保留全部 step 与原始 payload；合并会同时伤害两边。折叠（哪些行算气泡）放服务端，卡片怎么画仍归前端——不违反「服务端不拼展示串」。

当时的设计决策

孩子的会话必须只读，这不是 UX 取舍而是后端语义：家长发请求时 child_id 恒为 None，拿孩子的 session_id 续接必然过不了归属校验，后端会另建一段会话，屏幕上却像续上了——更糟的是校验失败后会启用客户端历史兜底，孩子的消息会被当成家长的 prompt 灌进新会话。另外：不调模型生成标题（首轮多一次调用 + 失败回退不值得）；读出侧必须回落 title（历史数据全为 NULL）；先修 turn 撞号缺陷再做回放（两者共用同一个排序键）。

同类主流实现方式

① 统一 thread API：Agent Protocol 的 /threads + /threads/{id}/history，一个抽象覆盖运行与会话。
② 服务端托管线程：OpenAI Assistants 的 threads（含消息列表），客户端完全不存历史。
③ 本地持久化：多数桌面 / 移动 Chat 应用把会话存本地库，跨设备靠同步；本仓因为要跨家长与娃娃两个角色共享，必须放服务端。

代价 / 遗留

无删除、无保留策略、无 FK 级联；无分页（只有 limit 上限 200）；孩子的会话组排序取「该组第一段在整体倒序中的位置」（零额外查询、确定性），不是按娃娃固有顺序。

ADR 锚点：ADR-0048（会话历史与只读回放）

检索练习（先想再看）

1. 「DATA 帧」和「TOOL_RESULT 帧」为什么要分成两条轨？

消费者不同：一个给模型（要够用的原始上下文），一个给人（要可分派的结构）。合成一条会让「为了好看而裁剪」污染模型上下文，或让「为了省 token 而压缩」导致卡片缺字段。

2. 为什么把 401 说成「模型不支持工具调用」比直接报 401 更糟？

因为它指向错误的修复动作：用户会去换模型，而真问题是密钥失效。失败分类默认落 PROVIDER_ERROR，正是为了让「不确定」时至少不指错方向。

3. strong/weak 两档协议判据，为什么强标记不要求点名已注册工具？

因为模型最常见的形态恰恰是编造工具名（把 list_wrong_questions 写成 get_mistakes）。若要求点名，这一形态必然逃逸，整段原始协议就会被当答案下发。

4. 孩子的会话为什么不能让家长续接，只能只读回放？

家长的 child_id 恒为 None，续接过不了归属校验 → 后端另建会话；更糟的是会启用客户端历史兜底，把孩子的消息当成家长的 prompt 历史灌进去，造成语义污染。
课后一问 挑本课任意一条「硬失败」规则，设想把它改成「静默降级为纯文本」：用户会看到什么？哪一类 bug 会从可观测变成不可观测？讲给 agent 听。
