一次请求的全链路：从一句话到一张卡

家长说「查一下小明的错题本」，这句话要走过 HTTP、编排、路由、模型、工具、落库六站。这一课把这条链路一步一步摊开，并说明每一步为什么这么切。

一、编排与路由

7编排下沉到 service，router 只做 HTTP 适配

router.py 只做三件事：空消息校验、鉴权、把 service 返回的异步迭代器包进 StreamingResponse（外加 X-Accel-Buffering: no 禁代理缓冲）。角色解析、依赖构造、会话 upsert、事件流折叠持久化全在 assistant_service.chat。

架构优点

编排可被单测直接调用（注入桩 runtime，不需要 HTTP 链路）；HTTP 关注点集中在一处，安全审计只看一个文件；协议升级与编排升级互不干扰。

当时的设计决策

ADR-0033 明确否决了「编排留在 router/FastAPI」：那个文件曾膨胀到 700+ 行，ORM 对象与领域类型泄漏到 HTTP 层，且无法在不开服务的情况下测。同一个 ADR 还定了一条跨层规则：REST 路由与 AI 查询工具共用同一套领域规则（决策 13）——「今日任务」在页面上和 AI 回答里必须是同一份口径、同一套错误文案，否则两个入口会各自漂移。

同类主流实现方式

① 框架即编排：LangGraph 里图本身就是编排，节点里写业务，天然可复用、可持久化；代价是业务与框架概念绑死。
② 控制器里写编排（多数 MVC 项目的现状）：最快，但难测、易膨胀。
③ 编排下沉 + 薄控制器：本仓与多数企业级后端的做法，service 是唯一可测的编排单元。

代价 / 遗留

service 承担了「编排 + 持久化 + 副作用（TutorLog）」三件事，文件本身会变大；落库失败不能破坏已流的响应，所以副作用要 try/except 包住并留痕。

ADR 锚点：ADR-0024（router 只做 HTTP 适配）· ADR-0033 决策 13（REST 与工具共用领域规则）

8预路由：一次决策，两处复用

开流之前先跑一次 rt.decide()——纯计算、不流式、不构建 provider，返回结构化的 RouteDecision(business, name)。这个决策随后被用了两次：写进会话的 kind 字段，和传给 run() 复用（避免重复路由）。

架构优点

消除「端点靠解析 THINKING 帧的 extra 才能知道路由结果」这种隐式契约；决策可在流式前做预航班（配额判定、灰度拦截）；落库的 kind 有了确定的来源，不再依赖帧序列。

当时的设计决策

早期实现是「先流后知」：runtime 在 THINKING 帧里塞 extra={"routing": True}，端点从帧里反读业务类型。ADR-0024 后期把它改成显式返回值——隐式契约的代价是顺序耦合（帧顺序一变就读不到），而结构化决策可以直接断言。

同类主流实现方式

① 边流边决定：多数流式实现把「路由中」也做成一帧，前端显示「正在选择助手」，简单但把判别逻辑塞进了展示通道。
② 两阶段 API：先 /classify 再 /run，清晰但多一次往返。
③ 框架内部路由：LangGraph 的条件边在流内分流，等价于边流边决定，只是它由图结构描述。

代价 / 遗留

多了一个需要两端/两层对齐的结构（RouteDecision）；若将来要在流中改判（先 query 后发现该 question），预路由的模型要重新设计。

ADR 锚点：ADR-0024（预路由消除隐式契约）

二、上下文与协议

9会话与上下文：谁在记你聊过什么

多轮上下文由服务端持有：Conversation + Message 两张表，客户端只拿一个 session_id。续接时按归属校验后载入历史；历史超预算时不是硬截断，而是把最旧的轮次压成一句摘要注入（compaction）。每条消息有 turn 序号，是回放与 prompt 共用的排序键。

架构优点

换设备 / 重启 App 都能续上；历史可被审计与回放；上下文拼装在服务端，客户端无法伪造历史（也就无法用「假历史」诱导模型）。

当时的设计决策

① 不调模型生成会话标题：标题取首条用户消息截断 20 字，写入点唯一、值稳定——省掉首轮一次模型调用与失败回退（ADR-0048）。
② turn 必须接着已有序号：曾出现两个计数器不同源（生成器的 turn=1 与 next_turn()），第二轮起回答排到提问之前，模型拿到倒置上下文。这类缺陷只能靠端到端守卫测出来（单轮不撞号、repository 单测绕开排序）。
③ 压缩用摘要而非丢弃：长对话连续性的必需项，失败则回退纯丢弃，不阻断主链路。

同类主流实现方式

① 客户端持有历史：每轮把整个 messages 数组回传（Vercel AI SDK、多数 Chat 应用的做法），服务端无状态、易扩展；代价是包体大、可被伪造、跨设备不共享。
② 服务端线程 / 检查点：OpenAI Assistants 的 threads、LangGraph 的 checkpointer + thread_id，与本仓同一思路，框架化程度更高。
③ 上下文工程中间件：LangChain 的 SummarizationNode、mem0 一类专门做压缩与长期记忆，可作为本仓 compaction 的升级方向。

代价 / 遗留

已写入的历史数据不回填（撞号已发生，排序无唯一解）；会话只增不删、无 FK 级联、无保留策略（ADR-0048 记为已知缺口）。

ADR 锚点：ADR-0022（Conversation/Message 模型）· ADR-0048（会话历史与只读回放）

10统一事件帧：一条流解释所有事

整条流由 AssistantEvent 帧组成，前端按 eventType 分发：RUN_STARTED / USER_MESSAGE / THINKING / ASSISTANT_MESSAGE / TOOL_CALL / TOOL_RESULT / STEP / DATA / ERROR / DONE。业务语义走 extra 扩展，内核不认识任何业务字段。客户端侧有一个纯函数折叠器（AiTextFold）：喂一帧返回新的「文本 + 卡片 + 阶段 + 错误」不可变值。

架构优点

新增语义加 extra 不加帧类型，协议不膨胀；折叠逻辑是纯函数，可以脱离 Riverpod 直接断言；「思考中」占位气泡能显示真实阶段（正在查询…）而不是静态转圈。

当时的设计决策

折叠逻辑原先写在 notifier 的 await for 循环里，夹在状态管理与 SSE 之间无法测试；ADR-0036 之后只剩一个消费方，于是把它抽成不可变值 + apply，测试直接喂事件列表。前端还定了「未登记的 kind 走降级卡」——宁可降级也不丢内容（v1 曾因 stem 为空直接 SizedBox.shrink()，新卡片整张消失）。

同类主流实现方式

① AG-UI（CopilotKit 主导）：把 agent→UI 的交互标准化为一条事件流，理念与本仓一致，规范目前仍是 draft。
② Vercel AI SDK 的流式协议：以 0:"text"、2:data 这类前置数字编码帧，紧凑且与 React 生态深度绑定。
③ 框架原生事件：LangGraph 的 stream_mode="messages|updates|custom"，能力丰富但与框架耦合。
④ 自建 JSON Lines / SSE：最常见的务实选择，本仓即此路 + 对齐 AG-UI 的命名习惯。

代价 / 遗留

前后端各持一份事件常量与卡片 kind 常量，跨语言无法直接断言一致，只能「两端各守自己那一半」+ 契约测试。前端目前只渲染 ASSISTANT_MESSAGE、忽略 THINKING，思维链回显尚未落地。

ADR 锚点：ADR-0025（事件帧契约）· ADR-0036（前端单一入口与折叠）· ADR-0042（类型化卡片）

11tool loop：模型选型，内核执行

声明了工具的 SubAgent 才跑 tool loop：把工具 schema 随请求发给模型 → 模型回 ToolCall → 内核执行 handler → 结果回灌成对（assistant(tool_calls) + tool(ref)）→ 再请求，直到模型不再要工具。同轮多个工具全部执行后再回灌。

架构优点

工具执行权不在模型侧、也不在框架侧，而在内核——于是权限校验、角色裁剪、结果裁剪都能在唯一一处做；回灌格式是中性契约，换厂商只改适配器的映射。

当时的设计决策

① opt-in：只有声明 tools 的 SubAgent 才跑 loop（tutor/question 是单调用），避免所有能力都被套上多轮开销。
② 轮次上限默认 3：查询场景通常 1–2 跳，上限是防「回灌丢失 → 模型反复重调」的烧钱死循环。
③ 回灌成对：assistant(tool_calls) 与 tool(ref) 必须成对，否则 OpenAI 兼容端点直接拒绝；缺 ref 时适配器用 FIFO 队列补配。

同类主流实现方式

① 预编译图：LangGraph 的 ToolNode + 条件边，循环是图结构，可可视化、可持久化、可 human-in-the-loop。
② 框架内置循环：OpenAI Agents SDK 的 Runner loop（带 handoffs）、Pydantic AI 的 run loop，写起来最省事，边界由框架定。
③ ReAct 范式：ReAct 论文提出的 Thought-Action-Observation 循环，是上述所有 loop 的思想源头。
④ 工具外置：MCP 把工具放到独立进程，与本仓「工具即进程内函数」相反——跨应用复用强，代价是多一层协议与部署。

代价 / 遗留

轮次上限是启发式：需要更多跳的能力要自己覆写 max_turns；回灌格式与厂商协议强相关（成对不变量），写错会在厂商侧报 400，本地难复现。

ADR 锚点：ADR-0033（轮次上限 / 硬失败 / 回灌契约 / 同轮多工具）

检索练习（先想再看）

1. 为什么路由要在「开流之前」算完，而不是边流边算？

流内算等于把判别逻辑塞进展示通道，端点要反读某一帧的字段才能知道结果，形成顺序耦合；预路由返回结构化决策，可被断言、可被落库复用、还能在流式前做配额预航班。

2. 多轮上下文放服务端，最大的收益是什么？最大的代价是什么？

收益：跨设备续接、可审计回放、客户端无法伪造历史。代价：服务端要有会话表与归属校验，且排序键（turn）一旦写错就是全局性的数据缺陷——还无法靠回填修复。

3. tool loop 里「既没工具也没正文」为什么必须硬失败，而不是让模型再说一句？

因为那意味着模型把调用意图留在了思维链里、没走原生 function calling；此时「再说一句」只会把内部独白（含调用草稿）当成答案下发，既不是用户要的结果，也泄露内部协议。
课后一问 「轮次上限 = 3」是个魔法数字。如果你的查询场景稳定需要 4 跳，你会改上限、拆工具、还是改 SOP？说出你的取舍。
