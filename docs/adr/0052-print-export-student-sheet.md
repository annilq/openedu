# 打印导出：服务端排版学生卷

家长端已有题库与任务两个模块，但缺一个把题变成纸的出口：家长要在平板上勾选题目或任务，
拿到一份能直接打印、给儿童账户手写的卷子。仓库此前**零** PDF / 打印能力——后端无 PDF 依赖、
无 `StaticFiles` / `FileResponse` 挂载、无导出端点先例；前端 `pubspec.yaml` 无 `pdf` / `printing`。
本 ADR 决定这条链路怎么建。

## 决策

- **生成端在服务端，客户端只预览与投递。**
  后端新增 `app/features/export/{__init__,repository,service,router,schemas}.py`，
  `POST /api/v1/export/sheet` 接收 `{source, ids, options}`，返回 `application/pdf` 字节；
  客户端 `features/export/` 拿到字节后用 `pdfx` 预览、用 `printing` 打印或分享。
  **预览 = 渲染将要投递的那份字节**，所以「预览与导出不一致」在构造上不可能发生。
  排版用 **Typst**（`typst-py` 0.15，Apache-2.0，Rust 编译的 wheel，无系统库）跑 `.typ` 模板，
  题目数据经 `sys_inputs` 以 JSON 传入。

- **内容只有题干与选项，绝不出现答案与解析。**
  卷子是给儿童账户写的；批改由家长用外部批改 App 扫码完成，不靠纸上答案。
  解析本轮完全不导出（它是讲题用的，不是批改用的，且文字长、排版成本高）。
  `answer` / `explanation` 字段**不进导出文档**，这是硬约束，由守卫断言。

- **纸面规格固定一套。**
  A4 纵向；页边距左右 20mm、上 18mm、下 16mm；页眉左为文档标题（任务名，或「{学科} · {知识点}练习」）、
  右为 `姓名 ________  日期 ________`（**手填，不预填儿童账户名**——同一份卷子可能给多个孩子用）；
  题干 12pt / 选项 11pt / 页眉 9pt，行高 1.5；题号 `1.` `2.` **跨节连续编号**，不按节重置。

- **作答留白按题型给，不按 qtype 名字猜。**
  `choice` 每题后 6mm（选项本身即作答区）；`fill` 题干内一条 40mm 横线；
  `calc` 35mm、`open` 50mm 空白答题区。判据沿用既有约定：**`options` 非空即走选项，否则走留白**。

- **一次导出单一来源，永远产出一份 PDF。**
  不允许题库与任务混选（分节语义会打架）。
  任务来源：每个任务一节，节标题为任务名（**不印状态**——纸上的卷子不需要知道 draft/assigned）。
  题库来源：按**学科**分节，节标题带学科几何标记 ■ ● ▲；只勾了一个学科时不分节，只给一个标题。
  **节内顺序 = 列表当前展示顺序，不做重排**——所见即所得，排序是列表页自己的事。

- **纸面视觉走「轻装饰」，不铺色块。**
  保留墨黑描边与学科几何标记，不铺任何彩色填充。理由：家长很可能用黑白激光打印机或打印店单色机器，
  色块在该场景会变成一团脏灰；而几何标记本就是学科三重编码里为色觉障碍准备的第二层，在黑白纸上天然成立。
  这也符合 ADR-0044「层级由描边与位移承担，不依赖色块面积」。

- **四个入口，导出器不反向依赖任何 feature。**
  题库页复用现有多选底栏（`parent_question_bank_view.dart` 已有 `Set<String> _selectedIds`）加一个导出按钮；
  任务页需新做选择态（`parent_tasks_view.dart` 目前只有 Tab）；
  错题本页导出**全部未毕业错题**，提供「只看今天到期」勾选项；
  复习页导出**当前到期复习项**（屏幕上是什么就导出什么）。
  按 ADR-0037（`shared/` 不得 import `features/`、feature 之间不得横向互引），
  `features/export/` **只放数据契约、请求与预览**，由四个页面各自把已选数据转成契约再交给它。

- **题干按富文本（标准 Markdown）承载，本轮纸面降级为纯文本。**
  后续图片 `![]()` 与公式 `$...$` 都进这一层。本轮服务端不渲染它们：
  导出时剥离 Markdown 标记与 `$...$` 定界符，保留内部文本（如 `1/2`），
  并在预览页明确提示「N 道题含公式或图片，已按纯文本打印」——比印出一堆 `\frac{1}{2}` 原始字符体面。

- **单次导出上限：客户端软提示 60 / 服务端硬上限 200。** 家长要印 100 题的复习卷是合理需求，
  超过 60 题时客户端提示建议分批但仍可继续；服务端 `EXPORT_MAX_QUESTIONS=200`（见 `app/core/config.py`）
  作为防超时 / 防内存的硬边界，超过返回 `400` 并带可展示的中文消息。

- **中文字体由配置指定，启动冒烟校验。**
  Typst 需要一份中文字体，经 `Compiler(font_paths=[...])` 传入（已验证 0.15 支持该参数）。
  路径由配置 `EXPORT_FONT_DIR` 给出，**不在代码里硬编码**。
  沿用 ADR-0041 的启动冒烟模式：启动时校验字体可用，缺失则告警，
  且导出端点返回明确错误——**绝不静默渲染出豆腐块**。
  字体由 Typst 自动子集化输出，不需要手工处理 `NotoSansSC.ttf` 的 17.7 MB。

- **编译是 CPU 密集，走线程池；归属校验走 `core.guard`。**
  60 题量级同步返回即可，但必须在线程池执行，不占事件循环。
  服务端按 id 取数意味着归属判定天然落在服务端——**必须经 `core.guard`**，
  不允许手写 `parent_id ==` 判定（AGENTS.md 跨层硬规则）。

## Considered Options

1. **客户端生成（`pdf` + `printing`）**：离线可用、后端零改动。但 Dart 手写排版维护成本高；
   `NotoSansSC.ttf` 17.7 MB 需自行子集化，有技术风险；而 `pdf` 包**既不支持 Markdown 也不支持公式**，
   题干定为富文本后要自己写一个 Markdown → `pw.Widget` 转换层——这个成本在首次评估时被低估了。拒绝。
2. **先客户端出纯文本版，公式二期再迁服务端**：看似稳妥，实则排版层整层重做，不是增量。拒绝。
3. **服务端生成但只让 Typst 出公式 SVG，主体仍在客户端**：屏幕与纸面两套渲染器，
   且把纸面绑到额外依赖上。拒绝。
4. **服务端用 WeasyPrint / ReportLab / fpdf2**：WeasyPrint 需 pango/cairo 系统库，
   ReportLab / fpdf2 无公式且要手工注册中文字体、手写排版。均不如 Typst。拒绝。
5. **服务端生成整份 PDF（Typst），客户端只预览与投递**（采用）：
   公式原生（`$...$` 与 Typst 数学语法同源）、中文一份字体即自动子集化、
   排版用 `.typ` 模板比 Dart widget 树易维护，且二期接公式时架构不动。

## 实现期补充决策（落地时登记）

- **复习页入口由娃娃 token 驱动，作用域服务端钉死。**
  复习页（`ReviewScreen`）在娃娃端、走 `CurrentChild` 鉴权，而导出端点原本只收家长。
  实现取「同一端点、双主体」：`source=wrong_book` 时娃娃 token 也可调用，
  但来源与 `child_id` 都由服务端按调用者钉死（请求体里传别人的 `child_id` → `400 EXPORT_80006`），
  `ids` 一并清空——授权主体是他自己、资源也必须是他自己的，不引入「孩子可查家长题库」的新面。
  前端按 ADR-0037 由 home 组合根注入回调（`ReviewScreen.onExportDue`），`features/review` 不 import `features/export`。

- **纯文本降级不剥「填空下划线」。**
  降级剥 Markdown 标记时，`____` 一律剥掉会把填空题的作答空位从纸上抹掉
  （孩子看着 "I  a student." 却没有地方下笔）。判据沿用 Markdown 本身的规则：
  强调必须**紧贴文字**——被空格孤立的下划线串是留白，保留；紧贴文字的成对下划线才是强调，
  且只剥定界符、保留被包裹的内容（`__8__` → `8`）。守卫在 `test_document.py`。

- **字体用变量字体实例化出的静态 Regular。**
  仓库里唯一的 `NotoSansSC.ttf` 是可变字体且默认实例是 Thin，Typst 不会按目标字重实例化，
  直接用会排出细笔画。`backend/scripts/build_export_font.py` 用 fontTools 把 `wght=400`
  实例化成静态 Regular 放进 `backend/assets/fonts/`（Dockerfile 一并 COPY），启动冒烟校验。

- **预览必须自己 await 打开文档的动作。**
  预览用的渲染引擎走原生插件，`PdfDocument.openData` 会失败——App 进程早于依赖安装
  （装完插件只 Hot Restart，原生那一侧没有 PdfxPlugin）、当前平台无实现、字节不是 PDF
  都是现实例子，表现为 `PlatformException(channel-error)`。把未完成的 Future 直接交给
  `PdfControllerPinch` 时，这个异常没有归属，落点是控制台一条 Unhandled Exception、
  页面停在加载态（既无错误态也无重试入口）。因此页面自己 await 并区分两个阶段
  （导出失败 / 预览失败），按钮可用性绑在「预览已就绪」而不是「字节已到手」——
  渲染都失败的文档不该承诺可打印。
  为使这条路径可测：打开动作收口到 `pdfDocumentOpenerProvider`（可直接替换成「抛指定错误」）。
  对着真实平台通道写替身不行——没有原生一侧时那个 Future 既不完成也不报错，测试只会挂住。

- **接住异常不等于问题消失了：控制台要留痕，文案要给「下一步做什么」。**
  加了 try/catch 之后线上表现为「预览失败，控制台却一句话没有」——异常被页面吃掉了，
  排障的人反而失去唯一线索。因此两阶段失败各留一条 `[export] <阶段> 失败: <error>`。
  同理，错误态那句文案不能是 `预览失败：PlatformException(channel-error, ...)`：
  用户看到错误类型做不了任何事。`channel-error` 的语义是**原生侧没有这个插件**
  （App 二进制比依赖装得早，装完只做了 Hot Restart），此时重试无意义，
  文案直接落到「完全退出 App 后重新打开 / 重新构建」上；其余原因才走通用文案。
- **新增原生依赖后的排障判据（本机 macOS）。**
  判「插件到底有没有进 App」不要靠猜：① `ps` 看运行进程的**启动时间**；
  ② 比 `build/macos/Build/Products/Debug/<app>.app` 与 `pubspec.lock` 的时间戳；
  ③ 真正落在包里的是 `Contents/MacOS/<app>.debug.dylib`（那个 59KB 的 `MacOS/<app>`
  只是壳），用 `strings ... | grep -i pdfx` 能看到插件的 pigeon 选择器即证明已链接。

## 与 ADR-0042 的关系

ADR-0042 立过「服务端不拼展示串、排版归前端」的原则。服务端排版 PDF 表面上与它冲突，
此处登记为**正当例外**并说明理由：ADR-0042 针对的是**助手卡片通道**，禁止的是
「服务端下发 UI schema 做通用 GenUI」；而 PDF 是**最终产物**而非 UI schema——
`.typ` 模板不下发给客户端，客户端也不解释它，只接收一个二进制。
本 ADR 不修改 ADR-0042 的适用范围，助手卡片通道仍严格遵循原规则。

## 守卫

后端 `backend/tests/`：

- 归属校验：用另一家长的 `question_id` / `task_id` 请求导出，不返回该题内容。
- 内容净化：导出的 PDF 文本层里**检索不到** `answer` 与 `explanation` 的字符串。
- 分节结构：任务来源按任务分组、题库来源按学科分组；单学科时不产生分节标题。
- 题号跨节连续，不按节重置。
- 上限：服务端硬上限 200 题（`EXPORT_MAX_QUESTIONS`，见 `app/core/config.py`）；客户端在 60 题时软提示建议分批。

前端 `frontend/test/`：

- 边界守卫：`features/export/` 不 import 其他 feature，`shared/` 不 import `features/export/`。
- 契约转换：四个入口各自能把已选数据转成 `ExportDocument`，且不含答案字段。
- 预览页几何：`Navigator.push` 的整页自带宽度约束（ADR-0045），不出现内容浮在屏幕中间。

## 后果

- 后端新增 `typst` 依赖（Linux wheel ~33 MB）与一份中文字体；部署体积上升，但无系统库。
- 导出强依赖后端可达——离线时导出入口应禁用并说明原因，这是相对客户端方案的明确退让。
- 预览与打印/分享走系统对话框，App 内不落盘、不做导出历史，无文件清理负担。
- 已知代价：屏幕题干（Flutter 富文本）与纸面（Typst）是两套排版系统，
  同一条公式在两端字体可能略有差异。这是可接受的两套版式系统差异，不是一致性缺陷——
  二者本就承担不同职责（一个可交互、一个要留白）。

## 后续（独立 ADR，不在本轮）

**题干富文本渲染（公式与配图）**：`QuestionSchema` / `QuestionOut` / `GeneratedQuestion` / ORM 加字段，
`parsers.py` 透传，prompt 追加「公式用 `$...$`」约定，屏幕侧由 `Text` 换成富文本渲染器
（`flutter_math_fork` 已作为 `gpt_markdown` 的传递依赖在仓库里）。
服务端用同一份 `$...$` 经 Typst 原生渲染，**两端共用一份源、纸面仍是矢量**。
图片管道（上传 / 存储 / 鉴权）不在该 ADR 范围内，需单独决策存储形态。
