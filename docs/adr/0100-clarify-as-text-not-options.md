# ADR-0100 缺槽追问只做文本引导，不做选项表单

- 状态：已采纳
- 日期：2026-10-19
- 关联：ADR-0095（工具输入 schema 与缺槽追问）、ADR-0098（二执行体收敛，出题 schema 落在 `intent_schemas.generate`）、ADR-0099（已确认规格跨轮回灌）

## 1. 背景

ADR-0095 定的澄清帧形状是「普通助手消息 + `extra.clarify.missing_slots`」，前端据
`missing_slots` 渲染**可点选的引导卡**：枚举槽铺一排 chips（科目 / 题型），带范围的
int 槽铺一排数字（年级 1-9）。

实机反馈（教师端出题）：

> 「除了渲染的 text 模板外，给每一个科目和年级以及题型都出了选项……这样用户需要选几次
> 才能补充完信息。如果以文本的形式引导，用户一次就可以输入完。」

问题成立，且根因不在渲染细节而在**交互模型与抽取能力不匹配**：

- 预检层（`slot_filling.fill_slots`）是**规则抽取**，按 `spec_keywords` 的正则/词表
  一次性吃下整句话——「三年级数学选择题 5 道」一轮就能填满 `subject` / `grade` /
  `qtype` / `count` 四个槽。
- 而 chip 的**回传粒度是单槽**：点「数学」只发「数学」，点「3」只发「3年级」。补三个
  必填槽 = 三次往返 + 三次服务端预检 + 三段会话历史。
- 于是 UI 把「一句话能说完的事」拆成了三次，比让用户自己打字**更慢**，也与用户真实
  输入习惯（一句话报清规格）相反。chips 解决的是「不知道能填什么」，而这里的真实
  痛点是「不想分三次填」。

## 2. 决策

**缺槽追问只做文本引导；不再渲染选项 chip。**

1. **正文由后端生成一句引导**（新模块 `backend/app/features/assistant/slot_clarify.py`）：
   `clarify_sentence(missing)` → 「还差科目、年级、题型这几项，可以一次说完。例如：
   三年级数学、选择题、5 道」。话术必须同时回答两件事：
   - **还差什么**（槽的中文标签，单槽时收短为「还差题型，补一句就行」）；
   - **怎么一次说清**（一个可照抄的示例句）。
   话术放独立模块而非 `slot_filling.py`：引擎只答「缺不缺」，文案是展示层决策
   （与 `slot_summary.py` 分家的同一条理由）。
2. **前端只留一个「一句补齐」入口**（`AssistantClarifyCard` 重写）：把示例句做成可点
   的一行，点它就把整句作为用户消息发出。不想打字的用户仍有 1 次点击的捷径，想打字的
   用户直接回一句——两条路都只需**一次**往返。
3. **`extra.clarify.missing_slots` 协议不变**：结构化载荷照旧下发（历史回放、汇总卡、
   读屏都依赖它）。本次只改**渲染**，不改协议——`AiTextFold` / `Conversation` /
   `repository` 一行未动。
4. **示例句覆盖不到的缺槽 → 不渲染按钮**：示例只覆盖出题必填槽
   （`subject` / `grade` / `qtype` / `count`）。若将来某业务有了这些之外的必填槽，
   卡片退化为「只有正文引导」——宁可不给按钮，也不给一个点了会补错值的按钮。

## 3. 后果

- 补槽往返从「每条必填一次」降到 **1 次**：用户回一句、或点一下示例句。
- 澄清气泡不再出现一排排 chips，视觉上回归一条助手消息的本分。
- 代价：**枚举槽失去了「看见有哪些值」的提示**。缓解方式是把可选项写进话术的示例句
  （题型示例「选择题」），以及 `prompt` 里保留括号说明（`schema` 未改）。真正需要
  完整枚举的场景（题库筛选、设置页）不在助手气泡里，不受影响。
- 代价：`AssistantSlotInput` 的枚举/int chip 分支现在只剩**汇总卡「修改」**一个调用点
  （`AssistantSummaryCard`）。汇总卡的「修改」是**单槽定点修改**（改一个已确认值），
  单槽粒度天然正确，故保留不动——两个调用点的语义差异在此显式记录，不要顺手「统一」。

## 4. 备选（否决）

- **chips 改成多选后一次提交**（勾科 + 勾年级 + 勾题型 → 一次性发）：仍要求用户在三组
  里各点一次，且引入「什么时候算选完」的新状态；对一句话需求来说更重。
- **只保留 chip、把正文去掉**：那正是本次要修的状态——用户被迫点三次。
- **让前端把 `missing_slots` 渲染成表单**（输入框 + 提交）：等于在聊天里塞进一个表单，
  与「对话式补信息」的产品形态冲突，且表单校验要与后端 schema 再同步一份。
- **去掉 `missing_slots`，只发文本**：会让历史回放与汇总卡的「修改」失去结构化依据，
  并使前端无法判断「本轮是不是澄清」。协议保持不动是更便宜的选择。
