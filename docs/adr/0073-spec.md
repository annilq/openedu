# ADR-0073 实施 Spec：场景库统一为单一「场景」概念 + 后端注册表（仅作者辅助）+ `scenes[].kind` 标识 + `scenes` 为唯一事实源

> 本文件由 `@skill:to-spec` 合成，作为 ADR-0073 草案的实施规格。待 `gh` 登录后可用 `gh issue create --label ready-for-agent` 发布。
> 仓库：`github.com/annilq/openedu`；标签：`ready-for-agent`。

## Problem Statement
当前「交互讲解场景」存在命名与解析的分裂：「模板」（`KnowledgePoint.scenes`）与「场景」（`Question.scene_spec` / `Courseware.sections`）本就是同一份 `SceneSpec` 字典，却因存放点和解析逻辑不同而被视为两类事物。同时，「默认 reflection」的默认参数（轴 90°、位置 0.5）散落在后端兜底 `default_scene_from_figure`、前端 `ReflectionSceneData` 的 0.5×4 镜像、以及编辑器 `_buildSpec` 手工重建结构三处，形成维护负担。图形几何（`scene_figures.py` ↔ `figures.dart`）更是真实的双份手写副本，靠 parity 测试钉死但已埋下「house 兜底」行为分歧。教师无法以低成本让多个轴对称知识点共享一份经维护的默认场景定义。此外，早期草案曾设想「知识点加 `scene_name` 列关联注册表、生成时取值」——但代码实证发现：① `kind` 标识今天已活在 `scenes[].kind`，无需独立列；② 全工程仅 `reflection` 一个可渲染 kind，教师无法自定义新类型（kind 由开发者定），「注册表覆盖不到的逃生口」从未真实存在。故收敛为更干净模型：`scenes` 是唯一事实源，注册表仅作者辅助。

## Solution
收敛为单一「场景（Scene）」概念：命名场景存于后端注册表（作者辅助库，以稳定 `kind` 标识），实例场景为落库快照。`kind` 标识直接来自 `KnowledgePoint.scenes[].kind`，**不新增任何列**。`scenes` 永远是完整、自包含、已解析的 SceneSpec 数组——渲染、题目生成、课件生成只读 `scenes`，永不回查注册表（彻底消除 live 绑定诱惑，快照铁律天然保住）。注册表经 HTTP 下发、前端拉取缓存（随包内置），仅用于编辑器下拉预填 + 浏览页枚举内置场景。未配置时仍弹开发者指引、不渲染表单。后续子阶段把图形几何也收拢为后端单一源，消除 parity 负担。

## User Stories
1. As a 教师, I want to associate a knowledge point with the built-in `reflection` scene by selecting a `kind` from the registry dropdown, so that all reflection knowledge points share one maintained definition (via the editor prefilling a complete scene from `BUILTIN_SCENES['reflection']`).
2. As a 教师, I want to override default parameters (axis angle, axis position) per knowledge point, so that I can tailor without editing the shared template — overrides are merged into the saved complete `scenes`.
3. As a 教师, I want the editor form to be generated dynamically from the scene definition's `inputs` schema, so that I don't hand-maintain a separate form per scene.
4. As a 教师, I want a live preview of the scene while tuning override values, so that I can verify before saving.
5. As a 教师, I want a dropdown of backend-known `kind` values in the editor, so that I only pick valid built-in kinds.
6. As a 教师, I want the editor to show a developer hint when no scene is configured (`scenes` empty), so that I know configuration is required.
7. As a 教师, I want generated questions/courseware to carry the exact scene as it was saved on the knowledge point, so that output matches instruction.
8. As a 教师, when the built-in registry definition is changed, I want already-issued questions/courseware to remain unchanged, so that historically distributed papers are never silently rewritten (guaranteed: instances copy `scenes`, never reference the registry).
9. As a 学生, I want interactive reflection scenes to render fully offline on my tablet, so that a weak-network classroom doesn't break learning.
10. As a 学生, I want the scene in my generated question to look exactly as it was saved on the knowledge point, so that practice matches instruction.
11. As a 开发者, I want the scene registry to be backend code (no DB table), so that definition changes ship with releases and avoid migration/FK burden.
12. As a 开发者, I want the `kind` string to be a stable contract (only deprecate, never rename), so that existing data and frontend dispatch are never broken.
13. As a 开发者, I want a single `resolve_kp_scene` entry point (a thin reader of `kp.scenes`) replacing scattered `kp.scenes` reads, so that question and courseware generation stay consistent (fixes the "different place, no figure" root cause).
14. As a 开发者, I want the default reflection definition unified into one place (the registry), so that I stop maintaining 0.5×4 duplicates across backend fallback, frontend data, and editor.
15. As a 开发者, I want the scene library exposed via an HTTP endpoint, so that the frontend can fetch and cache it for offline use (editor enumeration + browse-page listing).
16. As a 开发者, I want a new `kind` to still require a frontend renderer widget release, so that the API can never unilaterally render an unknown scene.
17. As a 开发者, I want the question instance to store the fully resolved scene copy (a deep copy of `kp.scenes`, not just a `kind` reference), so that snapshot immutability holds.
18. As a 开发者, I want unknown/legacy kinds to degrade gracefully (developer hint / unknown renderer), so that older frontends never crash on newer scenes.
19. As a 开发者, I want figure geometry to become a single backend source delivered over the API, so that I eliminate the `scene_figures.py` ↔ `figures.dart` parity burden and the house-fallback divergence.
20. As a 开发者, I want the registry (and figures) to be bundle-cached on the tablet, so that the teacher editor works without a live backend in an offline classroom.
21. As a 教师, I want a scene library page listing each built-in scene with its `kind`, the knowledge points that reference it (via `scenes[].kind`), and a built-in instance count, so that I can see which scenes are in use without hunting through every knowledge point.
22. As a 教师, I want to click a scene in the library and see all its built-in instances (the referencing knowledge points, each with its `scenes` override + a rendered `kind` preview), so that I can audit a scene's usage at a glance.
23. As a 教师, I want generated question/courseware snapshots to render only inside their own scene view (not listed in the library), so that the library stays a clean registry/association view rather than a snapshot dump.

## Implementation Decisions
- **Single concept:** Only 「场景（Scene）」; two forms — named scene (registry, authoring-aid library, identified by stable `kind`) and instance scene (snapshot, deep-copied from `scenes` at generation). Red line: instances store the fully resolved copy, never a live `kind`/`registry` reference (preserves ADR-0061 §U snapshot immutability).
- **`scenes` is the single source of truth:** `KnowledgePoint.scenes` always holds a complete, self-contained, resolved SceneSpec array (with `kind`/`title`/`inputs[]`/`controls`/`narrative`/`outputs`). Rendering, question generation, and courseware generation **read `scenes` only; they never query the registry.** This eliminates the live-binding temptation entirely.
- **No new column:** `kind` is identified directly by `scenes[].kind`; there is **no `scene_name` column** (early-draft proposal removed). No `kind` string is persisted into the resolved snapshot for lookup — `kind` is merely a classification/dispatch tag.
- **Backend registry:** a code module (not a DB table) keyed by `kind`; `reflection` is the first seed. The registry is an **authoring-aid library only** — it powers the editor dropdown prefill and the browse-page listing, never rendering or generation.
- **HTTP endpoint `GET /materials/scene-library`** returns all named scenes (kind + default `list` + `structure` + `associated_knowledge_points` + `instance_count`); frontend fetches and caches (bundle-cached for offline). `associated_knowledge_points`/`instance_count` are **computed server-side by scanning `KnowledgePoint.scenes` for matching `kind`** (no separate FK column). Endpoint value = centralized defaults + editor enumeration + browse aggregation only; it does NOT remove the frontend renderer-registry gate.
- **Thin resolver `resolve_kp_scene(kp)`:** returns `kp.scenes` (validated as a complete SceneSpec array). It does **NOT** merge a registry base with overrides — `scenes` is already the complete truth, with overrides merged in by the editor at save time. Question generation = `deepcopy(kp.scenes[0])` into `Question.scene_spec`.
- **Frontend dispatch:** `SceneInterpreter` routes by `scenes[i].kind` to the matching `XxxSceneWidget`; `unknown` retained as the "developer hint" gate. New `kind` = new `XxxSceneWidget` + frontend release.
- **Editor:** dropdown selects a built-in `kind` → editor prefills a **complete** scene from `BUILTIN_SCENES[kind]` (defaults + structure) → teacher tunes override params → **saves the complete resolved `scenes`** (with `kind`). "未配置弹开发者指引，不渲染表单" preserved (trigger = `scenes` empty). Teacher UI only offers registry kinds — cannot author a non-builtin `kind` (matches today's behavior and the "kind is developer-defined" constraint).
- **Backend fallback refactor:** `default_scene_from_figure` becomes a consumer of the registry (`instantiate_builtin("reflection", overrides={figure from stem})`), producing a **complete resolved SceneSpec**, not a reference. `house` fallback remains frontend-only (registry entry never pre-fills `figure`).
- **AI 答疑后端发射场景卡（已知缺口，待补）：** 出题链路今天已端到端跑通（抽取参数 → 融合落 `Question.scene_spec` → REST 下发 → `SceneInterpreter` 渲染）。AI 答疑链路存在缺口：前端 `AssistantInteractiveSceneCard` + `assistant_card.dart:199-203` 已预留 `interactive_scene` 卡类型与渲染卡槽，但对 `backend/app/features/assistant` 全量 grep `scene_spec|build_scene_spec|default_scene_from_figure|interactive_scene` → **零命中**，即后端 guide 当前**不发射**场景卡。补齐只需：几何类答疑命中图库图形时，复用既有 `build_scene_spec_for_question` / `default_scene_from_figure` 生成 SceneSpec，emit `data.type='interactive_scene'` 载荷。前端零改动（渲染器已就绪）。与 v3 设计完全自洽，属**实现待补、非设计不可行**。
- **Snapshot unchanged (and stronger):** instances hold the resolved copy; read path prefers snapshot → figure-library fallback. The registry is never referenced at render/generation, so changing `BUILTIN_SCENES` cannot affect already-stored `Question.scene_spec`. `derivedFrom` (if kept) is a provenance stamp only, **not used for instance enumeration** — the browse page aggregates backend built-in references only.
- **Figure geometry sub-phase:** backend becomes the single source of figure vertices, delivered via the library endpoint; frontend geometry module retired to fetch+cache. This also unifies the house-fallback divergence.
- **Migration:** **no new column**; `scenes` already carries `none_as_null`. Existing `scenes[].kind='reflection'` (if any) aligns naturally with registry `kind='reflection'` — no migration. The dual-semantics "escape hatch" (`scene_name` empty → full custom template) is **removed** because `scenes` is always a complete resolved scene.
- **API contract shape:** `GET /materials/scene-library` → `{ scenes: [{ kind, list: [{ name, value, type?, label? }], structure?, associated_knowledge_points?: [{ id, name, subject, grade, semester }], instance_count?: int }], figures?: [...] }`. `value` is a JSON union (number/string/array) — never narrowed to string. **No** instance-enumeration endpoint for generated snapshots (`GET /scenes/{kind}/instances` etc.) — the library aggregates built-in references only, not generated question/courseware snapshots.
- **场景库浏览页（Flutter 教师端）语义边界（共识锁定）：** 页面的「场景实例」**只引用后端内置参考**——即注册表中的命名场景（`kind`）与其关联的 `KnowledgePoint`（经扫描 `scenes[].kind == <registry kind>` 反查）。**不聚合**已生成的题目/课件快照（`Question.scene_spec` / `Courseware.sections[].spec`）。「内置实例数量」= 关联知识点数（= `associated_knowledge_points.length`）。「其余实例」（生成快照）**只在打开具体题目/课件时**由 `SceneInterpreter` 在其所属的具体实例场景中渲染，**不进入库清单**。列表项 = 场景名(kind) + 所属知识点 + 内置实例数量；点击进详情 = 列出该场景的全部内置实例（各关联知识点 + 各自 `scenes` override + `SceneInterpreter` 按 `kind` 渲染的预览）。

- **课件（Courseware）环节消费统一解析入口（已实施）：** 课件 `interactive_scene` 环节此前**完全没有**解析入口——场景全靠 AI 起草时顺便写进 `payload`，AI 没写就是没图，正是 ADR-0061 §U.4「换个地方就没图」在课件侧的同一根因。现由 `create_courseware` 在 AI 起草后、落库前调用 `resolve_kp_scene(kp)` 补上。**三条边界**：① 只在**新建（AI 起草）**时补，不在保存路径上补——否则教师「清除场景」会被立刻填回（与 `copyWith` 用 `??` 导致 null 不生效同款 bug）；② 只补 `interactive_scene`（素材画廊 / 练习挂轴对称场景是噪音）；③ AI 已在 `payload` 给了完整 SceneSpec（含 `kind`+`inputs`）时**不覆盖**（AI 按题面定制的比知识点默认的更具体）。落库为深拷贝快照，之后改知识点场景不影响已生成课件。

## Testing Decisions
- **New backend test module** covering: `get_builtin_scene('reflection')` returns the authoritative default list (axis 90°/pos 0.5, neutral seed, `figure` empty); unknown `kind` → `None`; `GET /materials/scene-library` matches the registry AND `associated_knowledge_points`/`instance_count` correctly aggregated by scanning `scenes[].kind`; `resolve_kp_scene(kp)` returns `kp.scenes` (no registry merge); **snapshot-immutability regression** (rewrite `BUILTIN_SCENES['reflection']`, assert an already-stored `Question.scene_spec` is unchanged — stronger here because nothing references the registry); `kind` stability assertion.
- **Prior art / reuse:** `test_scene_fusion.py` and `test_scene_figures.py` must stay green; `test_scene_extract.py` unaffected.
- **Frontend:** `flutter analyze` zero issues; `scene_editor_dialog_test` asserts the "select `kind` + prefill + tune override + save complete `scenes`" shape and the developer hint when `scenes` is empty; full suite (311 cases) no regression.
- **Good test = external behavior only:** assert resolved output and snapshot immutability, not the internal merge mechanism.
- **Highest seam (preferred):** the `resolve_kp_scene` (thin reader) unit test + the `GET /materials/scene-library` API test (with aggregation) + the frontend editor dialog test. No new seams needed.

## Out of Scope
- DB-backed template table / runtime editing / versioning (separate ADR; conflicts with the no-DB-table decision).
- Teacher-authored non-builtin scenes / "escape hatch" — **removed**: kind is developer-defined, teacher UI only offers registry kinds, and `scenes` is always complete (no custom-template escape hatch).
- Many-to-many scene association (deferred).
- `structure` 落点 choice (A: move structure into frontend renderer / B: keep in JSON) — recommended A, but explicitly pending a decision.
- Multi-graphics kinds beyond `reflection` (future).
- Live binding (explicitly rejected — would break snapshot immutability).
- **AI 答疑后端发射场景卡 — 待补（NOT out-of-scope）：** 见 Implementation Decisions 该条。这是分析发现的唯一缺口：前端渲染卡槽已就绪，后端 guide 尚未发射 `interactive_scene` 卡。应并入实施 ticket（建议并入原题 02 或新增后端发射卡 ticket），**不应视为不做**。

## Further Notes
- **Low immediate benefit, near-free cleanup:** only 1 reflection knowledge point exists in prod (`scenes` non-empty = 0 rows), so shared-template benefit accrues only once ≥2 points set `scenes[].kind='reflection'`. Value is mainly architectural: making the implicit fallback explicit, unifying the question/courseware parse entry, and scaffolding future multi-graphics kinds.
- **The real dual-hand-maintained copy is figure geometry, not the registry** — ✅ **已收口**：后端 `scene_figures.py` 是唯一手写事实源，前端 `figures.dart` 由 `frontend/scripts/gen_figures.py` **构建期生成**（非运行时拉取——整库画廊必须离线可用）。新增 `GET /materials/scene-library/figures` 作 wire 权威；`FigureShape.note` 承载教学意图且不进 `to_dict()`；前端 house 兜底保留为渲染层安全网（后端不兜底）。唯一失效模式「改顶点忘跑脚本」由 `--check` + `test_frontend_figures_are_not_stale` 变红灯。
- **Deployment default:** tablet-first / offline classroom → bundle-cached (fetch + cache) is the default; pure live-API is rejected for the teacher editor.
- **场景库浏览页只聚合后端内置参考**：不跨查 `Question.scene_spec` / `Courseware.sections[].spec` 生成快照，故**不引入** `GET /scenes/{kind}/instances` 类实例枚举端点；`derivedFrom`（若有）仅在落库快照里作溯源戳，不作为清单清点依据。生成快照的渲染归属其所属题目/课件的具体实例场景（由 `SceneInterpreter` 负责），与库浏览解耦。
- **v3 convergence vs early drafts:** removed the `scene_name` column and the "registry-as-generation-source + override merge" path; `scenes` is now the single source of truth and the registry is purely an authoring aid. This is safer (no live binding) and matches the empirical fact that teacher-authored non-builtin kinds never existed.
