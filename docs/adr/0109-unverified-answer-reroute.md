# ADR-0109 无据正文不硬失败，而是换一个业务重来一次（至多一次）

- 状态：已采纳
- 日期：2026-10-21
- 关联：ADR-0033（绝不静默降级，本 ADR 修订其**兑现方式**而非其约束）、ADR-0043（推理/正文分流）、ADR-0104（路由原语 = 决策模型 / LLM 分类）、ADR-0105（无命中落能力引导）、ADR-0107（门控上移，本 ADR 复用其门控与「不过门控 = 没决策」语义）、ADR-0081（动作直配）
- 实现：`agent_core/errors.py`（`UnverifiedAnswerError`）、`agent_core/subagent.py`（`run_with_tools(raise_unverified=)`）、`agent_core/runtime.py`（`run(allow_reroute=)` / `_reroute_unverified` / `_reroute_target`）、`app/features/assistant/service.py`（聊天路径开启）

## 1. 背景

ADR-0033 的**末闸**：声明 `requires_tool_data` 的业务（生产拓扑即 `tasks`）整轮没执行过任何工具
却产出正文 → 硬失败 `TOOL_UNSUPPORTED`。立闸的事故是 `c361dd01`：本地小模型流式下不产原生
function calling，直接编出「你共有 3 个学生在册」——权限层根本没被调用，用户看到的是假的。

这道闸守住的约束是**没有数据支撑的结论一个字都不许到用户面前**。但它的提示语把两种成因
混成了一句话：

```text
A 类（路由误判）：「23+45 怎么算」被判给了任务学情 → 模型直接作答（答对了）
  用户看到：当前模型没有调用任何查询工具就给出了结论…请重试；若反复出现，请改用支持原生工具调用的模型。
  实际：重试一万次也是同一条错误，且问题根本不在模型。

B 类（模型能力）：小模型产不出原生 FC，直接编造业务数字（c361dd01 原型）
  用户看到：同一句话。
  实际：这句话**恰好是对的**——真问题就是换模型。
```

同一句提示不可能同时正确。而对 A 类用户，它给的是一条**不可执行的建议**。

## 2. 决策

**末闸命中时不再直接报错，而是丢弃那段正文、换一个业务重来一次；换不出落点才回到原文。**

```text
requires_tool_data 且整轮无工具 → raise UnverifiedAnswerError(text=acc)   # 正文随异常丢弃
  → runtime：排除当前业务再问一次决策模型
       判得出且过门控 → 换业务重来（交接帧显式可见）
       判不出 / 不过门控 → 维持 TOOL_UNSUPPORTED 原文
```

三条落地约束：

1. **只有末闸参与，另外两闸不动。** `run_with_tools` 里「整轮无原生 ToolCall」其实有三种形态：
   - 正文里是调用草稿（`<invoke name="...">`）→ **模型能力**问题，仍是硬失败；
   - 只有思维链、无正文（独白留在思考里）→ 同上，仍是硬失败；
   - 正文干干净净、没有任何协议痕迹 → 本 ADR 的落点。
   前两种是 c361dd01 的形态，把它们也改成重路由，等于把「换模型」这个真问题藏起来。
2. **至多一次。** 候选集排除当前业务（所以新业务不可能是刚失败的那个）；接手的业务再无据时
   `raise_unverified` 为 `False`，直接收原硬失败。两个互相看不上的业务不会把一条消息弹到轮次上限。
3. **只有自然语言路径开启。** `allow_reroute=True` 只由「业务是路由算出来的」那条路径传入——
   生产聊天路径（`service.py` 的 `decide → run`）。结构化出题（`POST /tasks/generate`）自带
   `business`（规格即意图），把它改判到别的业务等于推翻调用方的显式指定。

### 2.1 这不是静默降级

ADR-0033 的原文是「**绝不静默降级为纯文本**」。区分点在于：

- **静默降级** = 放行那段正文（用户拿到假数据还以为是真的）；
- **重路由** = 换人。正文在抛异常前从未进过事件轨（思考缓冲要到末段才 flush），丢弃后它在
  结构上就不存在，调用方不可能误把它转发下去；交接本身在事件轨上显式可见（一条
  `THINKING(extra={"routing": True})` 帧）。

### 2.2 落点怎么选：再问一次路由，而不是挑一个固定的接盘侠

A 类与 B 类在该业务内部**无从分辨**（正文都是干净的自然语言）。分辨的办法是让路由在
**排除当前业务**的前提下再判一次：

- A 类：这句话天然是讲解问题，排除 tasks 后决策模型给 tutor 高分 → 换人，用户拿到解法；
- B 类：「小明最近错题多吗」排除 tasks 后在 {tutor, capability} 上拿不到高分 → 不过门控 →
  维持原文，用户拿到「改用支持原生工具调用的模型」这句**正确的**建议。

只问**决策模型**原语（本地 p50 23 ms），不问 LLM 分类（p50 1084 ms）：它本就产出
`probabilities` 全量分布，排除一项后概率重新归一化但仍**跨 K 可比**（ADR-0107 定的口径：
分数取概率而非 TypeSafe 的 `confidence`），故门控不用改。决策模型不可用 → 不猜，维持硬失败。

## 3. 为什么不这么做

- **改成静默放行正文**：那是 ADR-0033 明令禁止的，本 ADR 只是它的修订，不是它的废除。
- **三闸一起改成重路由**：会把 c361dd01 的真问题（模型不会原生 FC）掩盖成一次答非所问（§2.1）。
- **固定落点到某个业务**（如「一律转 tutor」）：B 类用户会拿到 tutor 对业务数据问题的讲解，
  同样是答非所问，且此时「换模型」这句正确的提示再也没有机会说出口。
- **允许两跳以上**：两个业务互相看不上时，一条消息会在它们之间弹到轮次上限（ADR-0033 的
  `TOOL_TURN_LIMIT` 保护都没机会生效，因为是跨 run 的）。
- **结构化路径也开**：规格即意图，改判等于推翻调用方的显式指定（§2.3）。
- **把开关塞进 `ctx.extra`**：`run` 是被多个测试桩覆写的公开接口，显式 kwarg 让覆写者必须
  表态（不接受的桩会当场 `TypeError`，而不是静默丢掉一个新选项）。

## 4. 后果

- 正面：A 类用户（路由误判）从「一条不可执行的建议」变成拿到接手方的回答；B 类用户的
  提示语不变；交接在轨迹上可见；循环有硬闸。
- 代价：A 类的用户侧延迟多一轮模型往返（本地 ~1 s 量级，与原本的 36 s 出题等待同族但更短）；
  `run_with_tools` 多一个 kwarg，`run` 多一个 kwarg（四个测试桩随之补签名）。
- 已记录的局限：轨迹里 `routing` 步记录的是**首路由**的业务，重路由后的实际接手者只出现在
  交接思考帧里（前端可见，轨迹步不重写）。需要时另开票。

## 6. 对 ADR-0033 的修订

ADR-0033 的末闸定义的行为是「产出 `TOOL_UNSUPPORTED` 并中止」。本 ADR 把它改为
「丢弃正文 → 换业务重来一次 → 换不出才产出 `TOOL_UNSUPPORTED` 并中止」。
**「绝不静默降级为纯文本」这条约束本身不变**——未验证的正文在任何路径下都不得到达用户
（见 §2.1 与守卫表里的第一条）。
