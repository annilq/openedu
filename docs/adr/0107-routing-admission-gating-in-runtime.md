# ADR-0107 路由采纳门控上移 runtime：模型只出分数，runtime 决定是否采纳

- 状态：已采纳
- 日期：2026-10-21
- 关联：ADR-0104（规则路由移除，路由原语 = 决策模型 / LLM 分类）、ADR-0105（无命中落能力引导；本 ADR 修订其「命中」定义）、ADR-0106（`routing_criteria`，本 ADR 的输入数据来自其落地后的分布）、ticket 11（决策模型上线 + 门控改用 pmax）、ticket 12（文案调优 59% → 74%，并给出 pmax 分布）、ticket 13（门控议题，本 ADR 的落地票）
- 实现：`agent_core/runtime.py`（门控表 + `consensus` 策略）、`agent_core/registry.py`（`min_adopt_score`）、`agent_core/adapters/laya.py`（去掉 `threshold`）、`agent_core/adapters/llm_route.py`（`confidence` 可空）

## 1. 背景

ADR-0104 之后，路由的形状是「动作直配 → 策略原语（决策模型 / LLM 分类）→ 无命中引导」。
其中「原语给出的业务算不算数」由**适配器内部的一个浮点数**决定：
`LayaDecisionModel(threshold=0.5)` 在 `decide()` 里比较 pmax，不够就返回 `None`。这带来
四个问题（ticket 13 的 Problem Statement）：

1. **阈值是构造参数而不是策略**：运行时无从按角色 / 按业务调整，学生端与教师端共用 0.5。
2. **「不置信」与「没决策」被压成同一个 `None`**：runtime 只看到「这个原语不决策」，看不到
   「它其实选了 X 但只有 0.43」。于是「换个更低的阈值再看看」「两个原语互验」这类策略
   **在当前结构下表达不出来**。
3. **LLM 分类器的置信度完全没被门控**：`classify_llm` 会回 `confidence`，但只被记进
   `extra`，从不参与采纳判断——同一次路由里两个原语的门控强度不一致。
4. **误判代价不对称**：判成执行体（tasks / tutor）＝自信地答非所问；判成引导类业务与
   ADR-0105 的「都没命中」在用户侧**同形**。同一个阈值等于默认两种错误代价相同。

ticket 12 把文案调优做完（74%），并留下结论：**收益在置信度分布而不在排序能力**——
这正好是门控议题的入口。

## 2. 决策

**决策模型只负责给出「候选 + 分数」；是否采纳由 runtime 的一处声明式门控决定。**

```text
score(primitive) = 决策模型的 pmax  |  LLM 分类的 confidence
accept           = score >= min_adopt_score(business, role)
```

`min_adopt_score` 的取值序（延续 ADR-0105 的声明式纪律）：

1. **业务自述**：manifest 的 `min_adopt_score`（新增字段，`0` = 未声明）。内核只认
   「这个业务声明了更高门槛」这个事实，**不认任何业务键**。
2. **角色覆盖**：`set_role_min_adopt_score(role, x)`（运行时 / 测试可设）。
3. **全局默认**：`DEFAULT_MIN_ADOPT_SCORE = 0.5`。

配套四点：

- **适配器不再吞结果**：`LayaDecisionModel` 移除 `threshold` 参数，解析出选项就回传
  `DecisionResult(choice, prob)`，低分也如实给（这是「换个原语再问一次」能表达的前提）。
- **被否掉的候选可见**：`extra["rejected"]` 记录 `{primitive, business, score,
  min_adopt_score}`，随无命中引导一起回传。此前 `routed_by="default"` 里混着「模型没回」
  与「回了但 0.43」，轨迹上分不出。
- **LLM 的 confidence 走同一张表**，但 **`None`（模型未自报）不作比较**。
- **交叉校验（consensus）作为可选策略**：`AI_ROUTING_STRATEGY=consensus` 时两个原语都跑，
  业务一致且各自过门控才采纳；不一致 → 无命中引导。**不进默认**。

## 3. 实测依据（ticket 13，全部来自 `eval/decision_model_eval.py`）

### 3.1 候选 A「学生端单独更高阈值」——被数据否决

`--sweep` 把 44 条计分用例（34 调优 + 10 留出）的 pmax 逐档摊开，按「正确 / 有害错
（→ 执行体）/ 无害错（→ 引导）」分面：

| 阈值 | 调优集净收益(+1/−3/−1) | 留出集净收益 |
|---|---|---|
| 0.50（现状） | +2 | −2 |
| 0.53 | **+7** | **−3** |
| 0.55 | +7 | −3 |
| 0.60 | −2 | −3 |
| 0.75 | +2 | −1 |

那条看似可观的「抬到 0.53」**在留出集上是反向的**——低分段每条用例逐条摊开也证实：
`[0.50,0.53)` 这段里调优集是 2 有害错 + 1 正确，留出集是 1 正确 + 0 有害错。**不存在可分离
区间**，阈值不是有效杠杆。学生端尤其如此：正确路由的 pmax 反而更低（0.41–0.76），抬门槛
先掉的是正确路由（挡掉 10 条正确才够到唯一一条学生端有害错 0.702）。

> 结论：默认 0.5 不动，角色覆盖表保持**空**（机制就位、有测试，生产不设值）。空表不是
> 「没做完」，空表的理由写进了代码注释与本节。

### 3.2 候选 C「与 LLM 分类器交叉校验」——实现并实测，但不启用

同一批 44 条用例，同时问本地决策模型（`laya:multilingual`）与真实 LLM 分类器
（生产默认模型 `deepseek-v4-flash`，走生产的 `classify_llm`）：

| 策略 | 正确 | 有害错 | 无害错 | 落引导 | 净(+1/−3/−1) | p50 |
|---|---|---|---|---|---|---|
| ① 决策模型（默认 auto，现状） | 29 | 9 | 2 | 4 | 0 | 60 ms |
| ② LLM 分类 | **42** | 1 | 0 | 1 | **39** | 1081 ms |
| ③ 交叉校验（一致才采纳） | 27 | **0** | 0 | 17 | 27 | 两者相加 |
| ④ auto 现状（不采纳才问 LLM） | 33 | 9 | 2 | 0 | 4 | — |

留出集口径一致（决策模型 5/10、LLM 分类 9/10、交叉校验 4/10 且 0 有害错）。

交叉校验确实把有害错降到 0，但**同样是付那次 LLM 往返，直接信 LLM 分类全面更好**
（正确 42 vs 27，有害错 1 vs 0），且它让 17/44 条落到引导。故：

> 结论：`consensus` 作为**可选档位**落地（契约完整、有测试），**不进默认策略**。

### 3.3 顺带修掉的一处误杀

`RoutingDecision.confidence` 原为 `float = 0.0`：`deepseek` 在 44 条里有 13 条不填该字段，
按 0 参与 0.5 门控会连带挡掉 **6 条正确**的路由（正确 36 → 30）。改为 `float | None = None`
后，「未自报」不再被当成「零置信」（改完该字段的自报率也明显上升：13 → 4）。

## 4. Considered Options（否决）

- **继续微调单一阈值**：见 §3.1，无可分离区间；调优集上的收益在留出集上是反向的。
- **把 `role` 塞进决策模型适配器**：决策模型端口是业务 / 角色无关的抽象，塞进去会让两个
  原语的门控再次分家。角色只有 runtime 知道，门控就该在 runtime。
- **为了交叉校验把默认策略改成必跑两个原语**：延迟（+1.08 s/轮）与「每轮同步路由」的
  定位冲突；且实测显示同样的预算下直接信 LLM 更好。
- **让 `capability` 声明更高门槛**：在本拓扑里它是 `fallback_guide` 的声明者，拒掉它、
  落点还是它——门控对它**是恒等变换**，设了也没用（这一条写在此处，避免以后重复讨论）。

## 5. 后果

- 正面：「不置信」第一次可观测（`extra["rejected"]`）；门控只有一处；两个原语同等对待；
  「按角色 / 按业务设门槛」第一次可表达（虽然当前数据不支持设值）。
- 代价：`LayaDecisionModel` 的构造签名变了（去 `threshold`），既有契约测试（「门控用 pmax
  而不是 confidence」）迁移到 runtime 层——断言点不变（给定输入 → 落在哪个业务），位置变了。
- 未决（**不在本 ADR 内**）：§3.2 的 ② 显示 LLM 分类器在准确率上显著优于本地决策模型
  （留出集 9/10 vs 5/10，有害错 1 vs 9），但延迟 60 ms → 1081 ms。是否把默认原语换掉是
  延迟 / 成本 / 准确率之间的取舍，需另开一张票由用户拍板（ticket 14）。

## 6. 守卫

| 测试 | 守护 |
|---|---|
| `tests/ai/test_routing_gating.py`（15 项） | 低分落引导且 `rejected` 可见、无答案时 `rejected` 为空、角色覆盖生效与可复位、业务自述门槛生效、**门控不认业务键**（给清单里本来没有的 `calendar` 声明门槛也生效）、LLM confidence 同门控、未自报不按 0 处理、consensus 一致才采纳 / 不一致落引导 / 两个原语都跑 / 单边不过门控不采纳、动作直配绕过门控 |
| `tests/ai/test_laya_adapter.py` | 分数取自 `probabilities` 的 top 值；低分**如实回传**不再被吞 |
| `eval/decision_model_eval.py --sweep` | 改阈值前必跑：分角色 / 分集（调优 vs 留出）的阈值扫描，判断可分离区间是否存在 |
| `eval/decision_model_eval.py --consensus` | 改路由原语前必跑：决策模型 × 真实 LLM 分类器同源对照；无可用 provider 时**跳过**，不得据此下结论 |

## 7. 对 ADR-0105 的修订

ADR-0105 定义的「命中」是「模型给出一个业务且 pmax ≥ 0.5」。本 ADR 把「命中」的定义改为
**「模型给出的业务通过了 runtime 的门控」**——落点（无命中引导）与「至多一个业务声明
`fallback_guide`」的纪律均不变，只是判定的位置从适配器移到了 runtime。
