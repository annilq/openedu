# ADR-0106 路由能力清单文案与用户可见清单分离（`routing_criteria`）

- 状态：已采纳
- 日期：2026-10-21
- 关联：ADR-0097（能力清单 = manifests 投影，单一事实源；本 ADR 为其**有据的例外**）、ADR-0104（规则路由移除，criteria 即路由候选）、ADR-0105（无命中落能力引导）、ticket 11（决策模型上线 + 中文基线 59%）、ticket 12（文案调优实测）、ticket 13（门控，后续）
- 实现：`routing_criteria` 字段（`agent_core/registry.py`）+ `router._capability_text` 优先级

## 1. 背景

ADR-0104 后，路由模型（决策模型 / LLM 分类）看到的候选就是 `router._capability_text` 的
投影：`name` + `description` + `actions`。也就是说，**manifest 的 description 同时是两个
消费者的事实源**——面向用户的能力清单（`capability_catalog` 渲染「name：description」）
和面向模型的能力清单。

ticket 11 实测中文路由准确率只有 **59%**（34 条用例，top-1 20/34），失败面集中在三条
criteria 的可分性，最坏一条是学生「23 + 45 怎么算」被判成能力自述。ticket 12 的目标
就是改这段文案并用同一脚本量化。

调优过程中撞上一个硬冲突：

| 需求 | 实测代价 |
|---|---|
| 用户需要知道「教师可管理题库、组建草稿任务」 | 这句留在路由文案里，准确率 **74% → 56%** |
| 模型需要短、可分的能力短句 | 删掉这句，用户可见清单就少了一条真实能力 |

同一份文本无法同时满足两端——这正是 ADR-0097 修掉的那类问题的反面：ADR-0097 的单一
事实源防止的是「手抄清单与拓扑漂移」，但它隐含假设了「一份描述能同时服务两个消费者」，
实测证明这个假设不成立。

## 2. 决策

新增**可选** manifest 字段 `routing_criteria`：路由专用能力描述。

- **只替换投影里的 `description` 部分**，`name` 与 `actions` 照旧；未声明时行为与声明前
  完全一致（存量业务、新业务零成本）。
- **面向用户的清单不受影响**：`capability_catalog` 直读 `description`，不读
  `routing_criteria`。契约测试守护「清单里显示的必须等于 `description`」。
- 决策模型与 LLM 分类共用同一段（`_capability_text` 是两者唯一的投影入口）。
- 缺省为空 = 保持 ADR-0097 的单一事实源；**只有实测证明同一份文本拖累了路由，才声明
  本字段**，并在 manifest 注释里写明实测数字与教训。

## 3. 实测依据（ticket 12，34 条调优用例 + 10 条留出用例）

基线 → 落地版本（`laya:multilingual`，阈值 0.5）：

| 指标 | 现状文案 | 落地文案 |
|---|---|---|
| top-1 | 20/34 = 59% | **25/34 = 74%** |
| 采纳且正确（pmax ≥ 0.5） | 15/34 | **24/34** |
| 未采纳（→ 能力引导） | 10/34 | 2/34 |
| 采纳但错误 | 9/34 | 8/34 |
| pmax ≥ 0.8 的错误 | 0 | 2（T01/T03 查数据 → tutor） |
| 留出集 top-1 / 采纳且正确 | 6/10 · 3/10 | 6/10 · **5/10** |
| p50 / 长历史 | 25 ms / 不截断 | 23 ms / 不截断 |

**留出集说明**：top-1 没有提升（60% → 60%），提升集中在「正确路由过得了 0.5 门控」
（30% → 50%）。即文案调优改的主要是**置信度的分布**，不是模型的排序能力——这点
直接喂给 ticket 13（门控）作为输入。

## 4. 实测教训（写进 manifest 注释，防止回潮）

1. **禁止排他式否定句**：「不查数据 / 不出题 / 不解答学科问题」让准确率掉到 35%、
   高置信错误涨到 6 条。注意 capability 的「能做什么、**不能**做什么」是对称措辞，
   实测有效，不在禁止之列。
2. **禁止堆示例问句**：「例子：我班有哪些学生、出 2 道数学题」掉到 50%。
3. **capability 不要窄化成「只在用户问助手自身时」**：掉到 44%（它同时是「都没命中」
   的落点，见 ADR-0105，窄化会削弱这个角色）。
4. **单条不超过约 120 字符**：保住 1024 上下文里的长历史余量。

## 5. Considered Options（否决）

- **继续共用一份 `description`，取折中措辞**：实测折中就是两头不讨好（要么掉 18 个点，
  要么删用户该知道的能力）。
- **给模型另起一份完整清单（连 name 一起覆盖）**：`name` 同时是轨迹页与清单标题的事实
  源，覆盖它会引入第三份事实源。只替换 `description` 是最小切口。
- **放弃文案调优，直接换权重**：ticket 11 已实测否决（`largha` 38% 且长历史 422）。

## 6. 后果

- 正面：路由质量显著提升（有效准确率 15 → 24 / 34），用户可见清单保持完整。
- 代价：出现两份描述，**存在漂移风险**——改了 `description` 忘了改 `routing_criteria`
  （或反之）。缓解：`routing_criteria` 是显式声明、manifest 注释写明实测数字、契约测试
  守护「用户清单 = description」与四条文案不变量（长度、无排他否定、无示例问句、各具
  专属动词）。
- 未达成的验收项：学生端 S01「23 + 45 怎么算」仍被判成 capability（0.56），且两条查数据
  用例变成高置信错误——二者都归 ticket 13 的门控议题。
