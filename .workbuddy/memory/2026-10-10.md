## AI agent 完备性深查（@skill:architect 的 Ground 阶段，未改码）
- **角色认知：不一致**。`query` 是唯一**机制级**执行者（`query/agent.py:65-69` `_CHILD_HINT/_PARENT_HINT` + `tools/_shared.py:215 project_for_role` 剥答案 + `:148 resolve_students` 学生恒为自己/教师只能查名下）；`tutor`/`question`/`guide` **不查 `ctx.role`**，只靠路由层 `visible_businesses(role)` 过滤后"假设"，缺防御纵深——若可见性误判，后三者不会自保。
- **边界：框架清晰、跨 agent 权威模糊**。`business`/priority/triggers/hints/`requires_tool_data`/tool-loop 硬失败都干净；但 agent 间"能碰什么"靠 prompt 承诺 + 无写工具，非强制（如 `query` 只读靠 prompt 说"不要改"）。⚠️ **越界路由**：`assistant/service.py:470-481` 按 `courseware` 上下文硬改决策（`提示`→tutor、`question`→guide），绕开 manifest 路由规则——是 out-of-band 分支，模糊了"路由唯一真相源"契约。
- **业务通讯：双通道、非统一**。`query` 走 `ToolSpec` 工具抽象（handler→`features.*.service`，有回灌/转写/硬失败）；`tutor`→`TutorService`、`question`→`pipeline`、`guide`/`courseware`→`provider.stream` 直连，**绕开工具 loop**（无轮次上限/工具回灌 seam）。`courseware draft/redraft`（`courseware/service.py:260,329`）整条**绕过 runtime**（无角色门禁/safety 分类/统一失败分类）。
- **收敛判定**：对话层已单入口单 runtime 单协议（✅）；生成/创作层有 2 漏（courseware 绕过 runtime + `guide._COURSEWARE_SYSTEM` 是 question 管线外的第二条平行出题实现，无 ADR 裁定）。建议：courseware 包成 subagent 进 runtime；`guide` 课件出题并入 `question.pipeline(mode=classroom)`；`_courseware_practice` 越界分支下沉进 `runtime.decide`（courseware-aware 路由）。

## AI 接口返回协议一致性 + 建议action/quiz 是否绕过 LLM（@skill:how+why，未改码）
- **Q1 返回协议不一致（实测）**：对话类 3 个是 SSE——`/assistant/chat`(`router.py:54` StreamingResponse+`text/event-stream`+`X-Accel-Buffering:no`)、`/tasks/generate`(`tasks/router.py:89`)、`/tasks/.../regenerate-stream`(`tasks/router.py:288`)；但**AI 内容生成端点却是一次性 JSON**——`POST /courseware` 起草(`courseware/router.py:53` response_model=CoursewareResp)、`POST /courseware/{id}/redraft`(:118) 直接 `provider.stream` 内缓冲后落库返回(`courseware/service.py:260`)；同步换题 `regenerate`/`regenerate-all` 也是 JSON(`tasks/router.py:269,297`)。即"长耗时 AI 内容"反而不是 SSE，是用户"等很久一次性返回"的真凶之一。
- **Q1 答疑(tutor)本身是真·流式**：链路 `service.chat→event_stream→rt.run→tutor.agent.run→aexplain_stream(tutor.py:272)→provider.tutor_stream(genkit_provider.py:114)→adapter.stream(genkit.py:443 用 `generate_stream`)→逐 chunk 产 `TextDelta(delta)`**。`tutor/agent.py:109-112` 注释明写：旧 `tutor()` 缓冲整段 65s 才吐，已改为逐 token 下推。故"答疑不是 SSE"是**观感误判**——协议是 SSE+逐增量；若仍觉得卡，根因是 ① RAG 检索(`tutor.py:298`)首 token 前延迟 ② 具体模型/引擎 `generate_stream` 缓冲 ③ 中间代理缓冲（但后端已 `X-Accel-Buffering:no`）。**真正缓冲的是 `query` 等工具型 subagent**：`run_with_tools`(`subagent.py:393-395`) 把整轮正文累积进 `acc` 末了才 `yield assistant_message(acc)`（按轮次而非按 token 流式）。
- **Q2 建议action 服务端静态目录、非 LLM 生成**：`build_suggested_actions`(`service.py:179`)+`SuggestedAction`（`kind=prompt|navigate,quiz:bool`，前端 `assistant_suggested_action.dart:3` 注释"由服务端按上下文从固定目录装配"）。讲课(courseware)上下文下带 kp_id 时多出 3 项：举生活例子(prompt)/出判断题(prompt,`quiz:true`)/讲解(prompt)。
- **Q2 quiz 动作确实绕过 LLM、不是"处理消息"**：前端点击→`onPrompt(payload,quiz)`(`assistant_suggested_actions.dart:67`)→`send(payload,courseware,quiz)(chat_page:452-454)`→`AssistantChatReq(message:payload, quiz:quiz)`(`assistant_notifier.dart:136-142`，`quiz` 仅 true 时带)。后端 `chat()` 见 `req.quiz=True`(`service.py:545`)**直接 `return _quiz_generate_stream` 跳过 `rt.run`**——该路径 `_quiz_generate_stream(:245)` 调 `generate_question` 管线出判断题，**从不把用户点的那句 canned payload 当指令喂给 LLM**，只按 `_resolve_kp_context` 的知识点上下文出题。`req.quiz` 分支在 `rt.run` 之前、无 provider 调用。即"LLM 没处理、只返回匹配数据"对判断题动作=**成立**（返回的是按 KP 生成的题，用户的动作文本被忽略）。
- **Q2 讲解/举例 prompt 动作 LLM 仍处理**：`quiz=false` 走 `rt.run`→tutor/guide 拿 canned payload 作 message 正常生成（属"模板化指令"而非自由意图）。故建议action里**只有「出判断题」是 flag 匹配的零 LLM 路径**，其余 prompt 动作仍过 LLM（只是输入是预设文本）。
- **设计含义**：建议action 的"零延迟/零 LLM"是刻意（ADR-0072 静态目录+判断题确定性闭环），不是 bug；但若用户以为"点动作=AI 理解我的意图"，需区分——quiz 是生成器触发，讲解是模板指令。课程提纲要让 courseware 起草也走 SSE（与 chat 一致）才彻底统一协议观感。
