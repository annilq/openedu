## 「发现即注册」vs 装饰器注册（教材 KP4 盘问，仅分析未改码）
- **结论**：两者不在同一轴竞争——装饰器解决「声明就近」，**不解决「谁来加载」**。纯 `@tool` 仍需有人 import
  该模块；规模化时靠 `importlib.metadata` entry_points 扫描，那又回到「发现」，只是对象从文件夹换成模块。
- **本仓选文件夹方案的三个真实理由**（非审美）：① 确定性——`router.py:23-26` 用 `(-priority, business)`
  显式排序，装饰器的注册序＝import 序（隐式）；② 契约集中——roles/priority/triggers 一处，可单测断言
  （`test_guide_subagent.py:73` 钉 guide > query）；③ 内核零三方依赖——装饰器自动生成 schema 需 pydantic，
  且 ADR-0040 要求手写「缺席编码」（`""`/`0`/`NO_FILTER`），自动生成表达不了。
- ⚠️ **文件夹方案的实测代价**：`business` 有**三处真相**（folder 名 / `MANIFEST["business"]` / 类属性
  `business="query"`），无守卫测试对齐；`registry._load_agent_cls` 取 `inspect.getmembers` 的**第一个**
  BaseSubAgent 子类（按名排序）→ 一个 agent.py 里出现第二个子类就静默选错；失败一律 print + continue。
- ⚠️ **教材 KP4 事实偏差**：写「启动时扫描」，实为 `runtime_singleton.get_runtime()` **首次调用惰性扫描**。
- 📌 **反例（最有说服力）**：工具层其实**没用发现**——`query/tools/registry.py` 手工列 8 个 SPEC，因为
  「顺序即 prompt 顺序」。⇒ **顺序敏感的集合不能靠发现**（装饰器同样无序，所以 SDK 也要求显式 `tools=[...]`）；
  文件夹发现之所以在 agent 层可行，是因为顺序已被 `priority` 提升为数据。
- 建议（未执行）：加守卫断言 folder 名 == MANIFEST.business == 类属性 business；工具层可用装饰器生成
  ToolSpec 但**保留显式列表定序**。

## AI 查询编造「小明/小红/小华」排查（结论：**不是数据越权，是模型没走 FC**）
- 现象：annilq 名下只有 lsc 一个娃娃，助手却答 3 个娃 +「小明」的明细数据。
- 判定证据：① 会话 `02f0a828…` 的 message 轨迹里 query 三轮**没有任何 tool_call/tool_result 步**
  （落库逻辑保证有就一定记）→ 工具从未执行；② 全库 user 表仅 3 个娃娃（lsc/k/k），无「小明」。
  工具层 `resolve_children` + `require_owned_child` 按 parent_id 过滤，实测只返回 lsc。
- ⚠️ **根因（实测，可复现）**：`ministral-3:3b` 在**流式**下不产出原生 tool_calls，直接编正文——
  同一 model/system/8 个工具 schema：curl `/api/chat` `stream=false` → 正确返回 `list_children`；
  `stream=true` → 直接输出「小明/小红/小芳」。而 `qwen3:1.7b` 流式 9/9 命中工具（答 lsc）。
  ⇒ 我们的链路是 SSE 流式，必踩这个分支。**流式与否会改变模型的 FC 行为**。
- ⚠️ **守卫缺口（ADR-0033 未覆盖的一档）**：`run_with_tools` 只硬失败「acc 为空 + 从未原生 FC」和
  「正文里写调用协议」，**不拦「有正文但整轮零 ToolCall」** → 「未查先答」的编造被当正常答复下发。
- ⚠️ **假绿灯**：`model_management/probe.py` 调 `generate_stream` **不带 tools**，只验连通
