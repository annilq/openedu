### 第二轮已定（2026-09-20 晚）
- 知识点目录：**涌现优先 + 骨架兜底**（有资料用资料解析的，无资料落回自编骨架）。
- embedding：**服务端基础设施**（`EMBEDDING_PROVIDER`/`EMBEDDING_MODEL`），与家长 `ModelConfig` 解耦，
  理由：向量绑定模型，家长换 LLM 会让存量向量跨空间失效。**须在 ADR 里显式豁免 ADR-0039**。
- 目录：网盘式，目录带 **subject + grade** 元数据、子项继承可覆盖；**不绑 child**（用户明确否掉）。
- 向量化：**手动触发** + 可「重新向量化」+ **必须标记状态**（pending/ready/failed/stale）。
- 出题检索范围：**按学科+年级元数据自动过滤**，结果显示「参考了 N 份资料」。
- 英语题目语言分层：**单独拆一个议题**（提示词类，与资料库/RAG 不同性质），不在 ADR-0055 内。
- 检索通道：**dense + sparse 双路 + RRF 融合**，ColBERT **不启用**（资料量小，存储换不来收益）。
  理由补充：数学题里 dense 会把「37+48」和「35+46」判得很近（数字在语义空间区分度差）→ sparse 必留。

## 「测试连接」实测太慢：归因 + 修复（同一天续）

用户反馈"测本地 ollama 怎么这么久"。两个独立原因，都已处理：

1. **探针自己跑成了长任务（真 bug，已修）**：`_call_once` 原本 `async for ... pass` 读完整个流 + `await response`。
   本地 `qwen3:1.7b` 带 thinking，一句「ping」先吐 **330 token 思维链**再回答，整轮 **6.4s**（curl 实测）。
   改为**首帧即停**：拿到第一个 chunk 就 `future.cancel()` 收工。实测 6.4s → **0.56s**。
   ⚠️ 收尾不能只 cancel：genkit 在 401 时一帧都不出、channel 只静默 `StopAsyncIteration`，
   必须判 `future.done()` 后再 `await`（让异常冒出来），否则「认证失败」会被判成「连接成功」。
   新增两守卫：`test_probe_stops_at_first_chunk`（替身首帧后 60s 不出帧 + 探针超时 2s，
   谁改回读完整个流就必红）、`test_probe_no_chunk_but_failed_is_not_success`。

2. **剩下的慢是 Ollama 冷加载，不是探针的锅（已确认，未改代码）**：`ministral-3:3b` 走探针 16.8s，
   直连 curl 同一请求只要 **81ms**；`~/.ollama/logs/server.log` 的 GIN 记录证实 **服务端真的花了 16s**。
   抓 SDK 入参确认很干净（`options:{}`、无 `num_ctx`/`keep_alive`）→ 不是 genkit 加料。
   真因是 **2.9GB 权重换入内存**，且连续切模型会互相挤掉（qwen3 1.35GB + ministral 2.9GB）；
   同一模型紧接着再测 **0.67s**。→ 真实出题同样要付这笔冷加载，不是探针独有。
   应对：20s 超时对 7B+ 偏紧，故**超时文案按 provider 分化**——ollama 提示「首次调用要加载权重，
   第二次通常很快」，避免把家长误导成"地址填错了"。前端按钮旁文案同步改为"收到首个响应即结束"。

- 校验：后端 `ruff` 全绿 + `pytest` **432 passed**（探针用例 8 → 10）；前端 `flutter analyze` No issues。
- 顺带修正：`latency_ms` 口径现在是「首个响应」而非整轮，成功文案也写明了，免得被当成模型速度。

## 出题「可取消 / 跨页可见」侦查（grill 设计，未写码）

用户诉求：点「生成任务」、草稿页「重新生成题目」后，页面跳转/关闭就不知道后台还在不在跑，想加取消以省 token。
只读侦查结论（事实，勿再重查）：

- **出题全部是 SSE 直跑在请求协程内**：`tasks/router.py:75` `StreamingResponse`，service 三处 `async def → AsyncIterator`；
  全 `app/` 无 `BackgroundTasks` / `asyncio.create_task`。底层是**逐题串行的单次 LLM 调用**（`question/agent.py:8` 注释 + `question/pipeline.py:175`）。
- **全仓零取消实现**：backend `grep -i cancel` 零命中（无 `CancelledError`、无 `is_disconnected()`）；
  frontend `CancelToken` 零命中，`dio_network_service.dart:160` `streamPost` 没有取消入口。
- **出题过程零持久化**：`tasks/service.py:1344` 明写「纯透传，不做持久化」，题由前端收齐后调 `/tasks/from-generated`；
  整卷重生成内存攒完一次性替换（`service.py:1133` + repository 先删旧再 add_all）→ **断流 = 前 N 题作废**。
  `Task.status` 无 progress 字段；出题 token/latency **不落库**（只有 assistant chat 写 `Message.usage`）。
- **状态其实在前端留存**（`taskGenNotifierProvider`、`parentTaskReviewProvider` 均非 autoDispose），但**三处 UI 断裂**：
  ① 表单料 `_rows/_titleCtrl/_modelId` 是页内 state（`parent_task_form_view.dart:87`），切侧栏即 dispose → 回来是新表单，
     预览区却还在（`ref.watch` 照渲染）→ 表单与这批题对不上；
  ② 成功/失败只在 `build` 内的 `ref.listen`（`form_view.dart:197`）处理 → 人不在页面时成功也不 toast、不 `reset()`、不跳审核页，
     草稿却已静默落库；失败更彻底——`build` 根本不渲染 `TaskGenError`；
  ③ 审核页 `initState → _loadDetail()`（`review_screen.dart:46`）无条件 `load()` → 覆盖在途的 `ReviewLoaded.progress`。
- **纯 UI 也能做「取消」**：`CancelToken` 只是断 HTTP 连接；想「取消但保留已出的题」不必动后端形态——
  断流后用手里的 `fold.questions` 调现成 `/tasks/from-generated` 落库即可。但服务端是否立刻掐断当前那次 LLM 调用
  取决于 Starlette/uvicorn 的断连传播，**不可向用户承诺「立即停止消耗 token」**，需实测。
- 明确边界：「关 App 后仍继续生成 + 可取消」必须服务端作业化（新的作业实体 + 状态/进度落库），不是 UI 能解决的。

## 报障分析：草稿页看不到「出题思路」（grill 三轮，已落 ADR-0056 + 术语，未动代码）

> ⚠️ 编号已定：本条用 **0056**；**0055 留给上面「资料库 + RAG」那条**（它先预留），别再占用。

真问题是两处设计：① `home_notifier.dart:124` 流一结束就 `POST /tasks/from-generated`，

② 草稿页 `review_screen.dart:264` 重生成时又显示思路 → 同一页面两种答案，这才是真不一致。

代价是预览态切走会丢题）· 草稿页去掉整卷重生成、**保留单题「换一题」** · 生成页明写"思路不随任务保存"。

**两条硬约束（新增事实）**：
- **草稿页是全局唯一能改题目的地方**：`service.py:1145` `edit_question` 有 `_require_draft` 守卫；

- **草稿页无「添加题目」入口** → 删除是单向的，故单题「换一题」是唯一能维持题数不变地改一道题的手段，不能砍。

  草稿页进页面强制 `GET /tasks/{id}` 重拉，思路在这里消失。
