## 侧栏娃娃浮层溢出侧栏（ADO-0046 第二轮补充）

用户报：「娃娃的触发卡点击时候浮层选项宽度超出侧边栏，这有点不规范」。

### 根因（两条叠加，实测数据）

侧栏 0–239、触发卡 8–179（宽 171）、**浮层外框实测 0–244（宽 244）**：

1. **锚点**：shadcn 默认 `ShadAnchorAuto(bottomCenter ↔ bottomCenter)` = 相对触发卡**水平居中**，
   而底层 `positionDependentBox` 还会再居中一次。触发卡 171 比浮层 224 窄 → 两侧各溢出 ~26px；
   左溢部分又被**屏幕左缘钳住**（`margin: 0`），于是左缘落在窗口 x=0（比触发卡左缘还靠左 8px），
   右缘 244 比侧栏（240）还宽 5px。
2. **宽度记账**：shadcn 的 `popoverTheme.padding`（本仓 `all(8)`）与 2px 描边都包在**内容之外** →
   内容 224 实际得到外框 **244**（chrome = 16 + 4 = 20，由祖先链约束实测证实）。

### 改动

- 新增 `AppLayout.popoverChrome`（= `2×AppSpacing.sm + 2×AppElevation.borderWidth` = 20）：
  把这笔「无法从内容侧推导」的开销显式记账。宽度令牌语义钉为**外框宽**。
- `AppLayout.menuWidth` → **`sidebarMenuWidth`**，值改为 `sidebarExpanded - 2×AppSpacing.sm` 推导
  （原来写死 224，且是「内容宽」语义）。改名理由：值来自「与侧栏等宽」这个具体约束，不该被当通用浮层宽复用。
- 锚点分两档（`_ParentChildSelectorState.build`）：
  - 展开 / 抽屉：`ShadAnchor(offset: Offset(0, xs))` → 开在触发卡下方、**左缘齐平**，整体落在侧栏内（8–232）。
  - 轨态：`ShadAnchor(overlayAlignment: Alignment.topRight)` → 向轨的**右侧飞出**、顶端与头像齐平。
    理由：轨态若沿用「下方左对齐」，224 宽的浮层会盖住整条 64px 轨道、挡掉导航图标，
    与 ADR-0046「轨态降级而非隐藏：信息不能丢」直接冲突。
- **命名方向易读反，已写进注释**：`ShadAnchor.childAlignment` 作用在**浮层**上、
  `overlayAlignment` 作用在**触发卡**上（依据 shadcn `raw_components/portal.dart` 里
  `followerAnchor: anchor.childAlignment` 的接线）。`ShadAnchor` 的默认值
  (`childAlignment: topLeft, overlayAlignment: bottomLeft`) 恰好就是「下方 + 左缘齐平」。
- 面板内部三套左边缘 → 一套：选项药丸 22、CTA **26 → 22**（与选项同缩进 `xs`）、
  分隔线 30 → **18–222 通栏**（面板级结构边，与侧栏右缘/顶栏底边同档）。
  实测确认：pill 22–218、divider 18–222、cta 22–218。

### 守卫（`test/sidebar_header_layout_test.dart` 5 → 9 例）

新增 4 例：浮层外框左缘齐平 + 宽度 == 令牌 + 不溢出侧栏；面板内部只有一条左边缘；
浮层 CTA 高度 == `AppControl.heightOf`；轨态向右侧飞出且不压住导航图标。
**已做反向验证**：去掉显式 anchor 后几何那条报 `Expected: <8.0> Actual: <0.0>`（正是原 bug）。
顺手修掉该文件台架自己的坑：原先 `ShadApp.custom` **没传 `theme:`** → 走 shadcn 默认主题
（浮层内边距 `h12/v6`），断言几何的用例会量到与产品不符的数。现已传 `AppTheme.shadFor(...)`。

### 排查中澄清的两件事（都差点误判）

1. **浮层 CTA 高度从 32 变 40，一度以为是自己的 anchor 改动引起的。**

## 控件高度标准：32 → 40（以触控锚点逐阶下推）· 另一个并发会话

> 本节的会话就是上一节里被记为「并发会话」的那一个。两边在同一天并行改同一批文件
> （`app_theme.dart` / `MEMORY.md` / `AGENTS.md` / `.impeccable.md`），
> **这是真实危险信号：多会话共享仓库时，任何「实测数据 + 归因」前都要先确认目标文件有没有被别人动过。**

用户报「输入框与按钮同行不协调，输入框 32 有点小」，要求分析通用组件高度标准并调到 38 或 40。

### 三层根因（都能定位到具体行）

1. **标准档取 32** —— 那是 **Ant Design / Element Plus 的桌面鼠标惯例**，而 `AppControl` 原注释自述依据
   是「平板优先 + 触控目标」，**理由与取值自相矛盾**（32 低于 Material 48dp 与 Apple HIG 44pt）。
2. **`ShadButton.height` 是「内容盒高」**，描边由 `ShadDecorator` 画在盒外 → 可见高 = 传入值 + 2×描边宽。
   探针实测：主题声明 32 的按钮**渲染 40**，而输入框被 `tightFor` 钉在 32 → 同行差 8px。
   （只看声明值永远发现不了，这是关键。）
3. **第三权威 `CupertinoButton`**：`CupertinoButton(padding: zero, child: Icon(...))` 默认 `minSize` **44×44**，
   在 `parent_question_card` 的「选项行」里与 `ShadInput` 并排。

### 决策

- 三档改为**以主行动档为锚点的等距阶梯**：标准档 = 锚点 − `AppControl.step`(8)，紧凑档 = 锚点 − 2×step。
  锚点 `heightLg` 取 48（同时满足 Material 48dp 与 HIG 44pt）。**调档位只需改锚点**。
- 新表（紧凑 / 标准 / 主行动）：parent·compact **32/40/48**、parent·normal 40/48/56、
  child·compact 40/48/56、child·normal 48/56/64。主行动档**未变**，只有紧凑/标准各上移一阶；
  副产物是阶梯首次可解释（child·compact ≡ parent·normal，因为「child 大一档」与「normal 大一档」是同一个 +8）。
- **取 40 不取 38**：38 是 Bootstrap 实现副产物（12px padding×2 + 24px 行高 + 2px 描边），既非设计原则
  也非本仓令牌；40 = `AppSpacing.xl4` = Material 3 按钮标准高 = 锚点 −1 阶。
- `AppControl.step` 独立成常量，**不复用 `AppSpacing.sm`**（否则日后调间距会静默改掉全站控件高）。

### 收口

- 删掉剩余硬编码高度：`parent_question_card` 的 `ShadButton.outline(height: 36)`、
  `profile_screen` 两处分段控件的 `ghost(height: 40)`（交还主题）。
- 新增 `AppIconAction` 并在 3 处取代 `CupertinoButton`（选项行删除键 / 表单行删除键 / 题卡 info）。
  **刻意不写成裸 `GestureDetector`**：内层走 `AppFocusableAction`，保住焦点树 + Enter/Space 激活 +
  焦点环 + 悬停底色，并补 `semanticLabel`（`CupertinoButton` 本就可聚焦，换裸手势是**倒退可达性**）。
- 口径澄清写进 MEMORY：**与控件同行并排**的图标操作 = 标准档；**输入框内部**（眼睛按钮）= `heightSmOf`。

### 守卫

`frontend/test/control_height_test.dart` —— 同时守**阶梯结构**（标准 = 锚点 −1 阶、紧凑 = 锚点 −2 阶）
与**实测渲染高度**（`getSize` 出来的值，**声明值不可信**——声明 32 却渲染 40 正是当初的 bug）。
覆盖 ShadInput / ShadButton 各变体 / AppPrimaryButton / AppBrutalButton / AppIconAction / ShadSelect /
AppTextField 内部输入框，含 child 与 normal 两档对照。

- `floating_assistant.dart` 的 `LucideIcons.smartToy` **在 lucide 里不存在**（只有 `bot`）→ 工作树**根本编译不过**，
  已改 `LucideIcons.bot` 并去掉多余的 `flutter/widgets` import。
- ⚠️ **游离的挂死 `flutter test` 进程会占住 build/test_cache 锁**：上一批遗留的

## 侧栏触发卡：内容贴顶（与容器上下不居中）

用户报：「`ParentChildSelector` 在没有收起的状态时候 `_buildTrigger` 中的内容与容器没有上下对齐」。

### 根因（探针实测，非推断）

触发卡被 `SizedBox(height: AppLayout.tapTarget)` 钉到 44，而 `ShadCard` 内部结构是固定的
`Container(padding) → Row(crossAxisAlignment: start, mainAxisSize: min) → Flexible →
Column(mainAxisSize: min) → Flexible → child`（`shadcn_ui-0.56.3/lib/src/components/card.dart`）。

两个 `start` / `min` 叠在一起 → **内容只按自身高度收缩、朝上沿贴**，容器被拉高也不会垂直居中。

| | top | bottom | h |
|---|---|---|---|
| 卡片（可见外框） | 12.0 | 56.0 | 44.0 |
| 内容（`AvatarSquircle.xs`） | 13.0 | 41.0 | 28.0 |

上边距 1、下边距 15；内容中心 27 vs 卡片中心 34 → **整体上偏 7px**（1px 那侧是发丝描边）。

### 改动

- `parent_child_selector.dart`：卡片内容外补一层 `Center`（唯一改动，一处）。
  **修在调用点而不是 `AppCard` 内部**——全站每张卡片都是内容自撑高度（容器高 == 内容高），
  在那里居中等于给全站布局加一层无人验证的变换，风险与收益不成比例。

## 设计盘问：助手页加「历史会话」入口（已落地 = ADR-0048）

用户问：「数据库中已设计会话表与消息表，是否应在 AI 学习助手页右上角加会话 icon 查看历史会话」。
用 `/grill-with-docs`（**该 skill 被 `skillOverrides` 禁用**，改为直读其 SKILL.md +
`/grilling` + `/domain-modeling` 手动跑）。**只做盘问与事实勘查，未改任何代码。**

### 勘查到的结构事实（复现成本高，先记下来）

`Conversation`/`Message`（ADR-0022）虽表结构与写入路径都在，但有五个「以为有、其实没有」：

1. **`Conversation.title` 从未写入**——全仓 `title=` 只有 Task / Question 在用。列表没有现成名字可用。
2. **`Conversation.kind` 不是「会话类型」**：只在建会话那一刻由**第一条消息**的路由写死
   （`service.py:152`），续接时（`:116-146`）完全不更新。首轮问出题 → kind=question，
   第二轮问学情 → 这一行永远写着 question。
3. **`ref_task_id` 从未写入**（只在 DDL 与 read schema 里出现）——「追溯出题结果」的意图未实现。
4. **已有读路径**：`GET /api/v1/ai/debug/conversations` + `/{id}`（`app/features/ai/router.py`，
   家长 + `require_owned`），**但前端零客户端**（grep `conversations` 无命中）。
   它返回的是**轨迹**（含 `system/routing`、`tool/tool_call|tool_result`、`blocked`），不是聊天历史；
   `ConversationResp` 也没有消息数 / 预览字段 → 列表渲染不出内容。
5. **`list_conversations(parent_id=...)` 不过滤 `child_id`** → 家长自己的会话（`child_id IS NULL`）
   与娃娃的会话（`child_id` 非空）会混在同一个列表里。
   另：**无删除路径、无保留策略**（retention/purge 全仓无命中）。

### 与既有能力的重叠（关键）

- 家长端侧栏**已有「AI 答疑记录」页签** → `ParentTutorLogsView`（`home_screen.dart:229` index 3），
  读 `TutorLog`，**仅在 `role==child && business=='tutor'` 时落库**，且带 ADR-0033 的去答案约束。
  → `Conversation` 是 `TutorLog` 的**超集**（还能含娃娃的 `query` 会话）。两个入口一旦都做「看孩子问什么」就重叠。
- `AssistantNotifier._currentSessionId` **纯内存**，重启即丢；`AssistantNotifier.reset()`
  **全仓无调用方**（死代码）→ 今天既没有「新对话」，也没有任何回到旧会话的路径。

### 术语缺口

`CONTEXT.md` **完全没有 AI / 助手章节**——「会话」「对话」「助手」三个词一个都没有
（只有「伴学 Tutor」）。「会话」一旦落地就是承重词汇，需要登记。

### Round 2 前又查实四条（都是「以为有、其实没有」）

6. **`Message` 的七个列全是死的**：`input_safe` / `output_safe` / `blocked` / `block_reason` /
   `latency_ms` / `usage` / `model` —— 写入点一个都没有（`service.py` 里 6 处 `Message(...)` 构造都不带这些参数）。
   ADR-0022 说的「安全标记挂 Message 便于审计被拦步骤」**未实现**；真正的安全记录只在
   `TutorLog.blocked`（`features/tutor/repository.py:32`）。→ 会话列表**渲染不出**「已拦截」。
7. **无任何 FK 级联删除**（`ondelete` 全仓零命中）→ 删一个 `Conversation` 不会连带删 `Message`；
   而 `Conversation` 今天根本没有任何删除路径。保留/清理是明确缺口，别顺手做。

   壳内页签）都是同一个顶栏，加 icon 是改一处调用点、不动顶栏。`AppIconAction` 已存在
   （`app_theme.dart:1802`，并发会话新增）。
9. **后端不允许家长续接孩子的会话，而且是静默失败**：归属校验为

所以家长回放孩子的会话，看到的内容与**孩子当时看到的一致**（不是上帝视角）。

另：「AI 答疑记录」（F-305）**不是**会话列表的重复品——它一格是「一问一答 + 学科标签 +

### 🔴 Round 3 前查出一个**现网 bug**：多轮历史从第二轮起顺序就是错的

`event_stream()` 的 turn 计数器**每次调用都从 1 重启**（`service.py:188 turn = 1`），
而续接轮的 user 消息用的是 `next_turn()`（`:140`）= **消息总条数**。两者不同源 → tum 撞车：

| | 第 1 轮（新建） | 第 2 轮（续接） |
|---|---|---|
| user/input | turn=0（`:160`） | turn=**3**（`next_turn`） |
| system/routing | turn=1（`:206`） | turn=**1** ← 撞 |
| assistant/output | turn=2（`:265`） | turn=**2** ← 撞 |

`_read_history`（`repository.py:30`）按 `turn asc` 取 `role in (user,assistant) ∧ step in (input,output)` →
拿到 turn ∈ {0, 2, 3, 2}，升序后是 **[user₁, assistant₁, assistant₂, user₂]** ——
第二轮的"答"排在第二轮的"问"前面。且 SQLite 对并列 `turn` **无确定次序**，可能不稳定。

**影响**：喂给模型的多轮上下文是错序的；`load_chat_history_with_summary` 的摘要路径同样受影响。
**测试为什么没发现**：`test_repository.py` 用 `_FakeSession` 直接喂**已排好序**的行（假 session 不经过 SQL），
`tests/api/routes/test_assistant.py` 只发**一轮**（单轮时 turn=0/1/2 恰好不撞）→ 顺序从未被覆盖。
**一行修法**：`turn = 1` → `turn = next_turn(session, conv_id)`（对首轮等价，对续接轮全局单调）。
→ 这是**做只读回放的前置**：回放若按 `turn asc` 排，会把同样的错序渲染给用户。

另修正我 Round 2 的一个成本误判：**折叠器不是完全不存在的**。`_read_history` 就是折叠的一半
（过滤 + 排序 + 取 `{role, content}`），且**每轮续接都在生产路径上调它**；缺的只是把 `payload.cards`
重新挂回气泡、以及过滤掉 `system/routing` 与 `tool/*`（后者它已经过滤了）。成本远低于我先前说的。

Round 3 已提出：Q9 页面结构（icon 切页内模式 vs push 独立列表页 → 栈到 3 层）· Q10 后端读路径
