## 侧栏娃娃浮层溢出侧栏（ADO-0046 第二轮补充）

用户报：「娃娃的触发卡点击时候浮层选项宽度超出侧边栏，这有点不规范」。

### 根因（两条叠加，实测数据）

侧栏 0–239、触发卡 8–179（宽 171）、**浮层外框实测 0–244（宽 244）**：

1. **锚点**：shadcn 默认 `ShadAnchorAuto(bottomCenter ↔ bottomCenter)` = 相对触发卡**水平居中**，
   而底层 `positionDependentBox` 还会再居中一次。触发卡 171 比浮层 224 窄 → 两侧各溢出 ~26px；
   左溢部分又被**屏幕左缘钳住**（`margin: 0`），于是左缘落在窗口 x=0（比触发卡左缘还靠左 8px），
   右缘 244 比侧栏（240）还宽 5px。
2. **宽度记账**：shadcn 的 `popoverTheme.padding`（本仓 `all(8)`）与 2px 描边都包在**内容之外** →
   内容 224 实际得到外框 **244**（chrome = 16 + 4 = 20，由祖先链约束实测证实）。

### 改动

- 新增 `AppLayout.popoverChrome`（= `2×AppSpacing.sm + 2×AppElevation.borderWidth` = 20）：
  把这笔「无法从内容侧推导」的开销显式记账。宽度令牌语义钉为**外框宽**。
- `AppLayout.menuWidth` → **`sidebarMenuWidth`**，值改为 `sidebarExpanded - 2×AppSpacing.sm` 推导
  （原来写死 224，且是「内容宽」语义）。改名理由：值来自「与侧栏等宽」这个具体约束，不该被当通用浮层宽复用。
- 锚点分两档（`_ParentChildSelectorState.build`）：
  - 展开 / 抽屉：`ShadAnchor(offset: Offset(0, xs))` → 开在触发卡下方、**左缘齐平**，整体落在侧栏内（8–232）。
  - 轨态：`ShadAnchor(overlayAlignment: Alignment.topRight)` → 向轨的**右侧飞出**、顶端与头像齐平。
    理由：轨态若沿用「下方左对齐」，224 宽的浮层会盖住整条 64px 轨道、挡掉导航图标，
    与 ADR-0046「轨态降级而非隐藏：信息不能丢」直接冲突。
- **命名方向易读反，已写进注释**：`ShadAnchor.childAlignment` 作用在**浮层**上、
  `overlayAlignment` 作用在**触发卡**上（依据 shadcn `raw_components/portal.dart` 里
  `followerAnchor: anchor.childAlignment` 的接线）。`ShadAnchor` 的默认值
  (`childAlignment: topLeft, overlayAlignment: bottomLeft`) 恰好就是「下方 + 左缘齐平」。
- 面板内部三套左边缘 → 一套：选项药丸 22、CTA **26 → 22**（与选项同缩进 `xs`）、
  分隔线 30 → **18–222 通栏**（面板级结构边，与侧栏右缘/顶栏底边同档）。
  实测确认：pill 22–218、divider 18–222、cta 22–218。

### 守卫（`test/sidebar_header_layout_test.dart` 5 → 9 例）

新增 4 例：浮层外框左缘齐平 + 宽度 == 令牌 + 不溢出侧栏；面板内部只有一条左边缘；
浮层 CTA 高度 == `AppControl.heightOf`；轨态向右侧飞出且不压住导航图标。
**已做反向验证**：去掉显式 anchor 后几何那条报 `Expected: <8.0> Actual: <0.0>`（正是原 bug）。
顺手修掉该文件台架自己的坑：原先 `ShadApp.custom` **没传 `theme:`** → 走 shadcn 默认主题
（浮层内边距 `h12/v6`），断言几何的用例会量到与产品不符的数。现已传 `AppTheme.shadFor(...)`。

### 排查中澄清的两件事（都差点误判）

1. **浮层 CTA 高度从 32 变 40，一度以为是自己的 anchor 改动引起的。**
   做隔离实验（只回退 anchor / 只回退宽度）+ 祖先链约束 dump 后确认：与 anchor 无关。
   真因是**并发会话正在重构 `AppControl` 高度阶梯**——原来 `parent+compact` 标准控件高是 32（`xl3`），
   他们把锚点移到 Material 的 48dp 最小触控目标（`heightLg = xl5`）后整条阶梯上移一档 → 40（`= heightLg - step`）。
   `app_theme.dart` mtime 00:24:23 正好落在我两次探针之间。
   **教训：多会话共享仓库时，测量数据必须先确认「同名文件/令牌有没有被别人改过」再归因。**
2. **新粗野的 2px 描边确实是浮层 chrome 的一部分**（外框 = 内容 + 主题内边距 + 2×描边），
   由祖先链 dump（`Padding 240×157` → `Padding 244×161`）证实，不是在猜。

## 控件高度标准：32 → 40（以触控锚点逐阶下推）· 另一个并发会话

> 本节的会话就是上一节里被记为「并发会话」的那一个。两边在同一天并行改同一批文件
> （`app_theme.dart` / `MEMORY.md` / `AGENTS.md` / `.impeccable.md`），
> **这是真实危险信号：多会话共享仓库时，任何「实测数据 + 归因」前都要先确认目标文件有没有被别人动过。**

用户报「输入框与按钮同行不协调，输入框 32 有点小」，要求分析通用组件高度标准并调到 38 或 40。

### 三层根因（都能定位到具体行）

1. **标准档取 32** —— 那是 **Ant Design / Element Plus 的桌面鼠标惯例**，而 `AppControl` 原注释自述依据
   是「平板优先 + 触控目标」，**理由与取值自相矛盾**（32 低于 Material 48dp 与 Apple HIG 44pt）。
2. **`ShadButton.height` 是「内容盒高」**，描边由 `ShadDecorator` 画在盒外 → 可见高 = 传入值 + 2×描边宽。
   探针实测：主题声明 32 的按钮**渲染 40**，而输入框被 `tightFor` 钉在 32 → 同行差 8px。
   （只看声明值永远发现不了，这是关键。）
3. **第三权威 `CupertinoButton`**：`CupertinoButton(padding: zero, child: Icon(...))` 默认 `minSize` **44×44**，
   在 `parent_question_card` 的「选项行」里与 `ShadInput` 并排。

### 决策

- 三档改为**以主行动档为锚点的等距阶梯**：标准档 = 锚点 − `AppControl.step`(8)，紧凑档 = 锚点 − 2×step。
  锚点 `heightLg` 取 48（同时满足 Material 48dp 与 HIG 44pt）。**调档位只需改锚点**。
- 新表（紧凑 / 标准 / 主行动）：parent·compact **32/40/48**、parent·normal 40/48/56、
  child·compact 40/48/56、child·normal 48/56/64。主行动档**未变**，只有紧凑/标准各上移一阶；
  副产物是阶梯首次可解释（child·compact ≡ parent·normal，因为「child 大一档」与「normal 大一档」是同一个 +8）。
- **取 40 不取 38**：38 是 Bootstrap 实现副产物（12px padding×2 + 24px 行高 + 2px 描边），既非设计原则
  也非本仓令牌；40 = `AppSpacing.xl4` = Material 3 按钮标准高 = 锚点 −1 阶。
- `AppControl.step` 独立成常量，**不复用 `AppSpacing.sm`**（否则日后调间距会静默改掉全站控件高）。

### 收口

- 删掉剩余硬编码高度：`parent_question_card` 的 `ShadButton.outline(height: 36)`、
  `profile_screen` 两处分段控件的 `ghost(height: 40)`（交还主题）。
- 新增 `AppIconAction` 并在 3 处取代 `CupertinoButton`（选项行删除键 / 表单行删除键 / 题卡 info）。
  **刻意不写成裸 `GestureDetector`**：内层走 `AppFocusableAction`，保住焦点树 + Enter/Space 激活 +
  焦点环 + 悬停底色，并补 `semanticLabel`（`CupertinoButton` 本就可聚焦，换裸手势是**倒退可达性**）。
- 口径澄清写进 MEMORY：**与控件同行并排**的图标操作 = 标准档；**输入框内部**（眼睛按钮）= `heightSmOf`。

### 守卫

`frontend/test/control_height_test.dart` —— 同时守**阶梯结构**（标准 = 锚点 −1 阶、紧凑 = 锚点 −2 阶）
与**实测渲染高度**（`getSize` 出来的值，**声明值不可信**——声明 32 却渲染 40 正是当初的 bug）。
覆盖 ShadInput / ShadButton 各变体 / AppPrimaryButton / AppBrutalButton / AppIconAction / ShadSelect /
AppTextField 内部输入框，含 child 与 normal 两档对照。

### 顺手修的阻断项与一个新坑

- `floating_assistant.dart` 的 `LucideIcons.smartToy` **在 lucide 里不存在**（只有 `bot`）→ 工作树**根本编译不过**，
  已改 `LucideIcons.bot` 并去掉多余的 `flutter/widgets` import。
- ⚠️ **游离的挂死 `flutter test` 进程会占住 build/test_cache 锁**：上一批遗留的
  `_tmp_assistant_page_shot_test.dart`（`toImage()` 未包 `runAsync`，MEMORY 已记过此坑）挂死 6 分钟，
  导致我的全量测试一直**等锁**，并连带出 2 个假失败（`sidebar_header_layout_test` 单跑 8 例全过）。
  `ps | grep flutter_tester` 揪出 → kill + 删临时文件 → 全量 4 秒跑完。
  **今后 `flutter test` 异常慢先查游离进程，别急着怀疑自己的改动。**
