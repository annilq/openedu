## Bug 修复：点击「生成任务」报「网络异常,请稍候重试」
- 症状：首页家长 `生成任务` 按钮触发 `home_notifier.generate()` → `streamChat` → `/assistant/chat` SSE，catch 到非 `AppException` 的裸异常 → 走 `catch (e)` 报「网络异常」。
- 根因 1（主因）：macOS `frontend/macos/Runner/Info.plist` 缺失 `NSAppTransportSecurity.NSAllowsLocalNetworking`，ATS 在 OS 层拦截明文 `http://127.0.0.1:8000`，请求根本到不了后端（后端零日志），DioException 被下方根因 2 的漏洞漏出。与 AGENTS.md「重新生成 macOS 项目会刷掉网络权限」现象一致。
- 根因 2（放大）：`DioNetworkService.streamPost` 正文 `await _dio.fetch<ResponseBody>(options)` 不在 try/catch 内，fetch 阶段抛的 DioException 直接逃离方法，被上层裸 catch 误报「网络异常」且吞掉真实错误文案（如 401 应提示登录过期）。
- 修复：① 跑 `python3 frontend/scripts/patch_macos_network.py` 幂等补回 Info.plist ATS 块（entitlements 的 network.client 本就在）；② `streamPost` 改调新增 `_safeFetch`，在 fetch 阶段即把 DioException 经 `_handleError` 转 `AppException` 再抛出。
- 验证：`flutter analyze` 全绿（No issues found）；`plutil -lint Info.plist` OK；entitlements 含 network.client。`git diff` 仅 dart 文件（Info.plist 改动由 patch 脚本落盘，未被 git 跟踪差异显示）。
- 必做收尾：改完 Info.plist 后必须**重新构建 macOS App**（`flutter build macos --debug` 或 `flutter run -d macos`），否则运行中的旧二进制仍带旧 plist。
- 注意（独立问题，非本次「网络异常」根因）：默认 `LLM_PROVIDER=mock`（无 key）下 `GenkitProvider.generate_question` 设计上返回 None → SSE 出 `count:0`「本次未能生成题目」。按 AGENTS.md/ADR-08b 出题/答疑/批改需配真实 LLM 引擎；修好网络后若仍无题，是缺 LLM key，不是网络 bug。

## 修正：上条根因判断有误（用户实测反馈）
- 用户实测：不是 macOS 网络权限问题；前端真实报错 `no host specified in uri /assistant/chat`，且**其它接口正常、唯独生成任务接口挂**。
- 真因（唯一根因）：`DioNetworkService.streamPost` 手写 `RequestOptions(path:'/assistant/chat',...)` 后直接 `_dio.fetch(options)`。读 Dio 5.11 源码确认：`fetch()` **不会**合并 baseUrl，只有便捷方法 `post/get/request` 内部会先 `.compose(_dio.options, path, ...)`。手写 fetch 拿到的 URI 只有相对路径、无 host → `no host specified in uri`；该 DioException 又被当时的裸 `catch (e)` 显示成「网络异常」（所以最初误判为网络/ATS 问题）。
- 修复：把 `streamPost` 改为 `Options(method:'POST', headers:{'Accept':'text/event-stream'}, responseType: ResponseType.stream).compose(_dio.options, path, data: body)` 再 fetch（与 Dio 自身 `request()` 一致）。同时保留 `_safeFetch` 把 fetch 阶段 DioException 转 AppException。
- 结论：Info.plist ATS 补丁并非本次触发点（但保留无害，macOS 明文 localhost 本就该有）；核心修复是 streamPost 的 compose。全项目 grep 确认仅 streamPost 一处直接调 `_dio.fetch`/`RequestOptions`，无同类隐患。
- 验证：`flutter analyze` 全绿。`/assistant/chat` 后端 curl 实测 200 SSE 正常，修复后前端将带上 `http://127.0.0.1:8000/assistant/chat` 完整 host。

## 第三次症状：点「生成任务」提示 `请先生成题目再保存`
- 这不是 bug，是 **mock 模式无题** 经后端护栏的正常体现。文案来自后端 `app/features/tasks/router.py:291` `AppErrorException(ErrCode.TASK_EMPTY_SPECS, "请先生成题目再保存")`（/tasks/from-generated 的 `if not payload.questions` 非空校验）。

## 第四次症状：配了 deepseek 仍提示「请先生成题目再保存」—— 真因是后端没真正启用 deepseek
- 用户声称已配 deepseek、之前能出題。实测运行进程（PID 99540）环境只有 `DEEPSEEK_API_KEY`，**没有 `LLM_PROVIDER=deepseek`**。`app/ai/engine.py:resolve_engine` 第146行 `provider = settings.LLM_PROVIDER`，该变量在 `app/core/config.py:37` 默认 `"mock"`，且只有 `provider=="deepseek"`（147 行）才用 deepseek key。光有 key 不配 provider → 仍走 mock → `count:0` → 落库报「请先生成题目再保存」。
- 关键误区：此前误以为「配了 key = 配了 deepseek」。代码要求**二者都有**：`LLM_PROVIDER=deepseek` + `DEEPSEEK_API_KEY`（AGENTS.md 也写明）。用户之前能出题，多半是当时启动后端的 shell 里设过 `LLM_PROVIDER=deepseek`，而当前运行的后端(99540)是未带该变量启动的；`fastapi dev --reload` 只在文件变更时重载代码，**不重载环境变量**。
- 修复（固化配置，避免复发）：从运行进程取到已有 `DEEPSEEK_API_KEY`（仅记长度不打印明文），写入 `backend/.env`：`LLM_PROVIDER=deepseek` + `DEEPSEEK_API_KEY=<key>`（config.py 读 `.env`，cwd=backend 时生效）。随后结束旧进程、后台 `uv run fastapi dev --reload` 重启。
- 验证：重启后 `/assistant/chat` 实打实返回 2 道真实数学题（`DATA type:question` ×2，`count:2`），不再 `count:0`；完整「生成→落库」模拟（拉 2 题 → POST /tasks/from-generated 带 UUID child_id）→ **201 成功**，返回 draft 任务含题目。护栏「请先生成题目再保存」不再触发。
- 客户端的"去掉 AI 模型默认选项"改动与此无关且正确：`model=null` 本就走后端全局 provider，结果一致；去掉默认项后若 `/models` 为空（见下），选择器会显空，但出题仍走全局 deepseek 不受影响。
- 附：`GET /models` 返回 `{"builtin":[],"custom":[]}` —— 本环境 `BUILTIN_MODELS="[]"` 且无自定义 ModelConfig。所以模型下拉即使不隐藏"默认"也只有空项；去掉"默认"后选择器为空。用户若想下拉有可选项，需设 `BUILTIN_MODELS`（env JSON）或家长自定义模型。这与"请先生成题目再保存"无因果。
- 结论：本次"请先生成题目再保存"是**后端运行实例未启用 deepseek（缺 LLM_PROVIDER 环境变量）**所致，非前端代码问题。已通过 `backend/.env` + 重启固化解决，并已端到端验证出題+落库成功。

## 诊断：点「生成任务」只渲染题卡、无流式文本（未修复，仅分析）
- 结论：**传输层无问题**（`DioNetworkService.streamPost` 用 `ResponseType.stream` + `Options.compose` 拼 baseUrl，SSE 确实逐帧到达）。断点在生成链路与前端渲染条件两处。
- 断点 1（后端，根因）：`app/ai/subagents/question/agent.py:254` 每题调 `provider.generate_question()` → `generation.py:238` `engine.genkit.generate(..., output_schema=QuestionSchema)` **一次性等完整 JSON**，全程不 yield 任何增量。整个出题流只发 `tool_call` → N×`data_event` → `tool_result` → `assistant_message`。`thinking()` 全项目仅 `runtime.py:89/100` 两处且都是带 `extra.business` 的路由帧（前端 home_notifier:96 已过滤）→ `liveReasoning` 恒空。`step()`/`_step_label()` 定义了但零调用（又一处死代码）。
- 断点 2（前端）：`home_notifier.dart` 从未给 `TaskGenPreview.liveIndex` 赋值（恒 -1），而 `parent_task_form_view.dart:491` 渲染条件是 `if (s.streaming && s.liveIndex >= 0)` → **内联推理区永不可能渲染**，即使后端下发 reasoning 也白搭。`ReasoningTypewriterWidget`（line 564）因此从未在出题场景露出。
- 历史关联：这正是上一轮删掉的 `generate_questions_stream`（STEP/REASONING/CARD 增量信封）本该提供的能力。当时它是零调用死代码，删除没错，但"删死代码"≠"补真流式"——真流式从未接进 subagent。
- 修复需二选一：(A) 彻底修真流式：出题 prompt 改成 `<reasoning>…</reasoning>` + JSON 单流，用 `generate_stream` 逐 token yield `thinking()`，subagent 发 `step()` 进度 + 设置 liveIndex；(B) 最小修：subagent 至少 yield `step(_step_label(...))` 让进度可见，前端修 liveIndex 并允许"无 reasoning 也显示进度面板"。

## 架构咨询：不考虑向后兼容时，解析层/转换层该怎么设计（仅设计，未落代码）
- 用户问：sa（所以）不考虑向后兼容，解析层或转换层应如何设计。产出四层管道方案，并指出当前实现 5 个真问题。
- **当前实现的 5 个问题**（读 `app/ai/generation.py` 确认）：
  1. 三层职责糊在一个 async generator：prompt 构造 + chunk 解码 + 状态机解析 + 安全闸门，6 个可变局部变量（buf/emitted/open_seen/phase/reasoning_parts/json_buf）。
  2. 协议隐式且分裂：prompt 在 `_build_stream_prompt`(142) 写「用 `<reasoning>` 包裹」，解析在 `generate_question_stream`(379) 手写状态机揣摩，隔 200 行无任何东西强制二者一致。
  3. 为「模型不听话」留 3 条猜测分支（不写标签 / 未闭合 / 尾部 `<` 保留）——用解析层补偿 prompt 层，且不可观测。
  4. 推理**两个来源**：文本 `<reasoning>` 段 + JSON 的 `reasoning` 字段，`_assemble_question` 用 `reasoning or raw.get("reasoning")` 兜。落库路径更离谱：让模型生成 reasoning 花 token，构造 `GeneratedQuestion` 时直接丢弃。
  5. **安全闸门漏了推理**：`check_output` 只校验 `stem/answer/explanation`，推理增量一路裸奔到孩子屏幕（`_assemble_question` 不校验 reasoning，流式 yield 也不校验）。
- **关键环境事实（影响选型）**：配置的模型是 `deepseek-v4-flash`（`config.py:46`），而 `engine.py:_REASONING_HINTS` 只含 `deepseek-reasoner/qwq/o1/o3/thinking` → **supports_reasoning=False**。所以 e2e 那 472 个推理帧全部来自文本标签解析，不是原生思维链。若改走「只保留 output_schema + 原生思维链」路线，该模型上推理会在 JSON 完成时才一次性到达，增量显示直接消失。
- **已核实的 genkit 事实**：`Genkit.generate_stream` 签名**支持** `output_schema` / `output_format` / `output_constrained` / `output_instructions`（`inspect.signature` 确认）；`.response` 是 awaitable Future（不是方法），resolve 出 `ModelResponse`，带类型化 `.output`。
- 提出方案：Decode(唯一碰 genkit) → Demux(REASONING 直通) → Parse(同步 push 状态机 feed/close) → Translate(语义事件→AG-UI 帧集中一处)。线上格式三选一：原生推理+output_schema / 单一分隔符 / 增量 JSON 抽取；推荐「单一分隔符」。Translate 层 2-3 个类型用 `match`，别上注册表（过度设计）；但应加**帧聚合**（472 帧太碎）。
- 用户决策：线上格式 → 原生推理+output_schema（虽明知 deepseek-v4-flash 上增量为零）；推理安全 → 推理完成时过闸门；范围 → 全套（重构 + 换格式 + 安全闸门 + 帧聚合）。
- 落地（ADR-0029，2026-09-09）：
  - `app/ai/segment.py`：Decode 层（genkit chunk → Segment），全项目**唯一**碰 genkit 的地方。换框架只改这一个文件。
  - `app/ai/parsers/question.py`：契约（QuestionSchema = output_schema）+ 解析器（SchemaQuestionParser）**同文件**，杜绝协议漂移；同步 push 状态机（feed/finish），无 async、无引擎依赖；解析失败/闸门不过/无产出统一发 QuestionFailed 显式事件，**解析层不做宽容兜底**。
  - `app/ai/runtime/translate.py`：Translate 层，match 派发 + **思维链帧聚合**（每 16 字符攒批，遇其它帧/流结束即冲刷）。未知事件直接 `raise TypeError`，拒静默丢弃。
  - `app/ai/subagents/question/agent.py`：SubAgent 不再 isinstance 派发，只 `async for frame in translate_stream(...)`；其上 `step()` 先发进度锚点再调流式生成。
  - `app/domain/genkit_provider.py`：生成题原语并入 `asdict(ev.question)` 出 DATA payload；`generate_question_stream` 无引擎时空迭代。
  - 安全闸门：`assemble_question` 拆成两层 — 题面（stem/answer/explanation）不过闸 → 整题作废（QuestionFailed）；推理单独过闸 → 不安全只丢推理，题卡照发。
  - `app/ai/generation.py`：瘦身，去掉 `_build_stream_prompt`、`TaskGenChunk`/信封、`_mock_*`（mock 兜底已删）/ `_tutor_generate`/`grade_open`（已下沉 provider）。
  - 新单测：`tests/ai/test_generate_question_stream.py`(9) + `test_question_subagent_stream.py`(5) + `test_translate.py`(4)。`test_reasoning_deltas_robust_to_any_chunk_boundary` 参数化 [1, 3, 17, 1000] 测任意切分点。
- 验证：ruff 全绿；`tests/ai`+`tests/domain` 91 passed/2 skipped；e2e 端到端：路由 THINKING 2 帧 / 非路由 53 帧 / STEP 2 / DATA 2 / 首个推理帧 1.99s（重构前 10s+ 整题等待）。
- ADR-0029 已追加；dev server(8000) 仍跑旧代码（启动方为用户），需重启生效。
- 经验沉淀：(1)「容错放解析层是治标」— 治本在 prompt 规范，漂移是隐性的；(2)契约与解析器同文件杜绝显式/隐式双协议漂移；(3)同步 push 状态机可独立测试，单测从「起假引擎喂完整流」降级到 `for i in range(len(s)): parser.feed(s[:i])`，鲁棒性参数化；(4)async generator 多个职责糊一起时，先抽四层管道，每层一职一责一失败方式，比抽 nth 个 helper 来得准。
