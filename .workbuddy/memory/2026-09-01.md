# 2026-09-01

## 分析：Flutter 客户端是否使用了 Genkit（票据 08 架构复盘）
- 用户判断「Genkit 是全栈方案，前后端都要支持效果才好」→ 核查当前状态。
- 结论：**前端没有用 Genkit，且当前架构下也无法直接用 Genkit Dart 客户端**。
  - 前端 `frontend/pubspec.yaml` 无 `genkit` 依赖；消费后端走自研 `SseClient`（`lib/shared/data/remote/sse_client.dart`），解析项目自定义 SSE 信封 `token/question/safety_refusal/done/error`。
  - 后端确实用了 Genkit（`app/ai/engine.py`/`flows.py`、`app/api/routes/stream.py`，依赖 `genkit`/`genkit-fastapi`/`genkit-openai`/`genkit-ollama`）。但 `stream.py:9` 明确「**不采用 serve_flow 原生格式，避免前端改解析**」——后端刻意把 Genkit 翻译为自定义 SSE 信封，且 `main.py` 只挂载 `api_router`，**未挂载 genkit-fastapi 的 `serve_flow` 原生 action 端点**。
- 官方 Genkit Flutter 客户端事实（来自 `genkit.dev/docs/app-frameworks/flutter/`）：
  - 包名 `genkit`，import `package:genkit/client.dart`；`flutter pub add genkit`。
  - 用法 `defineRemoteAction(url: flowUrl, fromResponse:, fromStreamChunk:)` → `.stream(input)` 返回部分对象的异步流；**它调的是后端 flow 的原生 action HTTP 端点**（如 `http://host:port/flowName`），吃 Genkit 的 typed structured streaming 协议，不是我们的自定义 SSE 信封。
  - 要求 **Dart SDK ≥ 3.10.0**；本机 Flutter 3.47.1 / **Dart 3.13.1** → 门槛满足，可装。
  - 需 CORS（web/调试）+ 自带的鉴权头注入（我们端点要 `Bearer`，genkit 客户端是否支持需验证）。
- 架构张力：用户的「全栈」直觉正确（GenUI/DevTools/结构化流式/统一多模型只有端到端才兑现）；但当前 ADR-0015 + ADR-003 是反方向决策——后端代理、前端与模型解耦、可无 key 跑 MockProvider 闭环。
- 若走全栈 Genkit（需用户拍板，勿擅自改）：① 后端挂载 `serve_flow` 把 flow 以原生 action 暴露（安全层包进 flow 或 wrapper action，守住 ADR-008）；② 前端 `flutter pub add genkit`，用 `defineRemoteAction` 替 `SseClient`，类型模型 TutorReply/QuestionPreview 配 `fromStreamChunk`；③ 代价=前端耦合 Genkit 线协议（部分反转 ADR-0015 的解耦收益）。建议分阶段：先并行挂原生端点（解锁 DevTools + GenUI 能力）同时保留生产自定义 SSE UI，再在小屏试点 `defineRemoteAction`。
- 待用户决策：是否从「解耦自定义 SSE」切到「全栈 Genkit Dart 客户端」。本会话仅分析，未改动代码。

## 修复二：生成任务 422 + 预览出题返回 mock
- 现象：(1) 点「生成任务」→ `POST /tasks/from-generated` 返回 422；(2) 点「预览出题」返回 mock 数据（而非真实模型生成）。
- 根因1（422）：前端 `home_notifier.dart` 的 `generate()` 调 `_persist(questions, body)` 时，`body` 漏注入 `questions`（`TaskFromGenerated.questions` 必填 `list[dict]`）；`savePreview` 才显式加了。修复：在 `_persist` 内统一 `body['questions'] = questions.map((q)=>q.toJson()).toList()`，并删除 `savePreview` 的冗余注入。
- 根因2（mock）：流式 flow `tasks_generate`（flows.py）调 `resolve_engine(input.model, parent_id=parent_id)` **没传 session**，且 `parent_id` 来自 `ctx.context` 是**字符串**（UUID 对象的 `str()`）；`engine.py` 第 1 步 `mc.parent_id == parent_id` 是 `UUID==str` **恒为 False**。两因叠加 → `ModelConfig` 自定义模型永不命中，回退全局 `LLM_PROVIDER=mock`（默认）。而同步 `batch-generate` 传的是 UUID 对象 + session，故曾行为不一致（也解释了之前"真实模型超时"只发生在同步路径）。
- 修复：(a) `engine.py` 比较改为 `str(mc.parent_id) == str(parent_id)`（兼容 UUID/str）；(b) `flows.py` 的 `tasks_generate` 与 `tutor_ask` 均在 `with Session(db_engine) as s:` 内调 `resolve_engine(..., session=s)`，使流式路径的 ModelConfig 解析与同步路径一致。
- 验证：后端 `ruff` 通过；新增 `tests/ai/test_engine_resolve.py`（字符串 parent_id 解析 ModelConfig、越权返回 None、缺 session 跳过）3 passed；全量 `pytest` 130 passed/3 skipped。前端 `flutter analyze` home_notifier 无警告。
- 说明：若用户未在下拉选模型且全局 `LLM_PROVIDER=mock`（无 key），预览仍走 mock——这是零 key 闭环设计；要真实生成需在 UI 选真实模型或配置全局 provider+key。

## 修复三：「生成任务」「预览出题」报 stream finished without a final result chunk
- 现象：两按钮都报该错，后端 `POST /ai/tasks/generate` 返回 200。根因两层：
  1. 主 bug：`generate_questions_stream` 真实引擎路径取 `result = await sr.response` 后直接 `result.stem`/`yield result`，但 Genkit 流式 `.response` 是 `ModelResponse`，结构化输出在 `.output`（而非响应对象自身）→ `AttributeError` 抛异常。异常被 `genkit_fastapi.event_stream` 捕获并发 `data: {"error": ...}` 错误帧，但 Dart 客户端（genkit 0.15.1 client.dart:97）**只认 `error: ` 前缀帧**，`data:` 错误帧既无 `result` 也无 `message` 键被静默丢弃 → `responseCompleter` 永不完成 → 报 "stream finished without a final result chunk"。
  2. 错误被掩盖：服务端错误帧前缀与 Dart 客户端不一致。
- 修复：
  - `flows.py`：`generate_questions_stream` 改为 `parsed = result.output` 再 `yield parsed`（QuestionSchema）；单题失败 `except` 回退 `_mock_question` 保证流不中断、末帧仍正常。
  - `main.py`：monkeypatch `genkit_fastapi.handler.format_stream_error`，把错误帧前缀从 `data: {"error": ...}` 改为 Dart 客户端可解析的 `error: {"error": {...}}`（含 message）。
  - `tests/utils/sse.py`：`parse_genkit_sse` 同步识别 `error: ` 前缀错误帧并抛 AssertionError（与真实线格式对齐）。
- 验证：无效 spec 实测返回 `error: {"error":{"message":"3 validation errors for TaskGenInput..."}}`，Dart 端将正确抛真实文案；后端全量 `pytest` **130 passed/3 skipped**（`test_generate_stream.py` 2 passed、`test_engine_resolve.py` 3 passed 均含）；`ruff` 通过。前端未改动（server-side 修复）。

## 设计讨论：合并「生成任务」+「预览出题」为统一「出题」（grill-with-docs）
- 用户报「生成任务」题都生成出来后 422（日志 `POST /tasks/from-generated -> 422`）。经穷举复现：端点仅在 `questions` 缺失或 `child_id` 非法 UUID 时 422；前端 `child_id` 恒为合法 UUID（`SelectedChild.id` String），且 `_persist` 已注入 `questions`（修复三的 home_notifier.dart:98）。真实流式题卡原样 POST 只拿 403（越权，非 422）。结论：用户 422 极可能是后端未热加载上轮的 `_persist` 修复 → 让其重启 `uv run fastapi dev` 再验；若仍 422 需贴 Network 面板 `detail` 原文。
- `InsecureKeyLengthWarning`（HMAC key 20B<32B）为独立安全问题，SECRET_KEY 应 ≥32 字节，先记下。
- 架构确认：两端点均为客户端主动调用（home_notifier.generate→_genkit.streamTasks→/ai/tasks/generate；流结束→_persist→POST /tasks/from-generated），服务端不自驱。
- 经 `/grill-with-docs` 访谈锁定合并方案（ADR-0016）：单一「出题」按钮 → 流式预览 → 家长手动「存为任务(draft)」/「加入题库(逐题多选)」；题任务关系=关联引用（question_id 指向题库 Question）；复用 from-generated，新增 POST /questions/bank/bulk。已写 ADR-0016 到 `../../docs/decisions/娃娃学习App_ADR.md`、补术语表「出题与题库同步」段。

## 功能：题库题目批量删除（被任务引用则跳过）

## 设计：出题推理过程流式通道（ADR-0017，grill-with-docs）
- 延续 R6：当前 `tasks_generate` 走 `output_schema=QuestionSchema` 结构化输出，后端每题只发 1 个 chunk（成品题卡）+ 末帧 result，中间无 token 流 → 「每题干等、整张弹出」割裂感根因。
- 访谈澄清并纠正：原 R6 误拆 think/typing/card 三类型。`thinking`=出题思路文字（内容），`typing`=前端打字机动画（呈现，非数据类型），`card`=成品题卡（数据）。合并后 = 单一 `REASONING` 通道（承载思路文字 + 打字机渲染），`card` 仍独立。
- 三决策（grill 锁定）：① 推理来源=混合——所有模型走「单次调用 + `reasoning` 字段 + 客户端打字机」打底（零额外成本、含 mock）；家长选 reasoning 模型时 `engine.supports_reasoning=True` 自动升级为真·思维链 token 服务端推送。② 推理仅预览态、不落库（零迁移）。③ 粒度=逐题，`q_index` 关联题卡。
- 数据结构（已定稿，未实现）：SSE chunk 由裸 `QuestionOut` 升级为带 `type` 信封（`REASONING`/`STEP`/`CARD`，对齐 AG-UI `BaseEvent.type` 多态）；`QuestionSchema`/`QuestionOut`/`QuestionPreview` 增 `reasoning:str`；前端 `TaskGenChunk` 密封类 + `fromStreamChunk` 按 `type` 分发；`home_notifier` 按 `q_index` 累积推理 + `ReasoningTypewriterWidget`。末帧 result 形状不变（cards 列表），`fromResponse`/`onResult` 无需改。

## 修复：概览「最近任务」+「任务」列表页永久卡 Loading
- 现象：概览页「最近任务」与任务列表页（ParentTasksView）都一直转圈（永久 Loading）。
- 根因：`parent_overview_view.dart` 的 `build` 内直接 `ref.read(parentTasksNotifierProvider.notifier).load()`——**在 build 期间同步修改被本组件 watch 的 provider**，是 Riverpod 反模式，会触发重入重建循环（每次 rebuild 重新进入 Idle→load，反复重置为 Loading），使共享的 `parentTasksNotifierProvider` 永远停在 Loading。两个页面共用同一 provider，故一起卡死。注：列表页自身的 `load()` 是在 `initState`（生命周期正确）触发，单独不会卡，是被概览的循环拖死。
- 修复：把 load 触发推迟到当前帧绘制之后（`WidgetsBinding.instance.addPostFrameCallback`），并在回调内再判一次 `ParentTasksIdle`，保证每次 Idle  episode 至多触发一次 load、绝不在 build 期间改状态。其余 `load()` 调用（initState/按钮/retry）本就合规，无需改。
- 验证：`flutter analyze lib/features/home/presentation/widgets/parent/parent_overview_view.dart` → No issues found。全项目 analyze 剩 12 个预存 error 全在 `test/`（NetworkService.delete 假实现未跟进 `body` 参数 + genkit 0.15.1 签名），与本次无关。

- 用户指出该 Riverpod 反模式已多次出现，要求写入 flutter 开发规范。已落地双保险：
  1. **代码层**：新增 `frontend/lib/shared/utils/load_once.dart` 的 `WidgetRef.loadWhenIdle(provider, isIdle, load)` 扩展——把「本帧绘制后 + 再判空闲」双重保护封装成一行式，从 API 层面杜绝 build 期误改。概览页已改用它（作为活样例），`flutter analyze` 两文件零问题。
  2. **规范层**：`docs/agents/frontend.md` 新增「## Riverpod 反模式清单（门禁级）」章节，含反模式 #1（build 内同步改被 watch 的 provider → 卡死 Loading，含 ✗/✓ 写法与 `loadWhenIdle` 用法）与 #2（build 主体禁止放 `notifier.xxx()` 副作用），并附 grep 自查命令。AGENTS.md 已引用该 frontend.md 为事实源，无需改。

## 修复：家长「任务」列表页 RenderFlex 布局崩溃（unbounded width）
- 现象：任务列表页（ParentTasksView，home index 8）渲染抛 `RenderFlex#88ffc NEEDS-LAYOUT` 连环错：`RenderFlex children have non-zero flex but incoming width constraints are unbounded` → `RenderBox was not laid out` → `'child.hasSize': is not true`。
- 根因：`shared/theme/app_theme.dart` 的 `AppCard` 在 `onTap != null` 分支用 `ShadButton.ghost(width: double.infinity)` 包裹 `ShadCard`；该 ghost 按钮内部 `ConstrainedBox(minWidth:∞, maxWidth:∞)` 把**无限宽**灌入 `ShadCard`，而 shadcn `ShadCard` 内部固定为 `Container → Row(mainAxisSize: min) → Flexible → Column → Flexible → child`，无限宽一路透传到卡片内容。任务卡片 `_TaskCard` 内容含 `Row(Expanded(Text), _statusTag)`，`Expanded` 在无限宽下直接崩。`onTap == null` 分支（直接返回 `card`）从不注入无限宽，故非点击卡片不崩。已读 shadcn_ui 0.56.2 源码 `card.dart:206-251` 与 `button.dart:1127-1143` 坐实根因。
- 修复：把 `onTap` 分支的 `ShadButton.ghost(...)` 包裹改为 `GestureDetector(onTap: onTap, behavior: HitTestBehavior.opaque, child: card)`。`GestureDetector` 是 pass-through（不注入宽度、不需 Material 祖先，安全用于 ShadApp），卡片内容拿到父级有界宽、仍靠自身 `Expanded` 撑满宽度，整卡可点行为不变。已加注释说明为何不能用 `ShadButton.ghost(width: double.infinity)`。
- 范围核查：全项目 grep 仅 `parent_tasks_view._TaskCard` 一处传 `onTap:`，其余 `AppCard(` 均不带 `onTap`，故改动仅精准命中崩溃页；`ShadButton` 仍被 line 808 使用，无悬空 import。
- 验证：`flutter analyze lib/shared/theme/app_theme.dart` → No issues found；全项目 analyze 仍剩 12 个预存 error 全在 `test/`（NetworkService.delete 假实现 + genkit 0.15.1 签名），与本次无关。建议真机/模拟器跑一次任务 Tab 做最终视觉确认（当前环境无法起 Flutter 运行实例）。
