# 2026-09-10

## /assistant/chat 后台架构审查（只读分析，未改代码）

五层：L0 `features/assistant/router.py`（SSE/鉴权/配额/落库）→ L1 `app/ai/runtime/`（AgentRuntime 发现+路由+装配，无状态）→ L2 `app/ai/subagents/<biz>/`（tutor/question/tasks，BaseSubAgent.run）→ L3 `app/domain/`（TutorService/LLMProvider ABC/Retriever/Safety/Quota）→ L4 `genkit_provider`+`ai/engine`+`generation/segment/parsers`。

协议三层（关键抽象）：领域模型 `GeneratedQuestion/TutorResult` →（SchemaQuestionParser）→ 语义事件 `QuestionStreamEvent`（ReasoningDelta/QuestionCard/QuestionFailed）→（translate_stream，攒批 16 字符）→ 传输帧 `AssistantEvent`（AG-UI/SSE）。每层只跨一层翻译。

### 发现的抽象裂缝（未修）
1. **engine 注入是死链**：runtime `resolve_engine(model, parent_id, session)` → `build_subagent(engine=)` → `BaseSubAgent.self.engine`，但 `GenkitProvider` 内部一律 `resolve_engine()` 无参，`self.engine` 零消费 → 家长 ModelConfig / 前端 `model` 字段在 /assistant/chat 上实际不生效，永远走全局 LLM_PROVIDER。这是功能 bug。
2. **manifest.skills 零消费**：`question_sop.md` / `tutor_sop.md` 存在但无任何代码读取，纯死元数据。
3. **manifest.tools 无调度器**：`_tool()` 只产出 TOOL_CALL 事件标签，实际调用硬编码在 agent 里，没有 tool 执行框架。
4. **文件夹发现不完整**：`discover()` 只发现 manifest，agent 类仍要在 `registry.py` 手工登记；`_PRIORITY` 在 intent_router 硬编码业务名 → 「新增 subagent = 丢一个文件夹」不成立。
5. **LLM 分类未接线**：`classify(llm_classify=)` 从未传参，混合路由实际只有「规则 + 启发式」两级。
6. **handle() 契约是死抽象**：全仓无调用方（tasks.handle 直接 raise NotImplementedError）。
7. 安全拒绝顺序：`decide` 判 INPUT_UNSAFE 后，router 仍先跑配额判定，可能先抛配额超限而非安全拒绝。

## 修 CI 红线：`test_assistant.py` 两条（本地绿 / CI 红）

根因：测试依赖真实 LLM。本地 `backend/.env` 有 `LLM_PROVIDER=deepseek` + key → 出题/答疑拿到真内容；CI 无 `.env` → mock，出题返回 0 题（无 DATA 帧）、答疑返回 None（ASSISTANT_MESSAGE 文本为空）。用 `LLM_PROVIDER=mock uv run pytest` 精确复现：2 failed / 144 passed / 2 skipped，与 CI 一致。

修法（测试与环境解耦）：
- 新增 `backend/tests/utils/fake_provider.py`：`FakeLLMProvider` 实现 `LLMProvider`，产出固定讲解文本 + `ReasoningDelta`/`QuestionCard` 序列。
- `backend/tests/conftest.py`：import app 前置 `LLM_PROVIDER=mock`；新增 autouse 夹具 `fake_llm` 打桩 `app.ai.runtime.runtime.build_provider`。
- 顺手修真 bug：`TutorService.aexplain` 缺 `raw is None` 分支（同步版 `explain` 有），无引擎时会下发 `answer=None / blocked=False`——娃娃看到空讲解、家长侧却记为一次正常答疑。并把 `explain` 改为 `asyncio.run(aexplain(...))` 同步桥，消除双份复制粘贴管道（分叉的根源）。

验证：本地有 key / 强制 mock / 临时移走 `.env` 三种环境均 146 passed 2 skipped，`ruff check .` 通过，耗时 22s → 6.5s。

## AI Agent 分层抽象分析：本项目 vs `pi`（只读，产出 `docs/architecture/AI_Agent分层抽象对比分析.md`）

参照 `pi`（pi-ai / pi-agent-core / pi-coding-agent / pi-tui，gist annilq/4fc974da06bbb7ccbadeebad404b7877）。

**核心结论**：`pi` 是「能力栈」分层（每层可独立消费）；本项目是「数据流管线」分层（同一条 SSE 管道的切段，不可独立消费）。`AgentRuntime` 语义上其实是 **Router**，不是 Runtime——没有 agent loop，模型从未见过工具声明。

**实测确认**（ADR-0030 已修掉 09-10 早间列的 1/2/4/5，但 3 与 6 仍在）：
- `subagents/{question,tutor,tasks}/tools/` **全是空目录**（只有 `__init__.py`）；`app/ai/tools/__init__.py` 的 `list_tasks`/`search_knowledge` 是普通函数，非 LLM 可调用声明 → `TOOL_CALL`/`TOOL_RESULT` 帧是装饰性的，调用顺序硬编码在 `QuestionSubAgent.run()` 的 for 循环里。
- `handle()` 仍是死抽象（全仓无调用方，tasks 版直接 `raise NotImplementedError`）。

**三大架构问题**：
1. `LLMProvider.generate_question_stream(**9 个业务参数)` 泄漏业务语义（subject/grade/knowledge_point/persona_hint…）→ 加业务要改 provider，换 provider 要懂教育。对比 pi 的 `streamFn(model, context, opts)`。ADR-0021 说「Persona 在调用方注入」只做了一半：`_build_question_prompt` 仍在 `app/ai/generation.py`（出题）与 `genkit_provider.py`（答疑/批改）两处散落。
2. 「工具」是谎言（见上）。
3. 层不可独立消费，别拿 pi 的渐进式组合叙事套。

**其余差异**：skills 语义相反（本项目=prompt 片段/数据面；pi=生命周期钩子/控制面，LLM 看不见）；本项目缺 compaction（全仓 grep 无 compact 实现，history 靠 `[-6:]`/`[-10:]` 硬截断）；路由下沉进 runtime（pi 在应用层 per-channel）；注入粒度本项目是对象级 `build_provider(engine=)`，pi 是函数级 `streamFn`（可拦每次请求）；无统一拦截点，安全闸门散在 `runtime.decide`/`TutorService`/`parsers` 三处。

**新发现的双源真相**：`router._get_runtime()` 模块级单例 与 `registry._CACHE` 进程缓存 是两处独立发现结果（ADR-0030 刚消灭一处，这里又长一处）。

**建议排序**：P0 收窄 `LLMProvider` 到消息级（`stream(system, prompt, output_schema, history)`，prompt 组装整体搬进 `subagents/question/`）；P0 给「工具」一个说法——推荐**删掉谎言**（删 `manifest.tools`、`_tool()` 改名 `_step_begin/end`、`TOOL_CALL` 帧改名 `STEP_START`），因为三个业务都不需要 loop；P1 加 compaction（`Conversation.summary`）；P1 路由改 `BaseSubAgent.can_handle() -> float` 置信度（保持确定性，不回退 LLM 分类）；P2 消掉双源真相。

## 用户新需求：把 agent 层抽成可复用的通用协议规范
- 用户希望后端 `app/ai` 提供**业务无关的 agent 抽象层**（协议 + subagent 注册 + subagent 路由 + 工具调用 + 统一事件流），作为内部通用规范接入各业务子项目，各子项目实现自己的 subagent 处理自身业务。
- 分析结论：**当前架构不满足（作为通用框架）**。它是一条"教育业务专属的 agent 管线"，离"可复用的通用 agent 框架"差两块：
  1. **真实 tool loop 缺失**（最大缺口）：`manifest.tools: list[str]` 仅声明；`subagents/*/tools/` 目录全空（仅 `__init__.py`）；`app/ai/tools/__init__.py` 直接 import `app.features.tasks.repository`（业务 repo，非模型可调用 tool）；`BaseSubAgent._tool()` 只是 TOOL_CALL/RESULT 事件对句柄，**runtime 里无 tool 执行阶段**，模型从未见过 tool schema、从不选择工具，调用是 `agent.run()` 内硬编码 for 循环。
  2. **解耦抽取缺失（结构性 blocker）**：`app/ai` 重度反向依赖 `app.domain`/`app.features`/`app.db`/`app.core`（engine→core.config/crypto/db.models.ModelConfig；runtime→domain.build_provider/build_retriever/safety.check_input；parsers/translate/generation→domain.provider；tutor/question agent→domain.quota.SUBJECTS/domain.tutor；tools→features.tasks.repository；debug_log→core.db/features.ai.repository）。无法作为独立包被其它业务工程 pip 复用。
- 已具备、可复用的资产：① `protocol.py` 的 `AssistantEvent` AG-UI 式信封（通用，仅 DATA.type/blocked 沾教育词，可用 extra 扩展）；② `registry.py`+`manifest.py` 的文件夹发现注册（机制与业务无关）；③ `intent_router.py` 的 manifest 驱动规则+启发式路由（不认识业务名）；④ `AgentRuntime.run` 的 `AsyncIterator[AssistantEvent]` 统一 SSE 流形。
- 还需补：A 抽 `agent_core` 独立包（零业务 import，定义抽象 seam：LLMProvider 消息级 / Retriever / Safety / Tool）；B 真 tool loop（subagent 声明 `tools: list[ToolSpec]`，runtime 发 schema→收 tool_call→执行→回灌→loop）；C 收窄 `LLMProvider` 到 `stream(system,prompt,schema,history)`；D 翻译/解析下沉到各 subagent（core 去领域化）；E 放松协议教育词；F 暴露可插拔 `classify` 钩子（代码已注释"约 5 行"）。

## ADR-0031 落地：agent_core 独立包 + 全量迁移（代码已写，全绿）

把 `app/ai/runtime`、`app/ai/subagents/base`、`app/ai/subagents/registry` 抽成零业务依赖的独立包 `backend/agent_core/`（protocol/seams/registry/router/runtime/tools/subagent/errors + pyproject.toml）。`app/ai/` 退化为教育集成层（仅 question/tutor/tasks 重写实现 `agent_core.subagent.BaseSubAgent`）。

**agent_core 关键契约（落地版）**：
- `LLMProvider.stream(system, prompt, *, schema, tools, history) -> AsyncIterator[StreamEvent]`，`StreamEvent = TextDelta | ToolCall | StructuredDone`（消息级，零业务参数）。
- `RouteDecision` 无 `subject` 字段（业务无关；subject 由端点算、经 `ctx.extra` 透传）。
- `AgentRuntime.run(message, *, role, ctx, deps, business=None, session=None) -> AsyncIterator[AssistantEvent]`（直接返回异步迭代器，非元组）。
- `BaseSubAgent` 是纯 `ABC`（非 `@dataclass`）；`tools: list[ToolSpec] = []` 类级 + `__init__` 内 `self.tools = []`。生产 subagent（question/tutor/tasks）保持 `tools=[]`（一次性，保 DATA/题卡前端契约）；真实 tool loop 经 `run_with_tools` + 单独契约测试示范。
- `ChildSafety` 适配 `check_input` 进 agent_core 的 `Safety` seam，仅 child 角色注入。

**本会话实测修的坑**：
1. `BaseSubAgent.tools = field(default_factory=list)` 用在非 dataclass 上 → `tools` 是 `Field` 实例 → `run_with_tools` 抛 `'Field' object is not iterable`（所有内容路径 `AGENT_ERROR`）。改 `tools: list[ToolSpec] = []` 类级 + `__init__` 初始化 `self.tools`。

## grill-with-docs：app/ai 与 subagents 边界三问分析（仅分析，未改码）

用户三问：① subagents 应提到与 app 同层；② ai 下通用方法移入 agent_core；③ generation.py/parsers/question.py 业务耦合，应抽象或移入 subagents。

**核心事实（已 grep 验证）**：
- `app/ai` 在 ADR-0031 后已是「教育集成层」：engine.py（**唯一真正 `import genkit`**，读 ModelConfig 表+解密+拼 genkit，最 app 耦合）、segment.py（genkit chunk→归一化 `Segment`，**用 duck-typing 读字段、零 genkit 硬 import，已是引擎无关**，可直接进 agent_core）、debug_log.py（绑 app.core.db+features.ai.repository 落库）、model_catalog.py（服务商产品配置）、generation.py、parsers/question.py、subagents/。
- `generation.py` 被两拨吃：出题 subagent（`build_question_prompts/stream_question/step_label`）+ **genkit_provider 的 `GradeSchema`（批改，line 26）** + 落库/测试兼容包装 `generate_question`。`parsers/question.py` 的 `schema_field` 也被 genkit_provider 吃（line 163）。→ 两文件不是纯出题，含批改 schema。
- agent_core 硬编码 `module_base="app.ai.subagents"`（runtime.py:58、registry.py:97-103）；端点 `features/assistant/router.py:86` 注释也写死此路径。

**结论**：
- Q1 直觉对（subagents 是应用层业务 agent，≠ 框架），但「与 app 同层」过头：subagents 重度 import app.domain/features/core，非可复用包，提为 `backend/subagents/`（与 app 同级）会误导且仍反向 import app.*。正确粒度＝Q3 落地后提为 `app/subagents/`（与 app/ai 同级、仍在 app 内）；命名保持 `subagents`（它们 subclass BaseSubAgent）。
- Q2 前提不成立：app/ai 无真正通用方法可进 agent_core（会破坏其零依赖契约）。仅 engine.py 真 import genkit 且本就是 app 专属（ModelConfig/crypto/settings），不应进 core；**segment.py 已是引擎无关（duck-typing，零 genkit import），可不经 genkit 集成直接进 agent_core**；debug_log 是 DB 实现、model_catalog 是产品配置——都应留 app。正确做法：agent_core 只放 seam 抽象 + 已无关的通用件（如 segment），实现与引擎留 app。
- Q3 诊断对，「移入 subagents」推荐，但须**拆分**不可整搬：出题专属（prompt 组装+stream_question+_generate_question*+translate）归 `app/ai/subagents/question/`；`GradeSchema` 是批改的归 grader；`schema_field` 小工具留 domain/随 grader。「模型调用时注入」已通过 `LLMProvider` 实现（ADR-0031），不必回推 agent_core。顺带废弃 engine 版 `_generate_question(_stream)`，让 generation 不再 import `app.ai.engine`，app/ai 即无教育内容 → 反过来支持 Q1。

**建议顺序**：先 Q3(b) 拆 generation（出题管线收进 question subagent、GradeSchema 归 grader、跑通测试），再评估 Q1 提升。Q2 基本不做。待用户拍板是否落 ADR-0032。

## Q4 追加分析：把 genkit 集成进 agent_core 是否可行（否决，改 contrib）

用户进一步问：把 genkit 集成进 agent_core，能否把 ai 的通用功能收进 core，使抽象更简单、基座稳定、外部拓展稳定。

**结论：不应该，且前提站不住。**
1. genkit 集成进 core 并不能解锁"通用功能上提"：ai 真正通用的只有 `segment.py`，而它**已零 genkit 依赖、今天就能进 core**，与 genkit 集不集成无关；其余（generation/parsers=教育业务、debug_log=DB、model_catalog=产品配置、engine=app 专属）都不是通用件。genkit 边界只卡住 `engine.py`（本就不属于 core 的引擎解析器），没挡住任何真·通用功能。
2. 它让基座**更不稳定**：genkit 一旦住进 core，切引擎=重写 core 的 genkit 部分=改基座，与用户"基座少改"目标相反。现状切引擎只动 `engine.py`+换一个 `LLMProvider` 实现，core 纹丝不动。
3. 它破坏"外部拓展稳定"：引擎无关 core 才让新方案插自己的 `LLMProvider`；genkit 烤进 core=强制所有消费者吃 genkit=强制收敛。

**推荐机制（非塌缩）：contrib 拆分**——
- `agent_core/` 保持纯引擎无关（稳定基座），把已无关的 `segment.py` 收进来。
- 新增 `agent_core/contrib/genkit.py`（或 `agent_core[genkit]` extra）：提供 `GenkitLLMProvider`（实现 `LLMProvider` seam）+ genkit `Segment` decoder。
- `app/ai/engine.py` 瘦身为「解析 model_ref → 构造 `GenkitLLMProvider`」。
- 收益：引擎切换仍只动一处（contrib 实现）、core 不动；外部方案自由插自己的 Provider；genkit 依旧首选引擎但不污染基座。

待用户拍板：做 2（先 contrib 拆分+segment 上提，小改零风险）或做 1（先落 ADR-0032 固化边界）。记忆修正：本段及上段 segment.py 描述已更正为「零 genkit 硬 import、引擎无关」。
