# 开发记录：中小学错题复习智能体（OpenEdu）

> 本记录说明这套系统是**怎么被开发出来的**。开发方式以**提示词驱动**为主，
> 因此这份文档的重点不是罗列代码，而是记录**人与 AI 如何协作**、以及**智能体的提示词是如何设计的**。

---

## 一、开发方式：以提示词驱动为主

本项目**不是逐行手写代码为主**，而是采用**提示词开发**（也称对话式开发）：

- **人负责**：想清楚要什么、验收结果、做关键决定；
- **AI 负责**：给出方案、写出代码、按反馈修改。

实际过程就是一轮轮"**说清楚需求 → AI 生成 → 运行验证 → 用提示词让它改 → 再验证**"。

这种方式的好处是**想法到成品的距离很短**：一个功能从"想要"到"能用"，往往只需要几轮对话；
代价是**AI 并不天然理解你的真实意图**，所以"把需求说清楚"和"每次都验证"变成了最关键的两件事。

---

## 二、一次迭代是怎么走完的

项目形成了一套固定的节奏，每一轮都按下面六步走：

1. **说清楚需求**——用大白话描述"我想要什么、给谁用、解决什么问题"。
2. **先质询，不动手**——让 AI 反过来追问需求里模糊的地方（边界、已有功能冲突、命名不一致等），把问题问透再开工。
3. **落成书面规格**——把确认后的需求写成一份简短的规格说明，作为这一轮的共同依据。
4. **拆成小任务**——把大功能拆成一张张能独立完成、独立验证的小任务票。
5. **逐个实现并验证**——每完成一小块就运行测试、实际点一遍，通过了再进入下一块。
6. **重要决定留档**——凡涉及架构方向、命名、取舍的决定，都写成决策记录（ADR）存档。

---

## 三、关键做法：一次只做一小块

开发中反复验证有效的一条经验是——**把大功能拆成"垂直切片"**，每片都能独立完成并验证，避免一次改动过大导致失控。

举例：课件模块的一轮改造就拆成了 7 张票，逐张完成并各自通过测试：

| 序号 | 这一票做什么 |
|---|---|
| 01 | 在课件中心给出明确的"新增课件"入口 |
| 02 | 课件的基本信息（标题、状态、教学目标）可以编辑 |
| 03 | 简化环节类型（分两步：先兼容、后彻底清理） |
| 04 | 支持老师**手动**添加讲解环节（此前只能靠 AI 生成） |
| 05 | AI 补充讲解时，引用**真实存在**的素材与场景，不凭空编造 |
| 06 | 让"课堂练习"在演示页面真正显示出来 |
| 07 | 收尾清理，去掉历史遗留的类型字段 |

教师端扩展、交互图形场景等模块，也采用了同样的"拆票 → 逐票验证"方式。

## 四、智能体的提示词是怎么设计的（本项目的核心）

对一套教育智能体来说，**提示词就是它的"岗位说明书"**：规定它**是谁、能做什么、不能做什么、话该怎么说**。

本项目的提示词不是一大段话，而是按**不同岗位分开写**、各司其职：

| 提示词 | 管什么（通俗解释） |
|---|---|
| 伴学答疑 | 讲解要适合中小学生的年龄；学生跑题时要温和地把话题拉回学习 |
| 智能出题 | 必须输出规整的题目（题干、选项、解析），好让系统直接拿去用 |
| 学科人格 | 语文、数学、英语等不同学科，讲解风格不同（数学重步骤，语文重理解） |
| 学情查询 | 只能报**系统里真实存在**的数据，不许估计、不许编造 |
| 课件起草 | 按知识点和老师填写的教学目标，组织出讲解环节 |
| 引导卡片 | 需要老师去某个页面操作时，给出**可以直接点的按钮**，而不是只说一句话 |
| 资料解析 | 从上传的教材、卷子里提炼出知识点 |
| 内容安全 | 不适合中小学生的内容，拒绝回答并说明原因 |
| 会话摘要 | 给一段对话做简短总结，方便续接 |

### 三条硬原则

1. **不许编造**——学情数字必须来自系统真实数据；出题引用必须来自已上传的资料。答不上来就说明"查不到"，而不是给一个看起来很像真的数字。
2. **适合年龄**——讲解符合中小学生认知，不超纲发挥，不用成人化表达。
3. **可以溯源**——回答要标注"这条来自哪份资料、哪个知识点"，方便老师核对。

> 这三条不是写在文档里的口号，而是**直接写进提示词、并用自动化测试守住**的约束。

## 五、功能是按什么顺序长出来的

整体遵循"**先能用，再打磨**"，按模块逐步推进：

1. **基础骨架**——登录、教师端与学生端两套界面、模型管理。
2. **AI 助手**——统一对话入口，出题、查任务、查学情、查题库、伴学都从这里进。
3. **学习闭环**——出题 → 布置任务 → 学生作答 → 错题进错题本 → 按 1/2/4/7/15 天提醒复习 → 做对毕业。
4. **资料库与知识点**——上传教材资料，系统自动整理出知识点目录，并支撑答疑时的检索。
5. **课件与课堂**——课件编辑、素材库、课堂练习、交互图形场景。
6. **教师工作台**——速览层（错题分布、正确率、掌握度）+ 分析层（按学科、年级、学期、知识点逐层细看）。
7. **打印导出**——把题目自动排版成纸质练习卷（**只含题目和作答空位，不含答案**）。
8. **教师端扩展**——班级管理、学生管理、批量派发、统计。

## 六、质量是怎么保证的

提示词开发很容易"看起来做完了"，所以用几条硬性规矩兜底：

- **每次改动都跑自动化测试**（界面与后台都有），没跑通就不算完成；
- **代码规范自动检查**，拦截明显问题；
- **重要决定写成决策记录（ADR）**，编号从 0044 起，已累计到 0078，共数十份。AI 不记得上一轮对话，这些文档能把上下文接续下去；
- **人工实际试用**：老师真的走一遍流程，发现问题再用提示词让 AI 修。

## 七、经验与反思

1. **"先说清需求"最省时间**——模糊需求直接让 AI 写，返工更多；先用一轮对话把需求问透，反而更快。
2. **AI 会自信地编造**——必须显式写进提示词"只能用真实数据"，并用测试守住，否则它会给出很像真的假数字。这是教育类应用最不能犯的错。
3. **一次改太大容易失控**——拆成小任务、逐块验证，是提示词开发最有效的节奏。
4. **决策留档极其关键**——对话有上下文长度限制，决策记录让项目在几十轮开发后仍保持一致。
5. **提示词是核心资产，要单独维护**——模型可以换、代码可以重构，但提示词背后的设计意图必须能追溯。
6. **部分环节仍在打磨**——例如"出题如何与学生错题、掌握度联动"在开发过程中被反复讨论并留有专门方案，实际进度以代码仓库与决策记录为准。
