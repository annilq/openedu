# 12: 路由能力清单文案调优——先改 criteria，用同一脚本量化收益

> 标签：`ready-for-agent`
> 来源对话：2026-10-20 用户「①先改 manifest 的 name/description 文案（criteria 的值）用同一脚本量化收益，而不是换权重；②再议学生端单独阈值或与 LLM 分类器交叉校验」
> 关联：ADR-0104（规则路由移除）、ADR-0105（不命中落能力引导）、ADR-0097（能力清单 = manifests 投影）、ADR-0098（二执行体）、ticket 11（实测基线与否决 largha）、ticket 13（门控与交叉校验，本票之后议）
> 术语以 `CONTEXT.md` 为准；业务键 tasks / tutor / capability 的含义见各自 `manifest.py`

**What to build:** 只改三个 manifest 的 `name` / `description`——它们就是喂给决策模型的 `criteria` 值——并用 ticket 11 那套评测脚本在**扩大的中文用例集**上量化收益。明确不动：不换权重、不改阈值、不改路由代码、不改 `ROUTING_HISTORY_LIMIT`。

**Blocked by:** ticket 11（已 done；提供基线 8/13、失败清单与可复跑脚本）

**Status:** `ready-for-agent`（未开工）

---

## Problem Statement

决策模型真正上线后（ticket 11），中文实测的 top-1 准确率只有 **8/13 = 62%**。用户视角的后果不是「慢一点」，而是**答非所问**：

1. **教师问学情，被送去讲解**：「我班有哪些学生」→ `tutor`（pmax 0.598），助手开始答疑而不是查名单。
2. **教师查错题，被判成能力自述**：「我的错题有哪些」→ `capability`（0.432 vs tasks 0.427，仅差 0.005），助手回一段「我能做什么」。
3. **教师求讲解，被送去出题**：「这道题为什么选 B」→ `tasks`（0.674）；续接转讲解「第一题怎么算的？」→ `tasks`（0.544）。
4. **最坏的一条——学生问解题，被 0.956 的高置信判成能力自述**：学生发「23 + 45 怎么算」，学生端可见集只有 `[capability, tutor]`（K=2），模型以 0.956 选了 capability。学生得到的是「我能做什么」的清单，而不是他问的那道题。

第 4 条叠加 ADR-0105 后尤其糟：**判成 capability 与「都没命中」在用户侧完全同形**（都是能力引导），所以这条错误不但答非所问，还**伪装成了系统设计好的降级路径**，从轨迹上看不出来是错的。

根因判断（ticket 11 已用实测排除另一条路）：

- **不是权重问题**：候选 `largha` 实测 5/13 = 38%、平均置信 0.270（阈值 0.5 下近乎恒不决策）、12 轮中文历史直接 `422 STATE_TRUNCATED`。换权重这条已在 ticket 11 否决。
- **是 `criteria` 的可分性问题**：模型看到的三条选项文本（`_capability_text` = `name` + `description` + `actions`）彼此重叠——「题目 / 题」同时出现在 tasks 与 tutor 的描述里；tutor 的描述只有一句泛泛的「给出适龄、纯学习相关的讲解」，没有说清它**不**做什么；capability 的描述「说明助手能做什么、不能做什么」读起来像在回答任何以「怎么 / 有什么」开头的句子。

所以先动文案：这是唯一一个「改完立刻能用同一脚本量化」的杠杆。

## Solution

把三条 `criteria` 改写成**彼此互斥、各自带排他句**的能力陈述，然后用同一套脚本、扩大的用例集，逐版量化：

1. **改文案，不换权重**：三个 manifest 的 `name` / `description` 是唯一的改动面（外加必要的既有断言同步）。
2. **量的是生产要发的那份文本**：评测脚本改为直接吃生产的 manifest 投影（`discover_subagent_manifests()` + `_capability_text`），不再维护一份手抄的 `CAPABILITY` 字典——否则「改文案 → 重跑」量的是两份可能已经漂移的文本。
3. **先扩容再迭代**：13 条用例里单条权重 7.7%，改一句文案就可能「修好 2 条、碰坏 1 条」而看不出是噪声。先把用例扩到 ~30 条（每条失败用例补 2–3 条近邻说法），并**用旧文案跑一遍新用例集**作为对照基线。
4. **单变量迭代**：一次只改一个业务的描述，跑一遍脚本，记录单变量增益；不一次改三条再归因。
5. **达不到验收线就换机制**：若同一份文本无法同时满足「用户读得懂」与「模型分得开」，启用降级方案——新增 `routing_criteria` 字段（模型专用描述），并补一条 ADR 修订说明为何 ADR-0097 的单一事实源在此处让步。

## User Stories

1. 作为教师，我希望我问「我班有哪些学生 / 我的错题有哪些」时落到任务学情助手，以便拿到真实数据而不是一段讲解或一段自我介绍。
2. 作为教师，我希望我问「这道题为什么选 B / 第一题怎么算的」时落到伴学答疑，以便得到讲解而不是被再出一张题卡。
3. 作为教师，我希望续接时改参数（「数学」「换成四年级的分数题」）仍留在出题助手，以便我不必把上下文重说一遍。
4. 作为教师，我希望我问「你能做什么」时落到能力自述，以便看到职责边界与可点方向。
5. 作为学生，我希望我发「23 + 45 怎么算」时落到伴学答疑，以便我拿到这道题的解法。
6. 作为学生，我希望我问「你能帮我做什么」时才看到能力清单，以便它出现在我真的在问助手能力的时候。
7. 作为学生，我希望我追问「还是不懂」时继续由伴学答疑接住，以便对话不中断。
8. 作为用户（教师/学生），当我说「随便聊聊 / 你好呀」这类模糊句时，我希望助手给能力引导而不是胡乱执行，以便我立刻知道可以往哪走。
9. 作为用户，我希望路由错了的时候**不要是高置信地错**，以便至少还有机会落到能力引导这种无害出口。
10. 作为开发者，我希望「改文案」这件事有可复跑的量化回路，以便任何一次措辞调整都能说出「涨了几个点、哪条翻正、哪条碰坏」。
11. 作为开发者，我希望评测脚本用的 criteria 文本与线上逐字同源，以免我量的是一份已经漂移的副本。
12. 作为开发者，我希望每次迭代只动一个变量，以免增益无法归因。
13. 作为开发者，我希望用例集足够大且有近邻变体，以免文案被「调参调到 13 条上」，换个说法就塌。
14. 作为维护者，我希望 criteria 的不变量（长度、互斥动词、排他句）有 CI 内的契约测试守着，以免某次「顺手改下描述」悄悄把准确率打回去。
15. 作为维护者，我希望契约测试**不断言逐字文案**，以免每次措辞迭代都要改一堆测试。
16. 作为维护者，我希望改 `description` 对用户可见能力清单的影响被显式核对，以免为了路由把面向用户的文案写成模型黑话。
17. 作为产品，我希望能力清单（用户看到的「你可以让我：…」）仍然是人话，以便它同时承担引导职责。
18. 作为产品，我希望学生端的路由正确率不低于教师端，以便最弱势的入口（只有一个执行体可选）不是最容易错的那个。
19. 作为开发者，我希望长历史（12 轮）仍然不触发 `422 STATE_TRUNCATED`，以免会话一长就整体降级。
20. 作为开发者，我希望路由延迟不明显劣化（p50 仍在几十毫秒量级），以免为了准确率把每轮消息都变成慢请求。
21. 作为开发者，我希望评测结果按日期落 JSON 并可对比，以便几周后回看能说出「62% → X%」是哪一版文案带来的。
22. 作为用户，我希望本轮改动**不改变**任何功能边界（出题仍走 `POST /tasks/generate`、学生仍看不到出题与答案），以便这是一次纯路由质量的改进。

## Implementation Decisions

### 1. 改动面就是三个 manifest 的 `name` / `description`

- 决策模型的候选选项来自 `agent_core.router._capability_text(manifest)`：``name`` + ``description`` + （有则）`actions: …`。三者即全部可调杠杆。
- `actions` 那一行只有 tasks 有（`actions: task_generate`），保留不动——它是结构化动作键的提示，不是自然语言卖点。
- **不改**：`LayaDecisionModel` 的权重、阈值、`_ROUTING_INSTRUCTIONS` 的问句、`_build_routing_state` 的形状、`ROUTING_HISTORY_LIMIT`。这些要么已被 ticket 11 实测否决（换权重），要么归 ticket 13（阈值与门控）。

### 2. 保持单一事实源：criteria = 用户可见清单的同一份文本

- 能力自述 subagent 的能力清单（`capability_catalog`）渲染的是同一个 `name` + `description`（ADR-0097：清单 = manifests 投影，正是因为「手抄清单与真实拓扑漂移」才改的）。本轮**沿用这一条**：只改这一份文本，同时服务「用户读」与「模型读」两个消费者。
- **不引入第二份「只给模型看的描述」为默认方案**：那会重新打开 ADR-0097 修掉的那类漂移（改了用户清单忘了改路由描述，或反之）。
- **降级条件（显式熔断）**：若实测证明同一份文本无法同时满足两端——要么路由分不开，要么为了分开把面向用户的文案写成了模型黑话——则新增 manifest 字段 `routing_criteria`（模型专用，缺省回落 `description`），并补一条 ADR 修订记录说明为何在此处让 ADR-0097 的单一事实源让步；同时加契约测试要求该字段非空且与 `name` 不矛盾。

### 3. 评测脚本改吃生产投影（消除手抄副本）

`.scratch/ai-intent-routing/eval/decision_model_eval.py` 当前有一份硬编码的 `CAPABILITY` 字典（「与 manifest 保持同源」只是注释约定）。本轮改为：

- 把 backend 加进 `sys.path`，`from agent_core.registry import discover_subagent_manifests`、`from agent_core.router import _capability_text`，criteria 直接取生产投影；
- `INSTRUCTIONS` 从适配器常量导入，不再复写一句中文；
- 用 `backend/.venv/bin/python` 运行（此前用系统 python），保证 import 路径与线上一致；
- 保留 `--models` / `--json` / `--probs` 参数与新结果文件名约定 `results-<日期>[-<版本标记>].json`。

这样「改 manifest → 重跑脚本」量的才是线上真正会发出去的那串文本。

### 4. 用例集扩容 + 先建对照基线

- 现有 13 条计分用例 + 2 条模糊句 + 1 条长历史。扩到约 30 条：每条失败用例补 2–3 条近邻说法（同义改写、加/去主语、口语化），并补学生端的算术/概念/追问变体。
- 每条用例标注来源：`trace <id>`（真实事故）或 `构造`。真实事故形状（trace `73000ee0` 的续接）不得被稀释掉。
- **新用例集先用旧文案跑一遍**，把这份基线 JSON 一起入库——否则「新文案 24/30」无从判断是文案之功还是题目变简单了。
- 模糊句（`随便聊聊` / `你好呀`）继续**不计分**，只观察 pmax 是否诚实（低于阈值即安全回落能力引导）。

### 5. 文案写法原则（可证伪，逐条由脚本验证）

- **专属动词**：tasks = 查询 / 生成 / 管理；tutor = 讲解 / 答疑 / 分析这道题；capability = 回答关于助手自身的问题。
- **排他句**：每条都写清自己**不做**什么（如 tutor「不生成题卡、不查数据」；capability「只在用户问助手能做什么时，不解答学科问题」；tasks「不讲解题思路」）。
- **消除跨类共用词**：「题目 / 题」今天同时出现在 tasks 与 tutor 里 → tasks 侧改用「练习 / 题卡」，tutor 侧用「这道题 / 解法」。学生端 K=2 对这类共用词最敏感（S01 就是这么错的）。
- **长度上限**：单条 criteria 控制在约 120 字内，保住 1024 上下文里的长历史余量（ticket 11 实测 12 轮 ≈ 719 字符仍不截断，但余量不多）。
- 每版文案只改一个业务，跑一次脚本，记录「改了什么 → 哪条翻正 / 哪条碰坏」。

### 6. 验收线（acceptance）

在**扩容后的用例集**上，与旧文案的基线对照：

- 教师端：准确率不低于旧文案基线，且**不出现 pmax ≥ 0.8 的错误**（高置信错误是最坏形态）；
- 学生端：S01「23 + 45 怎么算」必须翻正为 `tutor`，学生端用例全对；
- 长历史 12 轮：不出现 `422 STATE_TRUNCATED`；
- 延迟：p50 仍在同一量级（不引入数量级劣化）；
- 面向用户的清单读起来仍是人话（人工核对，不是脚本判据）。

达不到 → 启用决策 2 的 `routing_criteria` 降级方案，而不是继续微调同一份文本。

### 7. 既有断言的同步核对清单

改 `description` 会同时改到：能力自述的用户可见清单（`capability_catalog` 渲染「name：description」）、运行轨迹页里的业务名。需同步核对（**只更新断言，不改语义**）：

- `tests/ai/test_capability_subagent.py`（清单首行与内容断言）
- `tests/api/routes/test_assistant.py`（轨迹里的业务名断言）
- `tests/ai/test_tasks_subagent.py` / `test_intent_routing_contract.py` / `test_agent_runtime.py`（business/name 配对断言）

## Testing Decisions

- **pytest 侧唯一接缝仍是 `AgentRuntime.decide`**（INDEX §测试缝既有纪律）：所有离线断言打在它的返回值上——「给定角色 + 历史 + 消息 → 落在哪个业务」，不断言内部走了哪一级。本票不新增 pytest 接缝。
- **① 的量化不在 pytest 里**：它需要本机 ollaya 服务，不能进 CI。量化落在评测脚本 + 按日期落盘的 JSON（可复跑、可跨版本对比），这是 ticket 11 已经建立的既有做法。
- **新增一组轻量契约测试（criteria 不变量）**，补上「脚本不在 CI 里」的空档：
  - 每条 criteria 长度不超过约定上限；
  - 任一条 criteria 不包含另一条的**专属动词**（防止文案回潮到今天这种互相重叠的状态）；
  - 学生端可见的那两条（capability / tutor）各自含排他句。
  - **不断言逐字文案**——本轮就是要反复迭代措辞，逐字断言会让每次迭代都碎。
- **好测试的判据**：只断言外部行为（落在哪个业务 / 呈现在用户面前的文本是什么），不断言实现细节（哪一级路由、第几个候选）。
- **回归纪律**：跑 `tests/ai` + `tests/features/assistant` + `tests/api/routes/test_assistant.py`（`.env` 就位态），再按项目纪律隐藏 `.env` 跑一次全量（带 `--basetemp`），唯一允许的红是已知的 `materials test_empty_text_422` 环境性红。

## Out of Scope

- **换权重**（ticket 11 实测否决 `largha`；任何新候选进白名单前必须先跑本票的脚本）。
- **阈值 / 门控 / 交叉校验**（ticket 13，本票之后议）。
- Modelfile `CALIBRATION` 重标定（需要标注集，独立议题）。
- `ROUTING_HISTORY_LIMIT`、历史压缩、`state` 截断策略（ticket 11 Follow-ups 的另一条，长历史一旦开始截断才动）。
- 前端任何改动；结构化出题端点 `POST /tasks/generate` 的链路。
- 新增 subagent 或调整可见角色（学生端仍只可见 capability / tutor）。

## Further Notes

- **K=2 的不对称**：学生端候选只有 2 个，`probabilities` 的分布比教师端更极端，S01 的 0.956 就发生在这里。本票先用文案解决；若文案见顶仍有高置信错误，ticket 13 的「按业务/角色设不同采纳门槛」是下一个杠杆。
- **capability 误判的代价不对称**：判成 capability 与「没命中」在用户侧同形，而判成执行体会答非所问。这条观察直接喂给 ticket 13（capability 应当有更高的采纳门槛）。
- **样本量仍然小**：即便扩到 ~30 条也只是「能看出方向」的量级，结论按「翻正/碰坏了哪几条」读，不按百分点做精细比较。
- **评测是零风险离线动作**：脚本只 POST 到本地 ollaya，不碰数据库、不改生产配置；改文案本身有端到端影响（用户可见清单），故仍需跑全量。
