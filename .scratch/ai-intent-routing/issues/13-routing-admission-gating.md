# 13: 路由采纳门控——学生端阈值与 LLM 分类器交叉校验

> 标签：`done`（2026-10-21 落地；ADR-0107）
> 来源对话：2026-10-20 用户「①先改 manifest 的 name/description 文案（criteria 的值）用同一脚本量化收益，而不是换权重；②再议学生端单独阈值或与 LLM 分类器交叉校验」
> 关联：ADR-0104、ADR-0105（不命中落能力引导 + `fallback_guide` 声明式纪律；其「命中」定义由 ADR-0107 修订）、**ADR-0107（本票的决策记录）**、ticket 11（门控改用 `probabilities`、K=2 不可比问题）、ticket 12（先改文案并量化，本票的前置）
> 术语以 `CONTEXT.md` 为准

**落地摘要（先看这段）**：门控从适配器上移到 runtime（决策模型只出分数、`min_adopt_score` 声明式取值、LLM confidence 同表门控、`extra["rejected"]` 可观测），`consensus` 作为可选策略落地。**两个候选都被实测数据否决**：候选 A（学生端更高阈值）在留出集上反向（净收益 −2 → −3），低分段不存在可分离区间；候选 C（交叉校验）把有害错降到 0，但同样是付那次 LLM 往返，直接信 LLM 分类全面更好（正确 42 vs 27）——故不启用、不进默认。顺带修掉 `confidence` 未自报被当 0 而误杀 6 条正确路由的缺陷。**新发现转 ticket 14**：LLM 分类器在准确率上显著优于本地决策模型（留出集 9/10 vs 5/10），但延迟 60 ms → 1081 ms，默认原语选型需用户拍板。

**What to build:** 在 ticket 12 的文案收益见顶之后，回答一个问题——**模型给出了一个业务，我们要不要采纳它**。今天答案是「只要 pmax ≥ 0.5 就采纳」，全角色同一阈值、且不区分业务。本票把这件事从「适配器里的一个浮点数」升级为「runtime 的一处显式门控策略」，并由此让两个候选方案变得可表达、可量化：学生端单独阈值，与 LLM 分类器交叉校验。

**Blocked by:** ticket 12（必须先拿到改文案后的准确率与每条用例的 pmax 分布；没有数据选阈值就是拍脑袋）

**Status:** `done`（2026-10-21）

## Problem Statement

1. **阈值是适配器的一个构造参数，不是策略**：`LayaDecisionModel(threshold=0.5)` 固定在适配器里，运行时无从按角色调整——学生端与教师端共用 0.5，而学生端只有 2 个候选（K=2），同样的「置信水平」在这个可见集上更容易走到极端值（S01 的 0.956 就发生在这里）。
2. **「不置信」与「没决策」被压成同一个 `None`**：适配器不达阈值就返回 `None`，runtime 只看到「这个原语不决策」，看不到「它其实选了 X 但只有 0.43」。于是「换个更低的阈值再看看」「两个原语互验」这类策略**在当前结构下表达不出来**。
3. **LLM 分类器的置信度完全没被门控**：`classify_llm` 会返回 `RoutingDecision.confidence`，但 `_route_llm` 只把它记进 `extra`，从不参与采纳判断——同一次路由里，两个原语的门控强度是不一致的。
4. **误判代价不对称**：判成执行体（tasks / tutor）会答非所问；判成 capability 则与 ADR-0105 的「都没命中」在用户侧**完全同形**（都是能力引导），从轨迹上分不出是对还是错。今天对所有业务用同一个阈值，等于默认这两种错误代价相同。

## Solution

先把门控从适配器上移到 runtime（一处显式策略），再在它之上量化两种候选：

1. **门控上移**：决策模型只负责「给出分布」；runtime 负责「这个结果要不要采纳」。阈值不再是适配器的构造参数，而是一张**声明式**的门控表（默认 + 角色覆盖 + 业务自述覆盖）。
2. **然后才谈两个候选**：
   - **学生端单独阈值**（按角色）：学生端候选少、易极端，可用更高门槛换取「宁可落到能力引导，也不要自信地答非所问」。
   - **与 LLM 分类器交叉校验**（consensus）：两个原语都跑，一致才采纳；不一致则落能力引导（或按声明的优先级取其一）。
3. **取值必须来自 ticket 12 的脚本数据**：把每条用例的 pmax 摊开，看「正确路由的最低 pmax」与「错误路由的最高 pmax」之间有没有可分离区间；没有区间，阈值就不是有效杠杆，那就只剩交叉校验。

## User Stories

1. 作为学生，我希望我发「23 + 45 怎么算」时不要因为某个业务拿到 0.95 就被判成能力自述，以便我拿到解法而不是一份清单。
2. 作为学生，我希望当路由真的拿不准时，我得到的是能力引导这种无害出口，以便我立刻知道可以往哪走。
3. 作为教师，我希望「查学情/查错题」这类请求不会因为阈值一刀切而被送去讲解，以便我拿到真实数据。
4. 作为用户，我希望助手**宁可说不知道，也不要自信地答非所问**，以便错误信息不会以高置信的样子出现。
5. 作为开发者，我希望「不置信」与「没决策」是两种可区分的结果，以便我能写「低置信 → 换个原语再问一次」这类策略。
6. 作为开发者，我希望门控规则只有一处，以便调阈值不必同时改适配器和 runtime。
7. 作为开发者，我希望 LLM 分类器的置信度和决策模型的概率走同一套门控，以便两个原语被同等对待。
8. 作为开发者，我希望阈值/门控规则是**声明式**的（延续 ADR-0105 的 `fallback_guide` 做法），内核不硬编码 `capability` 之类的业务键。
9. 作为开发者，我希望任何门控改动都能用 ticket 12 那套脚本量化（记录 pmax、记录是否被采纳），以便我知道挡掉了哪些对的、放过了哪些错的。
10. 作为产品，我希望学生端（唯一一个只能选执行体或引导的入口）不是最容易错的那个，以便最弱势的入口最稳。
11. 作为开发者，我希望交叉校验是**可选策略**而不是默认，以便为每轮消息引入第二次模型往返这件事是被显式选择的。
12. 作为用户，我希望引入交叉校验后首字延迟仍在可接受范围，以便路由质量不以明显变慢为代价。
13. 作为维护者，我希望门控相关行为在 CI 内有离线测试（桩即可），以便不必依赖本机 ollaya 就能守契约。

## Implementation Decisions

### 1. 先做「门控上移」这个使改动（推荐，A 与 C 都依赖它）

- 决策模型适配器**不再**在内部做阈值比较而吞掉结果：它返回带分数的结果（沿用 `DecisionResult.choice / prob / raw`），由 runtime 决定是否采纳。
- runtime 侧新增一处门控判断（概念形状，来自本票的设计而非现有代码）：

  ```text
  score(primitive) = 决策模型的 pmax | LLM 分类的 confidence
  accept = score >= threshold_for(role, business)
  ```

  `threshold_for` 的取值顺序：业务自述的覆盖值 → 角色覆盖值 → 全局默认（0.5）。
- **声明式、内核不认识业务键**（延续 ADR-0105 的 `fallback_guide` 纪律）：若某个业务需要更高的采纳门槛（典型是 capability——它误判与「没命中」同形），由 manifest 声明字段（如 `min_adopt_score`）承载，注册表解析；runtime 只认「这个业务声明了更高门槛」这个事实，不认 `capability` 这个名字。
- **代价**：适配器「低置信 → `None`」的既有语义要改，现有契约测试（如「门控用的是 pmax 而非 confidence」那组）需迁移到 runtime 层，断言点不变（给定输入 → 落在哪个业务）、位置变了。

### 2. 候选 A：按角色（学生端）单独阈值

- 形状：角色覆盖表，学生端取更高门槛（具体值由 ticket 12 的数据定，本票不预设数字）。
- 适用条件：数据里存在可分离区间——即学生端错误路由的 pmax 集中在某个值以上，而正确路由的 pmax 也在附近但更高。
- 风险：抬门槛会把一部分正确的低置信路由一起挡掉，变成「什么都不做 → 能力引导」。挡掉多少必须由脚本数出来，不能凭直觉。

### 3. 候选 C：与 LLM 分类器交叉校验（consensus）

- 形状：新增策略档位（如 `consensus=[decision, llm]`），两个原语都跑；一致才采纳，不一致 → 落能力引导（默认）或按声明优先级取其一。
- 收益：决策模型「自信但错」的那类（S01 的 0.956）最可能被第二个原语否掉。
- **代价必须显式接受**：默认策略 `auto` 今天在决策模型命中时**不**调用 LLM；交叉校验会让每轮消息多一次 LLM 往返（延迟 + 成本），这与「每轮同步路由」的预算直接冲突。故只作可选策略，不进默认。
- 前置：需要先有门控上移（否则拿不到两个原语各自的分数做比较）。

### 4. 否决项（记录以免重复讨论）

- **继续微调单一阈值而不同时看误判代价**：capability 的误判与「没命中」同形，用同一阈值等于假设两者代价相同——这是错的。
- **在适配器里塞角色判断**：决策模型端口是业务/角色无关的抽象，把 `role` 塞进适配器会让两个原语的门控再次分家。
- **为了交叉校验把默认策略改成必跑两个原语**：延迟成本与「每轮路由」的定位冲突，属过度设计。

### 5. 量化协议（与 ticket 12 同一套脚本）

- 评测脚本扩展：除 choice / pmax / latency 外，记录**在若干候选阈值下的采纳结果**（是否 ≥ 阈值、不采纳则落到哪里），一次跑完即可画出「阈值 → 挡掉几条对的 / 放过几条错的」。
- 若引入交叉校验，脚本需能同时问决策模型与 LLM 分类器（后者需 provider 配置；无配置时该项跳过并标注）——**没有真实 provider 就不得据此下结论**。
- 结论表达为一张表，而不是一个数字：教师端 / 学生端 × 候选方案 ×（准确率、误判为 capability 的条数、落到能力引导的条数、p50）。

## Testing Decisions

- **接缝仍是 `AgentRuntime.decide`**（INDEX §测试缝的既有纪律）：本票所有离线断言都打在「给定角色 + 历史 + 消息 → 落在哪个业务」上，不断言内部走了哪一级、比较了第几个阈值。
- **离线可测、不依赖本机服务**：既有替身足够表达本票行为——`_StubDecisionModel`（可返回任意 prob）、`RoutingFakeProvider`（schema 为 `RoutingDecision` 时表态，含 confidence）。门控上移后新增用例：
  - 低置信不再静默消失，而是落到「不命中引导」（capability）；
  - 角色覆盖生效：学生端同一 pmax 被挡掉、教师端被采纳；
  - 业务自述的高门槛生效，且**内核不出现任何业务键字面量**（契约测试断言这一点）；
  - LLM 分类的 confidence 也走同一门控（此前完全不参与）。
- **阈值取值本身不进断言**：具体数字来自实测数据，会随文案/权重变化；测试只守「门控被应用了」这个行为，不守「阈值等于 0.7」这种会过期的值。
- **好测试的判据**：只断言外部行为（落在哪个业务、`routed_by` 是什么），不断言实现细节。
- **回归纪律**：`tests/ai` + `tests/features/assistant` + `tests/api/routes/test_assistant.py`（`.env` 就位态），再隐藏 `.env` 跑全量（带 `--basetemp`）；唯一允许的红是已知的 `materials test_empty_text_422` 环境性红。

## Out of Scope

- **改文案**（ticket 12，本票之前做）。
- **换权重 / 新增决策模型候选**（ticket 11 的纪律：任何候选进白名单前先跑中文评测）。
- Modelfile `CALIBRATION` 重标定（需要标注集；它改善的是概率的**绝对可信度**，与本票的「如何采纳」互补但不是同一件事）。
- `ROUTING_HISTORY_LIMIT` 与历史压缩、长历史截断策略。
- 前端任何改动；结构化出题端点链路。
- 把交叉校验设为默认策略（延迟成本，见决策 3）。

## 落地结果（2026-10-21）

### 1. 门控上移（使改动，A 与 C 都依赖它）—— 已落地

- `agent_core/adapters/laya.py`：`LayaDecisionModel` **移除 `threshold` 构造参数**，
  解析出选项就回传 `DecisionResult(choice, prob)`；`get_decision_model()` 同步去参。
- `agent_core/registry.py`：`SubAgentManifest` 新增 `min_adopt_score: float = 0.0`
  （`0` = 未声明）。
- `agent_core/runtime.py`：`min_adopt_score(business, role)` = 业务自述 → 角色覆盖
  （`set_role_min_adopt_score`）→ `DEFAULT_MIN_ADOPT_SCORE = 0.5`；`_route_decision` /
  `_route_llm` 共用 `self._adopt(...)`；被否掉的候选进 `extra["rejected"]`。
- `agent_core/adapters/llm_route.py`：`RoutingDecision.confidence` 改 `float | None`，
  `None`（未自报）不参与门控比较。
- 新策略档位 `consensus=[consensus]`：`_route_consensus` 两个原语都跑，业务一致且各自
  过门控才采纳（`routed_by="consensus"`），不一致 → 无命中引导。

### 2. 候选 A（学生端单独阈值）—— **实测否决，角色覆盖表保持空**

`eval/decision_model_eval.py --sweep eval/results-2026-10-21-final-landed.json`（44 条
计分用例，分调优集 / 留出集 / 分角色）：

| 阈值 | 调优集净收益(+1/−3/−1) | 留出集净收益 |
|---|---|---|
| 0.50（现状） | +2 | −2 |
| 0.53 | **+7** | **−3** |
| 0.55 | +7 | −3 |
| 0.60 | −2 | −3 |

低分段逐条摊开：`[0.50,0.53)` 在调优集是 2 有害错 + 1 正确，在留出集是 1 正确 + 0 有害错。
**不存在可分离区间**；学生端正确路由的 pmax 反而更低（0.41–0.76），抬到 0.75 才够到唯一
一条学生端有害错（0.702），代价是挡掉 10 条正确路由。→ **默认 0.5 不动，不设角色覆盖**。

### 3. 候选 C（交叉校验）—— 已实现、已实测、**不启用**

`--consensus`（44 条，决策模型 × 生产 LLM `deepseek-v4-flash`，走 `classify_llm`）：

| 策略 | 正确 | 有害错 | 无害错 | 落引导 | 净 | p50 |
|---|---|---|---|---|---|---|
| 决策模型（现状默认） | 29 | 9 | 2 | 4 | 0 | 60 ms |
| LLM 分类 | **42** | 1 | 0 | 1 | **39** | 1081 ms |
| 交叉校验 | 27 | **0** | 0 | 17 | 27 | 两者相加 |
| auto 现状（不采纳才问 LLM） | 33 | 9 | 2 | 0 | 4 | — |

留出集同向（5/10 · 9/10 · 4/10）。交叉校验把有害错降到 0，但同样付那次往返时直接信
LLM 分类全面更好 → **不进默认**，保留为 `AI_ROUTING_STRATEGY=consensus` 可选档位。

### 4. 顺带修掉的误杀（实测发现）

`confidence: float = 0.0` 时代，deepseek 有 13/44 条不填该字段 → 按 0 参与 0.5 门控会
挡掉 **6 条正确**路由（正确 36 → 30）。改 `float | None = None` 后未自报不再等同零置信
（且自报率随之上升：13 → 4）。

| 验收项 | 结果 |

## Further Notes

- **顺序不能反**：先文案（12）后门控（13）。文案能把 pmax 的分布本身拉开时，阈值这个杠杆才有干净的区间可用；文案没拉开就调阈值，只会得到「少错几条、也少对几条」的平移。
- **与 ADR-0105 的关系**：本票不改「都没有命中 → 能力引导」这条结论，只改「什么算命中」的判定——严格说是把 ADR-0105 的「命中」定义从「模型给出一个业务且 pmax ≥ 0.5」改成「模型给出的业务通过了门控策略」。若最终采纳了「按业务自述的更高门槛」，需在 ADR-0105 上补一条修订说明。
- **门控上移后，「低置信」第一次变得可观测**：今天 `routed_by="default"` 里混着「模型没回」与「回了但 0.43」，轨迹上分不出；上移后可以在 `extra` 里带上被否掉的业务与分数，便于下一轮定位（属于可选增强，不阻塞本票）。
