AI 功能返回协议 & 建议 Action 流向分析

基于代码实测（backend + frontend）· 回答两个问题：① 答疑是否 SSE / 各 AI 接口协议是否一致 ② 讲课建议 action 发到后端时 LLM 是否没处理、只返回匹配的数据

一、所有 AI 接口返回协议是否一致？

不一致。 代码里 AI 相关的端点混用了 SSE 流式 与 一次性 JSON 两种协议，且即便都是 SSE，流式的“粒度”也不同（逐 token vs 按轮次缓冲）。

端点协议是否 AI 生成说明
POST /assistant/chatSSE是对话式 AI 唯一入口，text/event-stream + X-Accel-Buffering:no（router.py:54）
GET /assistant/suggested-actionsJSON否服务端静态目录，零 LLM（service.py:179）
GET /assistant/conversations*JSON否历史会话读，纯 ORM
POST /tasks/generateSSE是结构化出题，流式题卡（tasks/router.py:89）
POST /tasks/{id}/questions/{tq}/regenerate-streamSSE是单题流式换题（tasks/router.py:288）
POST /tasks/{id}/regenerateJSON是整卷同步重生成，一次返回（tasks/router.py:297）
POST /tasks/{id}/questions/{tq}/regenerateJSON是单题同步换题（tasks/router.py:269）
POST /courseware（AI 起草）JSON是长耗时 AI 内容却一次性返回，provider.stream 内部缓冲后落库（courseware/service.py:260）
POST /courseware/{id}/redraftJSON是同上，返回逐段 diff（courseware/router.py:118）
结论：“长耗时的 AI 内容生成”里，/courseware 起草 / redraft 与同步换题是 一次性 JSON，只有 /assistant/chat、/tasks/generate、/tasks/regenerate-stream 是 SSE。这就是用户“等很久才一次性返回”的真凶之一——课件 AI 起草不是 SSE，是自然的一次性等全部生成完才回 JSON。

答疑（tutor）本身其实是真·SSE 逐 token 流

“答疑消息不是 SSE”更准确说是观感误判：协议层确为 SSE 且逐增量下推。完整调用链：

service.chat()→event_stream()→rt.run()→tutor.agent.run()
→aexplain_stream()→provider.tutor_stream()→adapter.stream()→genkit.generate_stream()
→逐 chunk → TextDelta(delta) → assistant_message(delta) 每 token 一帧

证据：tutor/agent.py:112 逐 delta 下推；aexplain_stream(tutor.py:272) 逐帧 yield；genkit_provider.py:114 tutor_stream 逐 delta；genkit.py:480 用 generate_stream 逐 chunk 产 TextDelta。tutor/agent.py:109-112 注释明写：旧 tutor() 曾缓冲整段 65s 才吐，已改为逐 token。

所以答疑“像一次性返回”的三个真实根因（按概率）：
  • ① RAG 检索前置延迟：tutor 在出首 token 前先做知识库检索（tutor.py:298），检索慢 → 前端先静默再出字，观感像“卡一下然后全来”。
  • ② 具体模型/引擎的 generate_stream 缓冲：代码已正确用流式 API，但若所配模型（尤其某些 OpenAI 兼容/o1 类）或代理不支持真流式，整段会攒齐再发。
  • ③ 你看到的其实是学情查询（query）而非答疑（tutor）：工具型 subagent 走 run_with_tools，整轮正文先累积进 acc 到轮末才 yield assistant_message(acc)（subagent.py:393-395），按轮次而非按 token 流式——所以 query 确实“一轮结束才整段冒出来”。

二、讲课时的建议 action，后端 LLM 是否没处理、只返回匹配数据？

分动作看：判断题（quiz）动作——是，LLM 完全没处理用户点的那句话；讲解/举例动作——否，LLM 仍处理（只是输入是预设文本）。

2.1 建议 action 本身是“服务端静态目录”，不是 LLM 生成的

讲课（带 courseware 上下文、有知识点 id）时空态会多出 3 个推荐操作，由 build_suggested_actions（service.py:179）从固定目录装配：

动作kindquiz点击后前端发出
举几个生活例子promptfalse{message: 预设文本, courseware}
出一道判断题prompttrue{message: 预设文本, quiz:true, courseware}
讲解这个知识点promptfalse{message: 预设文本, courseware}

前端证据：assistant_suggested_action.dart:3 “由服务端按上下文从固定目录装配（非 LLM 生成）”；assistant_suggested_actions.dart:67 onPrompt(a.payload, a.quiz)；chat_page:452 send(payload, courseware, quiz)；assistant_notifier.dart:136 AssistantChatReq(message, courseware, quiz)；assistant_requests.dart:30 仅 quiz:true 时带上。

2.2 “出一道判断题”= 标志位匹配的零 LLM 路径

点击“出一道判断题”后，后端 chat() 在 任何 provider 调用之前就拦截了：

if req.quiz:                                  # service.py:545
    return _stream_sse(_quiz_generate_stream(...))
# 上面这行直接 return，根本没走到 rt.run()

_quiz_generate_stream（service.py:245）调用 generate_question 管线，按 _resolve_kp_context 解析出的知识点上下文生成判断题——用户点选的那句预设文本从不被当作指令喂给 LLM。判定逻辑是确定性的小词典（service.py:129-148），答案存 pending_quiz 待用户作答，题卡下发前剥离答案/解析。

对你的问题的直接回答：“出一道判断题”这个建议 action，LLM 确实没有处理用户的动作消息——它是 quiz=true 标志位匹配的生成器触发，返回的是“按知识点生成的题”（不是从静态库“匹配”到的，而是 pipeline 现场生成，但不读你的动作文本）。注意：题本身仍是 LLM 生成的，只是不读你点的那句话。

2.3 “讲解 / 举例”动作——LLM 仍处理，但输入是模板

这两个动作 quiz=false，走正常 rt.run() → tutor/guide subagent 把预设文本作为 message 正常生成。因此 LLM 会处理，但处理的是服务端写好的模板指令（如“请详细讲解「分数乘法」…”），不是用户自由表达的意图。这是“模板化指令”，不是“零 LLM”。

判断题动作流向（零 LLM 读消息）

点击「出判断题」
↓ 携带quiz:true + 预设message
↓chat() 见 req.quiz→跳过 rt.run
↓_quiz_generate_stream→generate_question(知识点)
↓下发题卡（剥离答案）

用户的 message 文本在此链路被完全忽略。

讲解/举例动作流向（LLM 处理模板）

点击「讲解/举例」
↓ 携带quiz:false + 预设message
↓chat() 走 rt.run()
↓tutor/guide subagent→LLM 处理预设文本
↓逐 token 返回讲解

LLM 读到的是模板指令，不是用户自由意图。

设计含义（为什么是刻意的，不是 bug）：
  • 建议 action 用静态目录（ADR-0072）：零延迟、可控、可单测，避免每次空态都让 LLM 现编推荐项。
  • 判断题闭环用“确定性小词典判定 + pipeline 出题”：不靠 LLM 自由判定对错，避免小模型乱判（ADR-0040/0042）。
  • 所以“点 action = AI 理解我的意图”是认知偏差：quiz 是生成器触发，讲解是模板指令。若要让用户感觉“AI 真的在处理我点的东西”，这两类目前都不会把动作文本当语义输入。

三、若要“收敛到一处”，该补的两点

  1. 协议统一：把 /courseware 起草 / redraft 也改成 SSE（或至少流式进度），与 /assistant/chat 同观感；同步换题 regenerate 同理可补流式版。HTTP 多端点可保留（输出契约不同：气泡 / 落库任务 / 落库课件），但“长耗时 AI 内容”不应再是一次性 JSON。
  2. 流式粒度统一：query 等工具型 subagent 目前按轮次缓冲（subagent.py:393-395）；若希望与 tutor 一样“边生成边出”，需在 tool loop 里也把 acc 改为逐 delta yield（注意要保留“未查先答”硬失败判定所需的整轮聚合，不能简单拆散）。
  3. 建议 action 语义澄清：若产品希望“点讲解 = 针对该知识点深入讲解”而非“发一句模板”，当前模板已足够；若希望“点 action 后 AI 结合对话上下文续接”，需把 history 真正参与（目前 quiz 路径完全没用 history，prompt 路径已带 history）。

本报告全部结论均来自代码实测：backend/app/features/assistant/{router,service}.py、backend/app/domain/{tutor,genkit_provider}.py、backend/agent_core/{runtime,subagent,protocol,adapters/genkit}.py、backend/app/features/{tasks,courseware}/router.py，及 frontend/lib/features/assistant/**。
